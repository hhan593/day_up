## 一、为什么必须用线程池
1. **成本**：一个平台线程 = 一条 OS 线程 + 本地栈（`-Xss` 默认约 1MB，见 `16-JVM内存模型与GC.md`）+ JVM 内部结构，创建是系统调用级开销；3ms 的请求若付 1ms 建线程成本，吞吐直接砍半。
2. **无界创建必崩**：线程是稀缺 OS 资源。`for (int i = 0; i < 100_000; i++) new Thread(() -> handle()).start();` 通常在几百~几千个线程时抛 `OutOfMemoryError: unable to create native thread`（俗称 "too many open threads"），且崩溃发生在 OS/JVM 层，业务 `catch` 不住，进程直接不可用。
3. **需要配额 + 附带能力**：下游（DB 连接池、三方接口）能承接的并发是有限的，池是「上游并发度」的闸门；附带收益：复用、命名（可观测）、限流、拒绝、优雅关闭、指标。

## 二、ThreadPoolExecutor 七大构造参数（本篇核心）
| # | 参数 | 语义 | 工程实践 |
|---|---|---|---|
| 1 | `corePoolSize` | 常驻线程数，空闲也不回收 | 对齐「期望稳态并发」；`prestartAllCoreThreads()` 预热防首波抖动 |
| 2 | `maximumPoolSize` | **队列满后**才可扩容的上限 | 只有有界队列时才可能生效（见第三节） |
| 3 | `keepAliveTime` | 超出 core 的空闲线程存活时长 | 突发流量型设 30~60s；`allowCoreThreadTimeOut(true)` 可连 core 一起回收 |
| 4 | `unit` | 时间单位 | `TimeUnit.SECONDS` 可读性最好，别 `MILLISECONDS` 配 60 |
| 5 | `workQueue` | 待执行任务的缓冲队列 | **必须有界**；容量 ≈ 可容忍排队延迟 × 消费速率 |
| 6 | `threadFactory` | 线程制造者 | **务必自定义线程名 + UncaughtExceptionHandler + 非守护**，jstack 才认得出是谁的池 |
| 7 | `handler` | 线程满且队满时怎么办 | 默认 `AbortPolicy`；生产常用自定义「落 MQ / 落库 + 告警」 |

`workQueue` 选型（`maximumPoolSize` 生不生得效全看它）：`ArrayBlockingQueue(n)` 数组有界 FIFO，**推荐**；`LinkedBlockingQueue()` **无参构造默认 `Integer.MAX_VALUE` ≈ 无界**，是 OOM 之源；`SynchronousQueue` 不存元素、`put` 必须等到 `take`（handoff），只能配超大 `max`；`PriorityBlockingQueue` 无界且按比较器出队会**打乱 FIFO 时序**。
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(8, 32, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(512),                        // 有界，显式容量
        r -> { Thread t = new Thread(r, "order-pool-" + SEQ.incrementAndGet());  // 线程名 = 可观测的前提
               t.setUncaughtExceptionHandler((th, e) -> log.error("uncaught {}", th.getName(), e));
               return t; },
        new ThreadPoolExecutor.CallerRunsPolicy());
```

## 三、任务提交的执行流程（必考，顺序反直觉）
```
execute(task)
  ├─[1] workerCount < corePoolSize ?      是 -> 新建【核心线程】立即执行
  ├─[2] workQueue.offer(task) ?           是 -> 【入队等待】(由空闲 worker 在 getTask 里领走)
  ├─[3] workerCount < maximumPoolSize ?   是 -> 新建【非核心线程】执行
  └─[4] handler.rejectedExecution(task, pool)    -> 拒绝策略   （前一步不满足才往下判）
```
- **结论**：顺序是「**先入队、再扩容**」，与直觉的「先把线程开满再排队」**正好相反**；队列里的任务由已存活的空闲 worker **复用**执行，不新建线程。
- **推论**：无界队列 ⇒ [2] 永远成功 ⇒ `maximumPoolSize` 与拒绝策略**双双永久失效**，线程数恒等于 `corePoolSize`，队列无限长直到 OOM。这正是 `newFixedThreadPool`（无界队列）**任务堆积 OOM**、`newCachedThreadPool`（`SynchronousQueue` + `max = Integer.MAX_VALUE`）**线程数无上限 OOM** 的根因。

`core=2 / queue=ArrayBlockingQueue(2) / max=4`、任务均长时间不结束的逐次推演：

| 提交 | ①<core | ②入队 | ③<max | 落点 |
|---|---|---|---|---|
| T1 | 0<2 ✓ | — | — | 新建核心线程 W1 |
| T2 | 1<2 ✓ | — | — | 新建核心线程 W2 |
| T3 | ✗ | 成功 1/2 | — | 排队 |
| T4 | ✗ | 成功 2/2 | — | 排队 |
| T5 | ✗ | 队满 ✗ | 2<4 ✓ | 新建**非核心**线程 W3 |
| T6 | ✗ | 队满 ✗ | 3<4 ✓ | 新建非核心线程 W4（非核心到顶） |
| T7 | ✗ | 队满 ✗ | 4<4 ✗ | **触发拒绝策略**，默认抛 `RejectedExecutionException` |

> 注意：若 W1 在 T5 之前跑完，它会先取走 T3（复用、线程数不变），于是 T5 改为入队 —— 「同一段代码有时建线程有时不建」是正常的，取决于队列水位。

## 四、四种内置拒绝策略 + 自定义
| 策略 | 行为 | 副作用 |
|---|---|---|
| `AbortPolicy`（**默认**） | 抛 `RejectedExecutionException` | 不接住异常就会打断提交方 |
| `CallerRunsPolicy` | **谁提交谁执行**（在调用 `execute` 的那个线程上同步跑） | 天然**回压**，但**阻塞提交方**（如 Tomcat 工作线程），且**打乱时序**（新任务插到老任务之前） |
| `DiscardPolicy` | 静默丢弃、不抛异常 | **最危险**：数据无声消失，无日志无指标 |
| `DiscardOldestPolicy` | 丢弃**队首**最老任务后重试提交一次 | 丢掉的可能正是等了最久/最重要的那个 |
```java
class Compensate implements RejectedExecutionHandler {                 // 生产推荐：兜底不丢 + 告警
    @Override public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (e.isShutdown()) return;
        alarm.fire("order-pool rejected");                            // 打点/告警，让拒绝可见
        try { mq.send(toMessage(r)); } catch (Exception ex) { r.run(); }  // 落 MQ/落库补偿；MQ 也挂则本地同步跑
} }
```
另三种生产做法：**入队重试**（`queue.offer(r, 200, TimeUnit.MILLISECONDS)`，用等待换时间，只放慢不丢）；**降级**（返回旧缓存值/默认值，保住主链路 RT）；**动态扩队列**（把溢出任务转储到磁盘队列，不抬高内存上限）。

## 五、线程池状态机与生命周期
`RUNNING → SHUTDOWN / STOP → TIDYING → TERMINATED`（状态与 worker 数打包在 `ctl` 高 3 位，位运算细节见 `34-并发底层原理JMM与锁.md`）。

| 状态 | 接新任务 | 处理队列任务 | 进入条件 |
|---|---|---|---|
| `RUNNING` | 是 | 是 | 初始 |
| `SHUTDOWN` | **否** | **是**（跑完队列） | `shutdown()` |
| `STOP` | 否 | **否**，且中断在跑的 worker | `shutdownNow()` |
| `TIDYING` | 否 | 否 | 队列空 + worker 数归 0，独占 `terminated()` |
| `TERMINATED` | 否 | 否 | `terminated()` 执行完毕 |

- `shutdown()` 置 `SHUTDOWN`：不接新任务、存量跑完（平滑）；`shutdownNow()` 置 `STOP`：清队列 + 逐个 `interrupt()` worker，并**返回被移出队列、尚未执行的任务列表**；`awaitTermination(t)` 只等待，超时返回 `false`，**不改变状态**。
> 注意：`shutdownNow()` 返回的 `List<Runnable>` 是**唯一**找回机会；被中断的任务若吞掉 `InterruptedException` 又不落库重投，就永久丢了 —— 池内任务必须正确响应中断。
```java
@PreDestroy                                             // Spring 优雅停机标准模板
void shutdownGracefully() {
    pool.shutdown();
    try {
        if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {                   // 等存量跑完
            pool.shutdownNow().forEach(this::persistForRetry);               // 未执行任务落库重试，别丢
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) log.error("pool did not terminate"); }
    } catch (InterruptedException e) { pool.shutdownNow(); Thread.currentThread().interrupt(); }
}
```

## 六、为什么禁用 `Executors` 快捷工厂
《阿里巴巴 Java 开发手册》**【强制】**条款原意：线程资源必须通过线程池提供，不允许在应用中自行显式创建线程；**线程池不允许使用 `Executors` 去创建，而是通过 `ThreadPoolExecutor` 的方式**，理由是：
- `newFixedThreadPool(n)` / `newSingleThreadExecutor`：请求队列长度允许 `Integer.MAX_VALUE`（实为无界 `LinkedBlockingQueue`）⇒ **堆积大量请求/任务导致 OOM**，`max` 参数形同虚设；`newCachedThreadPool` / `newScheduledThreadPool`：允许创建的线程数量为 `Integer.MAX_VALUE` ⇒ **创建大量线程导致 OOM**。

结论：**显式 `new ThreadPoolExecutor(...)`**，让队列容量与线程上限成为代码里看得见的数字（`newVirtualThreadPerTaskExecutor` 不在此列，见第十三节）。

## 七、线程数到底怎么定
1. **经典公式（只是起点）**：CPU 密集 `N_cpu + 1`；IO 密集 `N_cpu * (1 + 等待时间/计算时间)` —— 后者假设所有线程同时阻塞，现实达不到。
2. **以压测吞吐与 RT 为准**：从 `N_cpu * 2` 起步逐步加压，找 **QPS 拐点**与 **P99 陡增点**，同时盯 CPU（>70% 再加线程基本无效）。
3. **按下游容量分配（最易忽略）**：若 HikariCP `maximumPoolSize = 20`，则**全站取连接的线程池并发总和超过 20 只是在排队**，加线程不增吞吐（→ `18-JDBC数据库编程.md`、`37-JVM调优与故障排查.md`）。
4. **多级隔离（线程池隔离）**：不同业务域独立池、快慢分离、核心/非核心分离，一个域打满不牵连其他域（与熔断限流同源 → `24-消息队列与微服务.md`）。
5. **失败案例**：某服务把「订单查询」与「报表导出」共用 `newFixedThreadPool(20)` + 无界队列；月末导出高峰占满 20 线程，查询请求排队 40s 超时，雪崩蔓延到上游全站。修复：拆两池 + 有界队列 + `CallerRunsPolicy` 回压，导出限 4 并发。

## 八、动态调参与可观测
`setCorePoolSize` / `setMaximumPoolSize` / `setKeepAliveTime` **运行期即刻生效**（队列容量不可变，故中间件常自定义 `ResizableCapacityLinkedBlockingQueue`）—— 这是所有「动态线程池」组件的基础。
```java
monitor.scheduleAtFixedRate(() -> {                      // 每 5s 采集指标 + 按队列水位自适应扩缩
    int q = pool.getQueue().size(); double water = q / 512.0;
    log.info("name=order active={} pool={} max={} queue={} completed={} largest={}", pool.getActiveCount(),
            pool.getPoolSize(), pool.getMaximumPoolSize(), q, pool.getCompletedTaskCount(), pool.getLargestPoolSize());
    if (water > 0.8 && pool.getMaximumPoolSize() < 64) {                       // 先扩 max，再提 core
        pool.setMaximumPoolSize(pool.getMaximumPoolSize() + 4);
        pool.setCorePoolSize(Math.min(pool.getCorePoolSize() + 2, pool.getMaximumPoolSize()));
    } else if (water < 0.1 && pool.getCorePoolSize() > 8) pool.setCorePoolSize(pool.getCorePoolSize() - 1);
}, 0, 5, TimeUnit.SECONDS);
```
- **注意**：必须**先 `setMaximumPoolSize` 再 `setCorePoolSize`**，反序会短暂 `core > max` 抛 `IllegalArgumentException`；上报指标用 `getActiveCount`（近似值）、`getPoolSize`、`getLargestPoolSize`（历史峰值，判断是否曾打满）、`getQueue().size()`、`getCompletedTaskCount()`。
- 开源参照：动态线程池组件（Hippo4j / Dynamic-TP 一类：配置中心推参数 + 指标上报）、Dubbo 的线程池隔离模型；Micrometer 接入见 `30-可观测性.md`。

## 九、任务异常处理（真实事故高发区）
**机制**：worker 抛出未捕获异常会**死掉**，池随后经 `addWorker` 补齐 ⇒ 表面「一切正常」，**异常静默无声**。

| 写法 | 异常去哪了 | 可靠性 |
|---|---|---|
| `submit(task)` | 被包进 `FutureTask`，**只有 `get()` 时才以 `ExecutionException` 抛出**；不 `get()` 永远看不到 | 差（最易吞异常） |
| `execute(task)` | 冒泡到线程，走 `threadFactory` 的 `UncaughtExceptionHandler` | 中（有日志，结果丢失） |
| 任务内 try-catch / 重写 `afterExecute` | 自己收口，可打点可告警 | **推荐** |
```java
pool.execute(() -> { try { doBiz(); } catch (Exception e) { log.error("biz fail", e); fallback(); } });  // 写法1
R v = pool.submit(callable).get(500, TimeUnit.MILLISECONDS);   // 写法3：及时 get(带超时)，异常在提交方可见
@Override protected void afterExecute(Runnable r, Throwable t) {                        // 写法2：统一收口
    super.afterExecute(r, t);
    if (t == null && r instanceof Future<?> f) { try { if (f.isDone()) f.get(); }        // 挖出 submit 吞掉的异常
        catch (ExecutionException e) { t = e.getCause(); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
    if (t != null) { log.error("task failed", t); alarm.fire(t); }
}
```

## 十、`CompletableFuture` 工程细节（API 清单见 `15` 篇，此处只补坑）
- **默认跑在 `ForkJoinPool.commonPool()`，全局共享**：并行流（`07-Lambda与函数式编程.md`）也用同一个池 ⇒ 带阻塞 IO 的慢任务会**污染整机的所有并行计算**。做法：异步一律**显式传入自定义 `Executor`**（或直接传虚拟线程执行器）。
- **超时**：JDK 8 无原生超时（只能另起 `ScheduledExecutorService` 手动 `cancel`）；**`orTimeout` / `completeOnTimeout` 是 JDK 9+ 才有**：`cf.orTimeout(300, MILLISECONDS)` 超时以 `TimeoutException` 异常完成，`.completeOnTimeout(defaultUser, 500, MILLISECONDS)` 超时给兜底值。
- **异常链区别**：`exceptionally` 仅异常路径执行（产出兜底值）；`handle` 成功/异常都执行、可转换结果；`whenComplete` 同样都执行但**不改变结果**，异常继续向下游传播。
- **一句话对照**：`thenCompose` = 有依赖的串行（前结果作后输入，扁平化 `CF<CF<T>>`）；`thenCombine` = 两个独立任务都完成后合并结果。

## 十一、线程间协作
### 1. 线程六态（`Thread.State`）
| 状态 | 触发条件 | jstack 里的样子 |
|---|---|---|
| `NEW` | `new Thread()` 尚未 `start` | 不在 dump 中 |
| `RUNNABLE` | 运行中，或**在 OS 层等 CPU/IO** | `runnable`；阻塞在 `socketRead0` 也算 RUNNABLE ⇒ 「RUNNABLE 多」≠ CPU 忙 |
| `BLOCKED` | 等待 `synchronized` 的监视器锁 | `blocked (waiting to lock <0x...>)` —— 锁竞争信号 |
| `WAITING` | `wait()` / `join()` / `LockSupport.park()` | `waiting on condition` / `parking to wait for` |
| `TIMED_WAITING` | `sleep(t)` / `await(t)` / `parkNanos` | `timed_waiting (sleeping)` |
| `TERMINATED` | `run()` 已返回 | 已消失 |

> 池「打满」在 dump 中的指纹：几十个同名线程（`order-pool-1..32`）全部 `WAITING (parking)` 卡在条件队列，或全部 `RUNNABLE` 卡在 `socketRead0`。定位方法见 `37-JVM调优与故障排查.md`。

### 2. `wait/notify/notifyAll` 与 `Condition`
- **必须在 `synchronized` 内调用**（它们操作的是 monitor），否则 `IllegalMonitorStateException`；**必须在 `while` 里判条件**而非 `if`，防**虚假唤醒**（spurious wakeup）与「被唤醒后条件又被别人抢走」。
- **丢唤醒事故**：`notify()` 只随机唤醒一个，若唤起到「另一类」等待者（生产者唤醒了生产者），真正该醒的没醒且无人再 notify ⇒ **永久挂死**；拿不准就 `notifyAll()`。
- **`Condition` 的价值**：一把 `Lock` 可挂**多条等待队列** ⇒ 精确唤醒、免 `signalAll` 惊群；`synchronized` 只有一个 wait set，做不到。
```java
class BoundedBuffer<T> {            // 有界缓冲区：生产者-消费者，两个 Condition 免惊群
    private final Deque<T> buf = new ArrayDeque<>(); private final int cap;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
    void put(T x) throws InterruptedException {
        lock.lock();
        try { while (buf.size() == cap) notFull.await();          // while：防虚假唤醒
              buf.addLast(x); notEmpty.signal(); }                // 只唤醒消费者，不误喊同伴生产者
        finally { lock.unlock(); }
    }
    T take() throws InterruptedException {
        lock.lock();
        try { while (buf.isEmpty()) notEmpty.await();
              T x = buf.pollFirst(); notFull.signal(); return x; }
        finally { lock.unlock(); }
    }
}
```

### 3. `CountDownLatch` / `CyclicBarrier` / `Semaphore`
| 工具 | 可否复用 | 计数能否增加 | 谁在等 | 典型场景 |
|---|---|---|---|---|
| `CountDownLatch(n)` | **一次性**，归 0 不复位 | 只能 `countDown()` 减 | 调 `await()` 的外部线程 | 并行调 3 个下游再汇总；等 N 项初始化 |
| `CyclicBarrier(n[, barrierAction])` | **可复用**（自动重置） | 可 `reset()` | 到达屏障的那 n 个线程本身 | 分段压测「同时起跑」；多阶段并行合并 |
| `Semaphore(permits)` | 可反复 | `release()` 可**超发**（动态放宽许可） | 拿不到许可的线程 | 限并发保护下游 QPS；配额型资源池 |
```java
CountDownLatch latch = new CountDownLatch(3);                       // 并行 3 下游，超时兜底
for (Down d : downs) pool.execute(() -> { try { d.call(); } finally { latch.countDown(); } });
if (!latch.await(800, TimeUnit.MILLISECONDS)) log.warn("keep partial result");
sem.acquire(); try { return thirdParty.call(); } finally { sem.release(); }  // Semaphore(50)：release 必在 finally
```
> 取舍：`CompletableFuture.allOf(a, b, c).get(800, MILLISECONDS)` 更省事且能取结果，`CountDownLatch` 主要出现在「线程不由你提交」的遗留代码。另：`Exchanger`（两线程成对交换数据）、`Phaser`（可动态注册、可分层的增强版 Barrier）了解即可，实际项目极少用。

## 十二、ThreadLocal：内存泄漏与脏数据串号
**结构**：**每个 `Thread` 实例持有一个 `ThreadLocalMap`**（不是 ThreadLocal 持有 map）；`ThreadLocalMap.Entry extends WeakReference<ThreadLocal<?>>` ⇒ **key 弱引用、value 强引用**。
```
 弱引用                    强引用链（泄漏路径）
 tl ─┐ (外部无强引用后 key 被 GC => null)
     v
Thread ──> ThreadLocalMap ──> Entry[key = WeakRef(tl)] ──> value = 用户对象
  线程池线程长期存活 => value 始终可达 => 永久堆积，且下次 get() 读到上一个请求的残留
```
- **为何 key 用弱引用**：避免「ThreadLocal 实例本身」因线程不死而被 map 强留、生命周期被拉长到线程生命周期；**为何 value 仍泄漏**：弱引用只断开 key，stale entry 仅在**下一次对该 map 做 `get/set/remove` 时**被探测式回收（`expungeStaleEntry`），池内线程后续用的是别的 ThreadLocal 时可能长期扫不到 ⇒ 线程不死，value 永驻。
- **`remove()` vs `set(null)`**：`remove()` 真正摘除 Entry 并清 key/value，**唯一正确做法**；`set(null)` 仍留下 value 为 null 的 Entry（桶位与 key 未清），且后续 `get()` 会重新走 `initialValue`（`withInitial(Supplier)` 是其声明式写法）。
- **第二个坑（比泄漏更致命）：脏数据串号**：线程复用使上一请求写入的用户身份/租户 ID 残留，下一请求读到 ⇒ **越权、数据串到别人账户**。故 `remove()` 是**纪律**而非优化：放 `finally`，或在 Filter/Interceptor 的 `afterCompletion` 统一清。
```java
public final class UserContext {   // clear() 必须在 finally / afterCompletion 调用
    private static final ThreadLocal<String> TENANT = ThreadLocal.withInitial(() -> "default");
    public static void set(String t) { TENANT.set(t); }  public static void clear() { TENANT.remove(); } }
```
- **跨线程失效**：`InheritableThreadLocal` 只在**子线程构造那一刻**复制父线程的值 ⇒ 池化线程早在第一个请求就建好，之后**永远拿不到当前请求上下文**（池化 + ITL = 失效）。解法：阿里开源 **`TransmittableThreadLocal`（TTL）**，以 `TtlRunnable.get(task)` / `TtlExecutors.getTtlExecutorService(pool)` 装饰，在**任务提交时**捕获快照、执行时回放、执行后恢复。
- **Web 实战**：Spring `RequestContextHolder` 内部即 ThreadLocal（请求结束由框架清）；日志 traceId 用 **MDC**（本质也是 ThreadLocal）⇒ 线程池下会丢，需搬 `getCopyOfContextMap()` / `setContextMap()` 或用 TTL/decorator（见 `30-可观测性.md`）；JDK 21 预览的 `ScopedValue`（`10-虚拟线程.md`、`11-Java8到21新特性.md`）不可变、作用域结束自动清除，从设计上消除这两类问题。

## 十三、虚拟线程时代的线程池观念变化
| 负载 | JDK 21 做法 | 理由 |
|---|---|---|
| IO 密集（RPC / DB / HTTP） | `try (var ex = Executors.newVirtualThreadPerTaskExecutor()) { ... }` | 虚拟线程极廉价、挂起不占载体 ⇒ **无池化需求**，「复用」这个支点消失了 |
| CPU 密集（压缩 / 加解密 / 序列化） | 仍用**平台线程池**，规模 ≈ `N_cpu` | 虚拟线程不额外提供核；`ForkJoinPool` / 并行流更合适 |
| 仍需资源配额 | 改用 **`Semaphore` 限并发**，而非限制线程数 | 虚拟线程会**绕过**你为限流设的线程数闸门（与 `10-虚拟线程.md` 官方原则一致） |

一句话：**从「限线程数」转向「限并发数 + 限队列」**。`ThreadPoolExecutor` 在拒绝策略、优先级、指标、CPU 任务上仍有价值，但不再是 IO 并发的默认答案；`ThreadLocal` 在百万虚拟线程下**变重**（每线程一份 map），应逐步迁到方法参数或 `ScopedValue`。

## 十四、常见面试题速答
> - **七个构造参数**：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`。
> - **执行流程**：核心线程 → **入队** → 非核心线程 → 拒绝策略；「先入队再扩容」是 `execute` 的真实顺序，后果是无界队列使 `maximumPoolSize` 与拒绝策略永久失效。
> - **四种拒绝策略**：`AbortPolicy`（默认抛异常）、`CallerRunsPolicy`（提交方执行、有回压但会阻塞且乱序）、`DiscardPolicy`（静默丢）、`DiscardOldestPolicy`（丢队首再试一次）。
> - **`shutdown` vs `shutdownNow`**：前者 `SHUTDOWN`（不接新任务、跑完队列）；后者 `STOP`（清队列 + 中断 worker + **返回未执行任务列表**）。
> - **为何禁用 `Executors`**：无界队列（fixed/single）或 `Integer.MAX_VALUE` 线程数（cached/scheduled）导致 OOM，必须显式 `new ThreadPoolExecutor`。
> - **`ThreadLocal` 为何泄漏**：`Entry extends WeakReference<ThreadLocal<?>>`，key 弱 value 强，`Thread → ThreadLocalMap → Entry.value` 强链随线程常驻；线程复用还会串号。解法 `finally { remove(); }`。
> - **线程数怎么设**：公式只是起点，按压测 QPS/RT 拐点定，且总并发不得超过 DB 连接池等**下游容量**，不同业务分池隔离。
