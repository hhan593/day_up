# 22 - 读写分离

> 目标：理解读写分离原理与实现方式，掌握主从延迟的处理。

---

## 22.1 什么是读写分离

**主库负责写，从库负责读**，把读请求分散到多个从库，提升整体并发能力。

```text
        写请求
客户端 ───────► 主库 Master
   │                │ binlog 复制
   │                ▼
   └── 读请求 ──► 从库 Slave1 / Slave2 ...
```

> 前提：**先搭好主从复制**（见 20 章，读写分离就是主从复制的应用）。

---

## 22.2 为什么能提升性能

| 原因 | 说明 |
|------|------|
| 读多写少 | 互联网读:写 ≈ 8:2 ~ 9:1，读压力分摊到多台 |
| 分摊并发 | 单库连接数有限，多从库横向扩展 |
| 主库专注写 | 主库不被慢查询占用，写更快 |

---

## 22.3 实现方式

| 方式 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **应用层手动** | 代码里区分写库/读库 | 简单可控 | 代码侵入大 |
| **中间件/代理** | ShardingSphere-Proxy、MyCat | 对应用透明 | 多一层运维 |
| **客户端 jar** | ShardingSphere-JDBC | 无额外部署 | 语言绑定 |

### ShardingSphere-JDBC 配置示例

```yaml
spring:
  shardingsphere:
    datasource:
      names: master,slave0
      master:
        url: jdbc:mysql://192.168.1.10:3306/study
      slave0:
        url: jdbc:mysql://192.168.1.11:3306/study
    rules:
      readwrite-splitting:
        data-sources:
          rw:
            write-data-source-name: master
            read-data-source-names: slave0
            load-balancer-name: round_robin
        load-balancers:
          round_robin:
            type: ROUND_ROBIN
```

> 配置后，应用无需改 SQL：`select` 自动走从库，`insert/update/delete` 自动走主库。

---

## 22.4 主从延迟导致的问题（重点）

读写分离最大的坑：**写完主库立刻读从库，可能读不到**（binlog 还没同步完）。

```text
1. 用户下单 → 写主库
2. 立刻查询订单 → 读从库（延迟）→ 查不到！用户以为下单失败
```

### 解决方案

| 方案 | 说明 |
|------|------|
| **强一致读主库** | 写后立即读的场景强制走主库（最常用） |
| **半同步复制** | 至少一个从库确认才返回（降低延迟窗口） |
| **延迟感知路由** | 主从延迟超阈值时自动读主库 |
| **应用层标记** | 写操作后的短时间窗口内读主库 |

```java
// 思路示意：用 ThreadLocal 标记当前请求强制读主库
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);      // 写主库
    // 后续读强制主库
    ReadMasterHolder.forceMaster(); // 标记
    Order saved = orderMapper.selectById(order.getId());
}
```

> **面试常问**：读写分离后一致性问题怎么解决？→ 强一致走主库、半同步、延迟感知、写后读窗口标记。

---

## 22.5 读写分离 vs 分库分表

| 对比 | 读写分离 | 分库分表 |
|------|---------|---------|
| 解决 | 读并发高 | 单表数据量大 / 写并发高 |
| 数据 | 每台都是**全量** | 每台是**部分**数据 |
| 复杂度 | 较低 | 高（路由/分布式事务） |
| 依赖 | 主从复制 | 中间件 |

> **演进顺序**：单库 → 主从复制 → **读写分离** → 缓存 → 分库分表。

---

## 22.6 案例：验证读写分离与延迟

```sql
-- 1. 主库写入
insert into study.student (name, score) values ('读写分离测试', 90);

-- 2. 立即从从库读（可能查不到，取决于延迟）
select * from study.student where name = '读写分离测试';

-- 3. 查看从库延迟
show slave status\G
-- Seconds_Behind_Master: 0 表示已同步

-- 4. 应用侧解决：该场景强制读主库
```

---

## 小结

- 读写分离 = 主库写 + 从库读，前提是主从复制。
- 实现：应用层手动 / 中间件代理 / 客户端 jar（ShardingSphere）。
- 最大的坑是**主从延迟导致写后读不到**，解决靠：强一致读主库、半同步、延迟感知。
- 演进顺序：主从复制 → 读写分离 → 缓存 → 分库分表。
