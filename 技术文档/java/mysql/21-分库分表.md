# 21 - 分库分表

> 目标：理解垂直/水平拆分的区别，掌握分片策略与常见问题。

---

## 21.1 为什么要分库分表

单库单表的瓶颈：

| 瓶颈 | 说明 |
|------|------|
| 数据量大 | 单表千万行以上，索引层次变深，查询变慢 |
| 并发高 | 单实例连接数、IO、CPU 到瓶颈 |
| 磁盘 | 单机存储有限 |

> **经验阈值**：单表 > 1000 万行 或 > 2GB，考虑分表；单库 QPS 到瓶颈，考虑分库。

---

## 21.2 拆分方式

### 垂直拆分

**按业务/字段拆分**：

| 类型 | 说明 | 例子 |
|------|------|------|
| **垂直分库** | 按业务拆到不同库 | 用户库、订单库、商品库 |
| **垂直分表** | 把不常用/大字段拆到另一张表 | 用户表拆「基本信息表」+「详情表」 |

```
垂直分库：db_user | db_order | db_goods
垂直分表：tb_user(id,name,phone) | tb_user_detail(id,bio,avatar)
```

### 水平拆分

**同结构表按行拆分**：

| 类型 | 说明 |
|------|------|
| **水平分库** | 同样结构的数据分散到多个库 |
| **水平分表** | 同样结构的数据分散到多张表（同库或跨库） |

```
水平分表：tb_order_0 | tb_order_1 | tb_order_2 | tb_order_3
按 user_id % 4 路由
```

| 对比 | 垂直拆分 | 水平拆分 |
|------|---------|---------|
| 拆分维度 | 业务 / 字段 | 数据行 |
| 解决 | 表宽、业务耦合 | 单表数据量大 |
| 复杂度 | 较低 | 较高（路由/分布式事务） |

## 21.3 分片策略

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **Range 范围** | 按 id/时间区间分 | 易扩容、范围查询快 | 热点集中（新数据都写最后一片） |
| **Hash 取模** | `id % N` | 分布均匀 | 扩容需重新分布 |
| **一致性 Hash** | 环上定位 | 扩容影响小 | 实现复杂 |
| **雪花算法 ID** | 时间+机器+序列 | 全局唯一、趋势递增 | 需部署发号器 |

```text
Hash 分片：user_id % 4 → tb_order_{0..3}
Range 分片：2026-01~03 → tb_order_202601，2026-04~06 → tb_order_202604
```

> **扩容问题**：`% 4` 扩到 `% 5` 会导致几乎所有数据要迁移 → 用**成倍扩容**（4→8）或**一致性 Hash** 降低迁移量。

## 21.4 中间件方案

| 方案 | 说明 |
|------|------|
| **ShardingSphere-JDBC** | 客户端（jar），代码内配置，无额外部署，性能好 |
| **ShardingSphere-Proxy** | 代理层，独立部署，支持多语言，运维统一 |
| MyCat | 老牌代理中间件 |

```yaml
# ShardingSphere-JDBC 示例（application.yml）
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0: { ... }
      ds1: { ... }
    rules:
      sharding:
        tables:
          tb_order:
            actual-data-nodes: ds$->{0..1}.tb_order_$->{0..1}
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order-inline
            key-generate-strategy:
              column: id
              key-generator-name: snowflake
        sharding-algorithms:
          order-inline:
            type: INLINE
            props:
              algorithm-expression: tb_order_$->{user_id % 2}
```

## 21.5 分库分表带来的问题

| 问题 | 说明 | 解决 |
|------|------|------|
| **分布式事务** | 跨库操作无单一事务 | Seata / 最终一致性 / 本地消息表 |
| **跨库 JOIN** | 无法直接 join | 冗余字段 / 广播表 / 应用层组装 |
| **全局唯一 ID** | 自增 ID 冲突 | **雪花算法** / 号段模式 / Redis |
| **跨库分页** | `limit` 难以聚合 | 应用层归并 / 二次查询 |
| **数据迁移** | 扩容要迁移 | 双写 + 平滑迁移 |
| **运维复杂** | 多库管理 | 中间件统一管理 |

### 雪花算法 Snowflake

```text
64 位：1 符号位 + 41 时间戳(ms) + 10 机器ID + 12 序列号
→ 全局唯一、趋势递增（利于索引）
```

---

## 21.6 何时不该分库分表

> **优先考虑**：索引优化 → 读写分离 → 缓存（Redis）→ 归档历史数据 → **最后才分库分表**。

分库分表是**架构复杂度的大跳跃**，能不分就不分。很多场景用「读写分离 + 缓存 + 索引优化」就能解决。

---

## 小结

- 垂直拆分按业务/字段；水平拆分按数据行。
- 分片策略：Range（易扩容有热点）、Hash（均匀难扩容）、一致性 Hash。
- 中间件：ShardingSphere-JDBC / Proxy。
- 分库分表带来的问题：分布式事务、跨库 JOIN、全局 ID、跨库分页。
- 分库分表是最后手段，优先索引/缓存/读写分离。
