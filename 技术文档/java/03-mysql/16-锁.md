# 16 - 锁

> 目标：掌握全局锁、表级锁、行级锁，理解间隙锁与死锁。**面试重点**。

---

## 16.1 锁的分类

按**粒度**分：

```text
全局锁（锁整个库）
  └─ 表级锁（锁整张表）：表锁、元数据锁 MDL、意向锁
      └─ 行级锁（锁某行，InnoDB 特有）：记录锁、间隙锁、临键锁
```

| 粒度 | 开销 | 并发 | 加锁速度 | 适用 |
|------|------|------|---------|------|
| 表级锁 | 小 | 低 | 快 | MyISAM |
| 行级锁 | 大 | 高 | 慢 | **InnoDB** |

---

## 16.2 全局锁

锁住**整个数据库实例**，只读不写：

```sql
flush tables with read lock;   -- 加全局锁（FTWRL）
-- 此时所有表只能读，不能写
unlock tables;                  -- 释放
```

**用途**：全库逻辑备份。**问题**：业务停写，影响大。

> 更优方案：用 `mysqldump --single-transaction` 在可重复读隔离级别下备份（InnoDB 支持一致性快照，不阻塞写）。

---

## 16.3 表级锁

### 表锁

```sql
lock tables tb_user read;      -- 表共享读锁：自己只读，别人可读不可写
lock tables tb_user write;     -- 表独占写锁：自己可读写，别人阻塞
unlock tables;                 -- 释放
```

### 元数据锁 MDL

- 在**访问表时自动加**（无需手动），保证表结构一致。
- 读操作加 MDL 读锁，写操作加 MDL 写锁。
- **坑**：长事务持有 MDL 读锁时，DDL 会阻塞，后续所有请求排队。

> 面试场景题：「为什么加个字段导致数据库卡死？」→ 长事务持有 MDL 读锁，DDL 等 MDL 写锁，后面的查询又被 DDL 挡住，形成堆积。

### 意向锁

- **表级锁**，表示「表中有行被加了锁」。
- 分为意向共享锁（IS）和意向排他锁（IX）。
- 作用：加表锁时**快速判断表里有没有行锁**，无需逐行检查。

## 16.4 行级锁（InnoDB）

InnoDB 行锁基于**索引**，有三种：

| 类型 | 范围 | 说明 |
|------|------|------|
| **记录锁 Record Lock** | 单条记录 | 锁住一行 |
| **间隙锁 Gap Lock** | 区间（不含记录） | 防止其他事务在间隙插入，避免幻读 |
| **临键锁 Next-Key Lock** | 区间 + 记录 | 记录锁 + 间隙锁的组合，**InnoDB 默认** |

```sql
-- 行锁示例（必须在事务中）
start transaction;
select * from tb_user where id = 1 for update;   -- 锁住 id=1 这行
-- 其他事务 update id=1 会阻塞
commit;
```

### 不同条件的加锁情况（重点）

```sql
-- ① 唯一索引等值命中 → 记录锁
select * from tb_user where id = 1 for update;        -- 只锁 id=1

-- ② 唯一索引等值未命中 → 间隙锁
select * from tb_user where id = 5 for update;        -- 锁 id 附近的间隙

-- ③ 非唯一索引等值 → 临键锁（可能锁多行）
select * from tb_user where age = 20 for update;      -- 间隙 + 记录

-- ④ 范围查询 → 临键锁
select * from tb_user where id > 10 for update;

-- ⑤ 无索引条件 → 锁全表所有行（效果等同表锁）
select * from tb_user where name = '张三' for update;  -- name 无索引
```

> **关键结论**：**没有索引的行锁会退化为锁全表**。这是 `UPDATE`/`SELECT ... FOR UPDATE` 必须走索引的原因（呼应 12.8）。

## 16.5 死锁

两个事务互相等待对方持有的锁：

```text
事务 A：锁行 1 → 请求行 2
事务 B：锁行 2 → 请求行 1
→ 互相等待，死锁
```

```sql
-- 模拟死锁
-- 事务 A
start transaction;
update tb_user set age = 1 where id = 1;
-- 事务 B
start transaction;
update tb_user set age = 1 where id = 2;
-- 事务 A 请求 id=2（被 B 占）
update tb_user set age = 1 where id = 2;
-- 事务 B 请求 id=1（被 A 占）
update tb_user set age = 1 where id = 1;
-- 其中一个报：Deadlock found when trying to get lock
```

**InnoDB 处理死锁**：
- 自动检测死锁，**回滚代价小的事务**。
- 查看死锁日志：

```sql
show engine innodb status;    -- 看 LATEST DETECTED DEADLOCK 段
```

**避免死锁**：
1. 事务中**按固定顺序**访问资源（如都按 id 升序更新）。
2. 事务尽量**短小**，减少锁持有时间。
3. 使用**合适的索引**，避免锁范围过大。
4. 一次锁定所需全部资源（`select ... for update` 提前锁）。

---

## 16.6 案例：验证行锁

```sql
-- 会话 A
start transaction;
select * from tb_user where id = 1 for update;   -- 锁 id=1

-- 会话 B（另开一个连接）
update tb_user set age = 99 where id = 1;         -- 阻塞，等待
update tb_user set age = 99 where id = 2;         -- ✅ 不阻塞（不同行）

-- 会话 A
commit;    -- B 的语句立即执行
```

---

## 小结

- 锁粒度：全局锁 → 表级锁（表锁/MDL/意向锁）→ 行级锁（InnoDB）。
- 全局锁用于全库备份，生产用 `--single-transaction` 替代。
- InnoDB 行锁：记录锁 / 间隙锁 / 临键锁（默认）。
- **无索引条件会让行锁退化为锁全表**。
- 死锁：InnoDB 自动检测并回滚代价小的事务；避免靠固定顺序 + 短事务 + 索引。
