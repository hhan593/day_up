# 09 · 线程池生产实践

> 线程池参数没有标准答案，但有标准的**决策过程**和**监控手段**。本篇讲"参数怎么定、怎么发现它有问题、怎么不重启调它"。
> API 与执行流程见 `../02-java-middle/35-线程池与线程协作.md`；总纲见 `../04-concurrency/README.md#五线程池`。

---

## 一、参数估算：公式只是起点，压测才是终点

```text
CPU 密集型：   threads ≈ 核数 + 1
IO 密集型：    threads ≈ 核数 * (1 + 等待时间/计算时间)
```

**公式的三个局限（实战中必须知道）**：
1. 等待/计算比是拍出来的，请求形态一变就失效。
2. 一个进程里往往有**多个线程池**（Web 容器、@Async、定时、各业务自建），公式只对单个池成立，总量会超载。
3. 公式假设线程是瓶颈，实际瓶颈可能是下游 DB/Redis。

**正确姿势**：公式给初值 → 压测看三指标（队列水位、拒绝次数、下游 RT）→ 调整 → 再压。**能压测永远别背公式**。

## 二、生产级线程池的六个必配项

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        20, 40, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(1000),                      // 有界！
        new ThreadFactoryBuilder()
                .setNameFormat("order-pool-%d")               // ① 必须命名
                .setUncaughtExceptionHandler((t, e) ->
                        log.error("pool thread died, thread={}", t.getName(), e))  // ② 兜底记录
                .build(),
        new OrderRejectedPolicy());                           // ③ 显式拒绝策略
executor.allowCoreThreadTimeOut(true);                        // ④ 低峰回收核心线程（可选）
```

| 必配项 | 不配的后果 |
|--------|-----------|
| ① 线程命名 | jstack 里一排 `pool-1-thread-123`，完全不知道是谁的池——**排查效率差 10 倍** |
| ② 异常处理器 | submit 的任务抛异常被静默吞掉（Future 才拿得到），任务"消失"无感知 |
| ③ 显式有界队列 | `Executors.newFixedThreadPool` 的无界队列 = OOM 倒计时 |
| ④ 显式拒绝策略 | 默认 AbortPolicy 裸抛异常；至少要记录+告警 |

**规约**：**禁用 `Executors` 的快捷工厂方法**（阿里规约条目），统一手动 `ThreadPoolExecutor`。

## 三、拒绝策略的实战选型

| 策略 | 适合 | 风险 |
|------|------|------|
| `AbortPolicy`（默认） | 能感知失败并处理的调用方 | 裸异常可能无人接 |
| `CallerRunsPolicy` | 能容忍调用方变慢的场景（削峰） | **同步阻塞发起线程**：Web 线程被拖住时等效于放大积压 |
| `DiscardPolicy` | 允许丢弃的指标/日志上报 | **静默丢弃**，出问题无感知 |
| 自定义（推荐） | 几乎所有业务 | 要写对 |

生产推荐：**自定义 = 记日志 + 打指标 + 落库/入重试队列 + 告警**：

```java
class OrderRejectedPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        log.error("thread pool rejected, queue={}, active={}, task={}",
                e.getQueue().size(), e.getActiveCount(), r);
        Metrics.counter("pool.rejected", "pool", "order").increment();
        persistAndRetryAsync(r);        // 落库，稍后补偿执行
    }
}
```

> **CallerRunsPolicy 的隐蔽事故**：Web 线程被拉去执行任务 → 该线程不释放 → Tomcat 线程也被占满 → 全服务不可用。它"降速"的特性在入口层是优点，在关键链路是事故。

## 四、监控：不看指标的线程池等于裸奔

```java
// Micrometer 定时上报（配合 Prometheus/Grafana）
Gauge.builder("pool.active", executor, ThreadPoolExecutor::getActiveCount)
     .tag("pool", "order").register(meterRegistry);
Gauge.builder("pool.queue.size", executor, e -> e.getQueue().size())
     .tag("pool", "order").register(meterRegistry);
```

**告警阈值经验**：
- 队列水位 > 80% 持续 1 分钟 → 预警（消费能力跟不上了）；
- 拒绝次数 > 0 → 立即告警（已经在丢任务）；
- 活跃线程长期 = max → 池太小或下游变慢。

## 五、动态调优：不重启改参数

`ThreadPoolExecutor` 的核心参数**本身支持运行时修改**：

```java
executor.setCorePoolSize(30);      // 运行中生效
executor.setMaximumPoolSize(50);
```

实践：
1. 参数收编到**配置中心**（Nacos/Apollo）监听变更 → 回调 setter（`../11-nacos/README.md`）。
2. 大促前在配置中心把池调大，结束调回。
3. 配合监控曲线反向验证：调大后队列水位应下降——不降说明瓶颈在下游，别再加线程。

> **为什么值钱**：线程池不合适导致的故障，以前只能"改配置 → 发版 → 重启"十几分钟；动态调优把止损压到秒级。美团的 DynamicTp、Hp-Sarabande 这类开源方案就是把这个流程产品化。

## 六、@Async 与 CompletableFuture 的两个默认值大坑

### 坑 1：@Async 默认线程池

Spring Boot 2.1+ 的 `@Async` 默认池：**核心 8、最大 `Integer.MAX_VALUE`、无界队列**——突发流量下线程数暴涨 + 队列堆积。**必须自定义**：

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(20); ex.setMaxPoolSize(40);
    ex.setQueueCapacity(1000);
    ex.setThreadNamePrefix("biz-");
    ex.setTaskDecorator(mdcTaskDecorator());   // ⑥ 透传 traceId（见 06 篇）
    ex.setRejectedExecutionHandler(new OrderRejectedPolicy());
    ex.initialize();
    return ex;
}

@Async("bizExecutor")        // 显式指定，别用默认
```

### 坑 2：CompletableFuture 默认用 ForkJoinPool.commonPool

```java
CompletableFuture.supplyAsync(() -> callRpc());    // ❌ 落到 commonPool
```

- commonPool 核心数 = 核数 - 1，且**全 JVM 共享**：你的 IO 任务把并行度占满，连并行流、其他框架全被拖慢。
- **规约**：所有 `supplyAsync` 第二参数**显式传自己的池**。

## 七、优雅关闭

```java
@PreDestroy
public void shutdown() {
    executor.shutdown();                     // 不接新任务，跑完存量
    try {
        if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
            executor.shutdownNow();          // 超时强停，避免卡住停机流程
        }
    } catch (InterruptedException e) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

不关闭的后果：发布时任务半途被杀（对账时发现"半条数据"）。
