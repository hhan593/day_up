# 06 · 日志与问题定位实战

> 出问题时，日志是你唯一的黑匣子。本篇讲：日志怎么打才能 5 分钟定位问题，而不是 5 小时翻海量 INFO。
> 关联：`01-线上故障排查实战手册.md`（排查链路）、`../08-springboot/README.md#十二日志`（配置基础）。

---

## 一、日志级别实战约定（别只会 INFO 和 ERROR）

| 级别 | 什么时候用 | 实战例子 |
|------|-----------|---------|
| ERROR | **需要人处理**的故障 | 调用第三方失败、数据不一致被兜底逻辑拦住 |
| WARN | 自动恢复但值得看的异常 | 重试后成功、降级触发、慢调用（>阈值） |
| INFO | 关键业务节点、状态变更 | 下单成功、支付回调到达、配置变更 |
| DEBUG | 开发排障细节，**线上默认关** | 方法出入参、中间变量 |

**两条铁律**：
1. **ERROR 必须有人消费**：接告警。打了一堆没人看的 ERROR，等于"狼来了"，真故障被淹没。
2. **WARN 是排障金矿**：大多数线上问题的前兆都在 WARN 里（重试、超时、降级）。

## 二、最影响排障效率的五个坏习惯（附正确写法）

### 坏习惯 1：字符串拼接 + 占位符混用

```java
log.debug("user:" + user + " order:" + order);     // ❌ DEBUG 关了也执行拼接
log.debug("user: {} order: {}", user, order);      // ✅ 占位符，关闭时零开销
```

### 坏习惯 2：只打 e.getMessage()，丢掉堆栈

```java
log.error("支付失败: " + e.getMessage());          // ❌ 只有"Connection refused"，不知道哪一行
log.error("支付失败, orderNo={}", no, e);          // ✅ 占位符写完后把异常放最后一个参数
```

> **细节**：`log.error("xx", e)` 会打完整堆栈；`log.error("xx" + e.getMessage())` 只有一行文字。丢堆栈是排障时最想打人的事。

### 坏习惯 3：打敏感信息

手机号、身份证、密码、完整 token 出现在日志里 = 数据合规事故。
```java
log.info("用户 {} 登录成功", maskPhone(user.getPhone()));   // ✅ 脱敏
```

### 坏习惯 4：没有上下文的一行日志

```java
log.error("库存不足");                              // ❌ 哪个商品？哪个订单？谁下的？
log.error("库存不足, goodsId={}, orderId={}, userId={}, remain={}",
          goodsId, orderId, userId, remain);        // ✅
```

**经验公式**：一条关键日志要能回答——谁、对什么对象、做了什么、结果如何。反过来说：**光看这条日志，不用看代码，能不能理解发生了什么？**

### 坏习惯 5：循环里打 INFO

```java
for (Order o : orders) {
    log.info("处理订单 {}", o.getId());   // 10 万订单 = 10 万行日志，磁盘打满还拖慢主流程
}
```
循环内改 DEBUG，或循环外汇总一条。

## 三、MDC traceId：全链路日志的骨架

没有 traceId，跨方法/跨服务的日志就是一盘散沙。

### 1. Filter 注入

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {
    private static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp,
                                    FilterChain chain) throws ServletException, IOException {
        String traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
                .orElse(UUID.randomUUID().toString().replace("-", ""));
        MDC.put(TRACE_ID, traceId);
        resp.setHeader("X-Trace-Id", traceId);      // 响应也带回去，方便用户反馈时提供
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.remove(TRACE_ID);                   // 线程池复用线程，必须清理！
        }
    }
}
```

### 2. logback 输出

```xml
<pattern>%d{HH:mm:ss.SSS} [%thread] %-5level [%X{traceId}] %logger{36} - %msg%n</pattern>
```

### 3. 跨服务透传（Feign 拦截器）

```java
@Component
public class TraceIdInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        template.header("X-Trace-Id", MDC.get("traceId"));   // 下游服务同样注入 MDC
    }
}
```

**生产事故案例级细节**：
- 线程池会**复用线程**：`finally` 里不 `MDC.remove()`，B 请求的日志带着 A 请求的 traceId——查问题查到怀疑人生。
- **`@Async`/自建线程池会丢 MDC**：需要 `TaskDecorator` 包装（复制父线程 MDC），或改用 TransmittableThreadLocal（`../04-concurrency/README.md#九threadlocal`）。

```java
@Bean
public TaskDecorator mdcTaskDecorator() {
    return runnable -> {
        Map<String, String> ctx = MDC.getCopyOfContextMap();   // 提交时快照
        return () -> {
            if (ctx != null) MDC.setContextMap(ctx);
            try { runnable.run(); } finally { MDC.clear(); }
        };
    };
}
```

## 四、该打哪些日志（业务日志规划）

| 位置 | 级别 | 必须包含 |
|------|------|---------|
| 接口入口/出口 | INFO | 入参摘要、耗时、结果码 |
| 外部调用（RPC/HTTP） | WARN/ERROR | 目标、耗时、状态——**超时与重试必打 WARN** |
| 状态流转 | INFO | 单号、旧状态 → 新状态 |
| 降级/兜底 | WARN | 触发原因、兜底值 |
| 定时任务开始/结束 | INFO | 处理量、耗时、失败数 |

**慢调用监控日志**（极其实用，一行代码顶半个 APM）：

```java
long start = System.currentTimeMillis();
Result r = paymentClient.pay(req);
long cost = System.currentTimeMillis() - start;
if (cost > 500) {
    log.warn("slow call, target=payment, cost={}ms, orderNo={}", cost, no);
}
```

## 五、实战案例：一次用日志定位的故障

**告警**：运营反馈"用户反馈支付后订单还是未支付"，无 ERROR。

```text
1. 拿用户的 orderNo → grep 业务日志：
   [2026-09-20 10:01:02.101] INFO  [a1b2c3] OrderPayConsumer - 收到支付回调, orderNo=xxx
   [2026-09-20 10:01:02.305] WARN  [a1b2c3] RedisLock - 获取锁失败, key=lock:order:xxx
   [2026-09-20 10:01:02.306] INFO  [a1b2c3] OrderPayConsumer - 回调处理结束   ← 没处理就结束了？

2. traceId=a1b2c3 全链路搜索 → 发现锁获取失败后 return，没有任何重试
3. 再查 WARN："获取锁失败" 在 10:01:02 出现了 3 次 —— 支付渠道重复回调并发抢锁
4. 结论：回调并发 + 抢锁失败直接丢弃 → 两次都"处理结束"，订单卡在 PAYING
5. 修复：抢锁失败改为短暂自旋重试 + 失败入重试队列（NACK），而不是静默丢弃
```

**方法论**：这条链路里没有一行 ERROR，全靠 **traceId 串联 + WARN 前兆**。这就是"日志规范"投资的回报。

## 六、日志治理红线（团队规约建议）

1. 禁止 `System.out.println` / `e.printStackTrace()`（不走日志框架，无级别无 traceId）。
2. ERROR 必须可行动：要么修，要么告警；打完就忘的 ERROR 降级为 WARN。
3. 循环/高频路径禁止 INFO。
4. 所有日志带 traceId；关键业务日志带业务单号。
5. 异常对象永远作为**最后一个参数**传给 logger。
6. 日志配置必须有滚动切割 + 保留天数（防磁盘，见 `01-线上故障排查实战手册.md` 场景六）。
