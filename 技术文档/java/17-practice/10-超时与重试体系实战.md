# 10 · 超时与重试体系实战

> 分布式系统的稳定性，一半靠超时，一半靠"别乱重试"。本篇讲超时怎么分层配、重试怎么放大故障、两者怎么与幂等咬合。
> 容错理论见 `../09-microservices/README.md#八服务容错熔断限流降级`；幂等见 `05-接口幂等与防重实战.md`。

---

## 一、超时的本质：快速失败是一种自我保护

没有超时的调用 = 把自己的线程命运交给别人。下游卡死 → 你的线程全部挂起 → 线程池满 → 整个服务不可用 → **故障沿调用链向上蔓延（雪崩）**。

超时的目的不是"更快"，是**把故障隔离在可承受的资源范围内**。

---

## 二、超时配比原则：层层收缩，上游 > 下游

```text
用户/网关：   10s
 └─ A 服务：  5s（留给自身处理 5s，其中调用 B、C）
     ├─ B 服务：3s
     │    └─ B 的 DB：2s
     └─ C 服务：2s
```

**铁律：每一层的总超时必须大于其所有下游超时之和 + 自身处理时间**。

反例（真实事故形态）：

```text
A 服务 read-timeout = 2s
A 串行调用 B（timeout 3s）→ A 等 B 的第 2 秒时自己先超时放弃
但 B 并不知道，还在继续跑完 → A 重试 → B 重复执行
```

下游超时 ≥ 上游超时 = **上游永远看不到下游的结果，还制造重复请求**。

### 各层超时清单（都要显式配，默认值不可信）

| 层 | 默认值 | 风险 |
|----|--------|------|
| Feign/RestTemplate read-timeout | Feign 60s / RestTemplate ∞ | 下游卡死时线程挂 60s |
| HikariCP connection-timeout | 30s | DB 不可用时线程排队 30s 才报错 |
| JDBC socketTimeout | **0（无限）** | 慢 SQL 把连接和线程一起拖死 |
| Redis Lettuce command-timeout | 60s | Redis 抖动拖垮全应用 |
| MQ 消费/发送 | 各客户端不同 | broker 无响应时消费者假死 |
| HTTP Server（Tomcat）connection-timeout | 20s | 慢连接占用接入层 |

> **JDBC socketTimeout=0 是最隐蔽的**：连接池的 connection-timeout 只管"拿连接"，拿到连接后 SQL 执行多久没人管——慢 SQL 治理（`08-MySQL生产实战踩坑.md`）+ socketTimeout 兜底两者都要。

## 三、重试：最容易被低估的故障放大器

### 重试什么时候救命，什么时候致命

```text
超时 ≠ 失败：请求可能已经成功，只是响应没回来
盲目重试的代价：
  ① 放大流量：下游 50% 失败时重试 1 次 → 实际请求量 ×1.5，下游更糟
  ② 重复副作用：非幂等接口重试 = 双倍扣款
  ③ 重试风暴：全链路每层都重试 → 3 层各重试 2 次 = 流量 ×8
```

### 生产级重试四原则

1. **只重试"值得重试"的错误**：网络超时、502/503 可重试；400 参数错、业务拒绝**重试一万次也是失败**，直接抛。
2. **重试必须幂等兜底**：没有幂等保护（`05` 篇）就不允许自动重试——宁可失败让人处理，不可重复扣款。
3. **指数退避 + 抖动**：`delay = base * 2^n + random(jitter)`，避免重试请求同步扎堆形成波峰。
4. **预算控制**：限制"重试流量占比"（如 retry budget ≤ 10%），超了就熔断重试。

```java
// Resilience4j：重试 + 熔断 + 超时组合（而不是裸 for 循环）
RetryConfig retry = RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(200))
        .intervalFunction(IntervalFunction.ofExponentialBackoff(200, 2.0))
        .retryOnException(e -> isRetryable(e))     // 只重试可重试异常
        .build();

CircuitBreaker cb = CircuitBreaker.of("payment",
        CircuitBreakerConfig.custom()
                .failureRateThreshold(50)          // 错误率 50% 熔断
                .slidingWindowSize(20)
                .waitDurationInOpenState(Duration.ofSeconds(10))
                .build());

Supplier<Result> s = () -> paymentClient.pay(req);
Result r = Decorators.ofSupplier(s)
        .withRetry(Retry.of("pay", retry))
        .withCircuitBreaker(cb)
        .withFallback(e -> Result.degraded())      // 熔断/耗尽后降级
        .get();
```

## 四、组合拳：超时 + 重试 + 熔断 + 降级的正确咬合

```text
请求 → [超时 3s] → 失败 → [重试 ≤2 次，指数退避，仅可重试错误]
        → 仍失败 → [熔断器记账]
        → 错误率超 50% → 熔断打开 → 后续请求直接降级（10s 后半开试探）
        → 降级动作：返回缓存/默认值/排队提示（见 05 篇幂等保证重试安全）
```

**参数联动细节**：
- 熔断的滑动窗口要 ≥ 重试的影响范围，否则刚重试完就熔断误伤。
- 降级返回的必须是"业务可接受的值"（缓存旧值、排队中状态），**不要在 fallback 里再调一次下游**——那是伪装的重试。

## 五、实战案例：一次"重试风暴"复盘

**背景**：下单服务调库存服务，超时 1s，无重试。某天库存服务 DB 抖动 RT 从 200ms 升到 1.2s。

**事故链**：
1. 库存接口 RT 1.2s > 下单侧 1s 超时 → 全部超时；
2. 同学紧急加上"重试 3 次"救火 → 流量 ×4，库存服务雪上加霜；
3. 下单侧 Feign 线程池被 1.2s 的挂起请求占满 → **下单服务整个不可用**，连不依赖库存的接口也挂了；
4. 恢复后的真正修复：
   - 库存侧：DB 慢 SQL 治理 + 限流（保护自己）；
   - 下单侧：超时收敛 800ms + 重试 1 次（指数退避）+ **熔断**（50% 失败直接降级"稍后重试"）+ 降级期间订单标"待确认库存"异步补偿；
   - 两侧对齐超时配比，杜绝"下游比上游慢"。

**教训**：没有熔断的重试是雪崩加速器；没有超时的重试是定时炸弹。

## 六、检查清单

```text
□ 所有外部调用都有显式超时（connect/read 分开），不依赖默认值
□ JDBC socketTimeout 已设置（不是 0）
□ 下游超时之和 < 上游总超时（画一张超时拓扑图）
□ 重试只针对幂等接口 / 已有幂等兜底（05 篇）
□ 重试带指数退避 + 抖动 + 次数上限（≤2~3 次）
□ 关键链路有熔断 + 降级（降级返回业务可接受值）
□ 可重试异常与不可重试异常已分类
□ 重试/熔断/降级都有指标与告警
```
