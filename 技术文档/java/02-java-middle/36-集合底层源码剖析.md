## 一、全景：本篇视角与重排对照表
用法与接口树见 `05-集合框架.md`，一句话带过。本篇沿一条演进主线看所有实现：**数组（下标定位 O(1)，增删挪动）→ 链表（增删灵活，查找 O(n)）→ 哈希表（数组+链表，期望 O(1)）→ 红黑树（防哈希退化，O(log n) 兜底）→ 并发变体（整表锁 → 分段锁 → 桶级锁+CAS）**。下表按「结构/线程安全/有序/null/复杂度」重排（与 05 按接口分类的视角不同，这是本篇的地图；队列家族见十五节）：
| 类 | 内部结构 | 线程安全 | 有序? | null key/value | 查找/插入 |
|---|---|---|---|---|---|
| ArrayList | 可缩容数组 | 否 | 插入序 | 允许/允许 | O(1) 随机访问 / 尾部 O(1)、中间 O(n) |
| HashMap | 数组+链表+红黑树 | 否 | 无序 | 允许 1 个/允许 | 均摊 O(1)，退化 O(log n) |
| LinkedHashMap | HashMap + 贯穿双向链表 | 否 | 插入或访问序 | 同 HashMap | O(1) |
| TreeMap | 红黑树 | 否 | 按键排序 | 不允许 key | O(log n) |
| Hashtable | 数组+链表，全方法 synchronized | 是（全表锁） | 无序 | 都不允许 | 均摊 O(1) 但锁死 |
| ConcurrentHashMap | 数组+链表+红黑树 + CAS+桶锁 | 是 | 无序 | **都不允许** | 均摊 O(1)，读基本无锁 |
| CopyOnWriteArrayList | 写时复制数组 | 是 | 插入序 | 允许/允许 | 读 O(1) / 写 O(n) |
> 注意：「有序」分三种要答清——插入序（LinkedHashMap）、排序序（TreeMap）、访问序（`accessOrder=true`，LRU 的基础）。

## 二、从数组到哈希表：为什么需要哈希
```java
static final int hash(Object key) {          // OpenJDK HashMap.hash()（源码同构）
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```
数组线性查找 O(n)；哈希表让「位置由 key 算出」：`index = f(hash(key))`。
- **扰动函数**：n 较小时 `(n-1) & hash` 只用低几位（n=16 只用低 4 位），hashCode 高 16 位完全不参与定位；把高 16 位异或进低位使其影响桶选择，显著减少碰撞，代价仅一次移位+异或。`null` 的 hash 规定为 **0** → null key 恒在 **0 号桶**。
> 注意：右移位数以 OpenJDK 源码为准：`HashMap.hash()` 与 `ConcurrentHashMap.spread()` 均为 **`h >>> 16`**，动机即「让高 16 位参与运算」；部分二手资料写 13 是讹传，面试按源码答 16 并讲出理由。
- **容量为什么必须 2 的幂**：n=2^k 时 n−1 二进制全为 1，`(n-1) & hash` 恰好取低 log2(n) 位、与 `hash % n` 等价而位运算远快于除法，且取连续低位分布更均匀。构造参数经 `tableSizeFor()` 向上取整到 2 的幂——`new HashMap<>(17)` 实际容量 32。
- **负载因子 0.75**：源码注释——理想哈希下桶内节点数服从**泊松分布**，0.75 是空间利用率与链长/扩容频率的经典折中：调大省内存但链更长，调小反之。阈值 `capacity × 0.75`，默认 16 → **第 13 个元素触发扩容**。

## 三、HashMap 数据结构：数组 + 链表 + 红黑树（JDK 8）
```
Node[] table（长度恒为 2 的幂，默认 16）
┌────┬────┬────┬─ ... ─┬─────┐
│ 0  │ 1  │ 2  │       │ n-1 │   ← 数组：定址
└────┴─┬──┴─┬──┘       └─────┘
     ┌─┴──┐ ┌───┐        链表：冲突处理（尾插），Node{hash,key,value,next}
     │ a  │→│ A │→ null
     └────┘ └───┘        链长 ≥8 且表长 ≥64 → 树化：TreeNode 另带 parent/left/right/before/after/red，
                         查找 O(n)→O(log n)，节点内存约为链表节点的 2 倍
```
插入方向是必考历史题：**JDK 7 扩容时头插**（元素在新表逆序），两线程并发扩容各自头插、交错写入可使新表链表**首尾相连成环**，之后任何一次 `get` 遍历该桶即**死循环、CPU 100%**（真实生产事故）；**JDK 8 改尾插**保持原链顺序不再成环——但并发 put 丢数据依旧，见第八节。

## 四、HashMap.put 全流程（本篇最重要）
六步：① 扰动 hash；② `table` 为 null 或空 → `resize()` **懒初始化**（无参构造不分配数组，首次 put 建 16 长表、阈值 12）；③ 目标桶为空 → 直接放新 `Node`；④ 桶非空 → 遍历判同：`p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k)))`——**先比 hash、再 `k == key` 短路、最后 equals**，相同则覆盖 value，不同则**尾插**（已是 TreeNode 则树插入）；⑤ 尾插后链长到 8：表长 <64 时**先扩容代替树化**，否则该桶树化；⑥ `if (++size > threshold) resize()`。
**手动推演**（默认容量 16、阈值 12；单字符 String 的 hashCode 即字符值，均 < 2^16 故扰动后不变）：
| # | put | 扰动 hash | 桶 =15&hash | 操作后 | 动作 |
|---|---|---|---|---|---|
| 1,2 | "a","b" | 97, 98 | 1, 2 | [1]:a  [2]:b | 懒初始化 table=16 |
| 3,4 | "A","B" | 65, 66 | **1, 2** | [1]:a→A  [2]:b→B | 与 a/b 同桶尾插（'a'−'A'=32=2^5，低 4 位相同必碰撞） |
| 5,6 | "1","2" | 49, 50 | **1, 2** | [1]:a→A→1  [2]:b→B→2 | 同桶第 3 个 |
| 7–12 | "3"…"8" | 51–56 | 3–8 | 各占一桶 | size=12，`12 > 12` false，不扩容 |
| 13 | "9" | 57 | 9 | size=13 | **13 > 12 → 扩容到 32** |
扩容到 32 后（掩码 31）：a/A/b/B 仍在 1/2，"1"→17、"2"→18、"3"…"9"→19…25——恰好验证第六节高低位拆链；全程无人均链长达 8，**无树化**。

## 五、树化的三个魔法数字（必考）
| 常量 | 值 | 语义 |
|---|---|---|
| `TREEIFY_THRESHOLD` | **8** | 链长达到 8（且表长 ≥64）→ 树化 |
| `UNTREEIFY_THRESHOLD` | **6** | 扩容拆分时子树节点 ≤6 → 退回链表 |
| `MIN_TREEIFY_CAPACITY` | **64** | 表长不足 64 时优先扩容稀释碰撞，**不树化** |
- **为什么是 8**：源码注释的泊松分布论证——理想哈希下链长期望约 **0.5**，链长到 **8 的概率约千万分之一**；真到 8 说明哈希分布极差或被恶意构造碰撞（hash-flooding DoS），树化是**防退化兜底而非常规优化**。
- **8 与 6 之间为什么留空档**：退化只发生在扩容拆链时，若临界同值，阈值附近的桶会「树化↔退化」反复抖动，6 留缓冲带避免震荡。
- **为什么不默认树化**：TreeNode 内存约两倍、维护复杂，且 key 必须可比较——`Comparable` 优先，否则 `tieBreakOrder` 按**类名再 `System.identityHashCode`** 兜底（所以 HashMap 不强制 key 实现 Comparable）。一句话：**常态 O(1) 走链表，异常哈希才升级 O(log n)**。

## 六、resize 扩容全流程：高低位拆链
新容量 = `oldCap << 1`（**翻倍**；上限 `1<<30`，超过则阈值置 `Integer.MAX_VALUE` 不再扩——`sldThr` 等极端细节略），新阈值 = 新容量 × 0.75。**JDK 8 经典优化——不重算 hash**：容量翻倍使掩码多一位，新位置只取决于 hash 在 oldCap 那一位的值：`(e.hash & oldCap) == 0` → **留原索引**，否则 → **原索引 + oldCap**。
```
oldCap=16，旧桶[1]: a(97) → A(65) → 1(49)   hash & 16:  0     0     16
  lo = a → A（留新表 [1]）    hi = 1（挪新表 [1+16]=[17]）（若 hi 为空，lo 整链直接挂原槽，零搬迁；树桶拆分时子树 ≤6 退化回链表）
```
为什么必须按 load factor 及时扩容：`(n-1)&hash` 只取低位，元素越多链越长，**不扩容查找就退化**；这也解释了「表长 <64 优先扩容『摊薄』、≥64 才树化『加固』」的顺序设计。

## 七、key 的 equals/hashCode 契约
HashMap **定位桶用 hashCode（扰动后取低位），桶内判同用 equals（`==` 短路在前）**。契约破坏的两个方向：
| 错误 | 后果 |
|---|---|
| 只重写 equals | 两个「相等」对象 hash 不同 → 落不同桶：**存重复键、get 不到** |
| 只重写 hashCode | 同桶但 Object.equals 比引用 → 同样**重复键、覆盖失效** |
```java
class BadKey { int id; BadKey(int id){ this.id = id; }                    // 故意漏掉 hashCode
    @Override public boolean equals(Object o){ return o instanceof BadKey b && b.id == id; } }
Map<BadKey,String> m = new HashMap<>();
m.put(new BadKey(1),"x"); m.put(new BadKey(1),"y");                       // 存进"重复"键
System.out.println(m.get(new BadKey(1)));                                 // null：找不到

List<Integer> k = new ArrayList<>(List.of(1));                            // 可变 key："丢失元素"bug
Map<List<Integer>,String> m2 = new HashMap<>();
m2.put(k,"v"); k.add(2);                                                  // 入表后 hashCode 漂移
m2.get(k); m2.remove(k);   // null / false —— size() 仍 1：条目卡在旧桶被 table 强引用，GC 收不了
```
> 注意：**String/Integer 适合做 key** 正因为**不可变 + hashCode 算一次缓存**（`String.hash` 字段、Integer 值即 hash），入表后定位永不漂移；可变对象做 key 再改字段等于制造孤儿条目。契约细节见 `33-字符串与常用API.md`。**null key** 恒在 0 号桶、只允许 1 个（再 put 覆盖）。

## 八、HashMap 非线程安全的表现与四种解法
表现：① 并发 put 同桶 → 后者覆盖前者（**丢数据且不报错**）；② JDK 7 头插并发扩容 → **成环死循环**；③ `++size` 非原子 → size 不准；④ 扩容中读表 → 读到中间态。
| 解法 | 锁粒度 | null | 迭代 | 评价 |
|---|---|---|---|---|
| `Collections.synchronizedMap` | 单把互斥锁包全部方法 | 允许 | **必须手动 `synchronized(包装对象)` 包住整个迭代** | 无并发收益 |
| `Hashtable`（遗留，勿新用） | 方法级 intrinsic lock | 都禁止 | `Enumeration` 或手动同步 | JDK 1.0 类，`contains`/`containsKey`/`containsValue` 历史包袱 |
| `ConcurrentHashMap` | CAS + 单桶头节点锁 | **都禁止**（原因见下节） | 弱一致迭代器，不抛 CME | 首选 |
| 自实现分段锁 | 按 key 分片加锁 | 视实现 | 视实现 | CHM 就是官方的"分片"，不必重造 |
`synchronizedMap` 迭代仍抛 CME 的原因：同步只保护**单个方法调用**，迭代器不持锁，别的线程改 `modCount` 照样被 fail-fast 抓到；整段迭代加锁又等于回到全表锁。

## 九、ConcurrentHashMap（JDK 8+）：结构与算法
**结构**：`Node[] table` + 链表/红黑树；写路径**空桶 CAS、非空桶 `synchronized` 只锁头节点**；`Node.val` 为 volatile 使读基本无锁。
> 注意：**JDK 8 起 `Segment` 已整体废弃移除**——面试先报版本再答结构。
| | JDK 7 | JDK 8+ |
|---|---|---|
| 锁单位 | `Segment[]`（默认 16 段，每段 `extends ReentrantLock`） | 单条桶的头节点 |
| 空桶写入 | 仍需锁段 | **CAS 无锁** |
| 结构 / 并发度 | 数组+链表 / 固定 16 段 | 数组+链表+红黑树 / 按桶粒度 |
**为什么「空桶 CAS、非空锁头」**：空桶写入竞争只有一个引用槽，CAS 一次搞定；链/树插入涉及遍历、拆分、可能树化等多步修改，CAS 无法原子化，而锁头节点竞争面已极小（CAS/synchronized 原理见 `34-并发底层原理JMM与锁.md`，此处不重复展开）。
**size 计数**：`baseCount` + `CounterCell[]` 分散计数（CAS 争 baseCount，失败退化到随机 cell 累加，与 `LongAdder` 同一套思路，见 34 篇）；求和瞬间仍在变，**是近似快照**，推荐 `mappingCount()`（long 防溢出）。
**`ForwardingNode` 与协助扩容**：扩容中被搬空的旧桶放 `ForwardingNode`（hash = `MOVED` = −1）作路标，到达的线程经 `helpTransfer()` 按 CAS 领取 `transferIndex`（步长 `TRANSFER_STRIDE=32` 个桶）分段迁移，读线程也经路标转发到 `nextTable`——**扩容是集体协作而非单人阻塞**，这是 CHM 扩展性核心。
```
oldTable[i] → ForwardingNode(hash = MOVED = -1) ──指向── nextTable（迁移中…）：后来线程领取 transferIndex 段帮忙搬
```
`initTable` 占位的 `ReservationNode`、树桶 `TreeBin`（自带读写状态锁）各一句话：均为锁粒度优化的内部角色，深挖少见。
**key 与 value 都不允许 null（必考标准答案）**：HashMap 单线程下 `get` 返回 null 可用 `containsKey` 复查消歧；**并发下「get 判 null」与「containsKey 复查」两步不原子**——复查瞬间键可能已被删/改，任何答案都可能错。为消灭二义性，CHM 直接**禁止 null key 与 null value**（put 即抛 NPE），使 `get==null` 唯一表示「不存在」；`Hashtable` 同理禁止。
**原子复合操作**：`computeIfAbsent / computeIfPresent / merge / compute / putIfAbsent` 在**桶锁内原子执行**，check-then-act 无需外加锁：
```java
static final Map<String,Object> CACHE = new ConcurrentHashMap<>();
static Object get(String key) { return CACHE.computeIfAbsent(key, q -> loadFromDb(q)); }
    // 同 key 并发时 mappingFunction 只执行一次，其余线程等本桶锁拿结果 → 本地缓存+击穿防护
CACHE.merge("pv", 1, Integer::sum);   // 并发安全计数
```
> 注意：不要在 `mappingFunction` 里递归操作同一 map，CHM 检测到抛 `IllegalStateException("Recursive update")`；函数里做长 IO 会把桶锁变热点。
**弱一致性迭代器**：不抛 CME、不保证读到最新写入、`size()` 近似——并发遍历语义是「最终一致」。

## 十、ArrayList 与 CopyOnWriteArrayList
**ArrayList**：无参构造只指向共享空数组 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA`，**首次 add 才分配 10**（`DEFAULT_CAPACITY`，懒初始化）；扩容 `newCap = oldCap + (oldCap >> 1)` 即 **1.5 倍** + `Arrays.copyOf` 全量拷贝，已知规模用带参构造/`ensureCapacity()` 预分配。`subList()` 返回**视图**（`ArrayList.SubList`）：对子列表的结构性修改**反映到原列表**，但先改原列表结构再用子列表 → 视图 fail-fast 抛 CME。
| 构造 | 长度 | null 元素 | 改元素 | 增删元素 | 本质 |
|---|---|---|---|---|---|
| `Arrays.asList(a)` | 定长 | 允许 | 可（写回原数组） | 抛 `UnsupportedOperationException` | 原数组的**视图** |
| `List.of(a,b)`（**JDK 9**） | 固定 | **禁止** | 不可 | 不可 | 真·不可变集合（要可变列表就 `new ArrayList<>(...)` 包一层拷贝） |
| `Collectors.toList()` | — | — | 不保证可改 | 不保证 | 当前实现给 ArrayList 但**契约不保证**；确定语义用 `toUnmodifiableList()`（JDK 10）或 `Stream.toList()`（**JDK 16**，不可变） |
> 注意：「三个 List 的区别」是全 Java 面试第一坑——`Arrays.asList` 定长视图但元素可改；`List.of` 彻底不可变且禁 null；`subList` 是视图不是拷贝。
**CopyOnWriteArrayList**：写操作（add/set/remove）`ReentrantLock` 加锁 → 复制整份新数组改完后 **volatile 发布替换**；读完全无锁、迭代器持数组快照。适合**读极多写极少**（监听器表、黑白名单）；大列表每次写 O(n) 拷贝 + 峰值双份内存，高频写是事故源。

## 十一、LinkedList
双向链表：`Node { E item; Node prev, next; }` + `first/last` 指针，同时实现 `List` 与 `Deque`（`addFirst/addLast/pollFirst/pollLast/peekFirst` 两端 O(1)；`get(i)` 从较近端向中间走 O(n/2)）。实际性能常**不如 ArrayList**：每元素背两个指针引用加对象头（24+ 字节开销）、节点散铺堆上**缓存极不友好**（遍历即指针追逐）。结论：几乎不该当"列表"用，主要价值是**双端队列**——即便如此官方 Javadoc 也指出 `ArrayDeque` 做栈/队列都快于它。

## 十二、LinkedHashMap 与 LRU（30 行不到）
HashMap 主结构之外用 **before/after 双向链表贯穿所有节点**（插入序）；`accessOrder=true` 时每次 `get` 把节点移到链尾（访问序），配合 `afterNodeInsertion` 回调的 **`removeEldestEntry` 钩子**：
```java
class LruCache<K,V> extends LinkedHashMap<K,V> {
    private final int max;
    LruCache(int max) { super(16, 0.75f, true); this.max = max; }     // accessOrder=true
    @Override protected boolean removeEldestEntry(Map.Entry<K,V> eldest) { return size() > max; }
}   // 超容量即自动淘汰链头（最久未访问）——十行 LRU，与 23 篇 Redis 的 LRU 淘汰同思路
```
三兄弟对比：`HashMap` 最快无序；`LinkedHashMap` 保序略费内存、可 LRU；`TreeMap` 排序 O(log n)。**`IdentityHashMap`**：数组+开放寻址，key 用 `==` 而非 equals，用于按对象身份记状态（序列化框架跟踪引用）。**`WeakHashMap`**：key 为弱引用，key 无强引用时条目自动回收——按实例建缓存不怕泄漏；value 反向强引用 key 会让弱引用失效。

## 十三、TreeMap / TreeSet 与比较器、TimSort
红黑树（CLRS 标准结构）保证 `get/put/remove` **O(log n)**、按键序遍历；**不允许 null key**——定位必须比较，比较天然拒绝 null（理论上自定义 `Comparator` 可绕开部分限制，实践中保守别用）；`TreeSet` 即 TreeMap 的 key 壳，去重依据是**比较结果为 0** 而非 equals。自然序（key 实现 `Comparable`）vs 定制序（构造传 `Comparator`）；链式写法 `Comparator.comparing(U::getName).thenComparing(U::getAge)`。
- **排序算法（必背区别）**：`Collections.sort`/`List.sort`/`Arrays.sort(Object[])` 自 **JDK 7 起用 TimSort**（归并+插入混合、**稳定**、利用真实数据中的有序段）；`Arrays.sort(int[]/long[]/double[])` 基本类型用**双轴快排**（不稳定，基本类型无稳定性需求）。
- `IllegalArgumentException: Comparison method violates its general contract!`：TimSort 运行时校验比较器**传递性**（a≤b∧b≤c ⇒ a≤c），减法比较器整型溢出、带外部状态的比较器等都会触发——真实高频线上事故，根因几乎都在比较器（减法溢出坑见 `33-字符串与常用API.md`）。

## 十四、fail-fast 与 fail-safe
`modCount` 记录结构性修改次数；迭代器创建时快照 `expectedModCount`，**每次 `next()`/`remove()` 前比对，不等即抛 `ConcurrentModificationException`**。
> 注意（最多人答错）：CME 不是"一进并发就抛"，**检查时机是迭代器的下一次游标移动**；单线程 for-each 中直接 `list.remove(x)` 同样触发；且官方明说这是 **best-effort 检测**，不能作为并发正确性机制。
```java
for (String s : list) if (s.equals("b")) list.remove(s);   // ❌ CME：for-each 脱糖为迭代器，list.remove
                                                           //    改了 modCount，迭代器不知情
for (Iterator<String> it = list.iterator(); it.hasNext(); )
    if (it.next().equals("b")) it.remove();                // ✅ iterator.remove 同步 expectedModCount
list.removeIf("b"::equals);                                // ✅ 更短：内部标记+一次压缩，免逐元素挪动
```
fail-safe（弱一致）容器为何不抛：`CopyOnWriteArrayList` 迭代的是**快照数组**，与后续修改无关；CHM 遍历当前 table 但从不校验 modCount——代价是可能读到旧值。

## 十五、队列家族底层
- **ArrayDeque**：循环数组 + head/tail 双指针，两端 O(1)，满时容量翻倍；**不允许 null**——`poll()` 返回 null 无法与"队列空"区分（与 CHM 禁 null 同理，官方选择语义一致）。做栈（push/pop）和队列都**快于 `Stack`（包装 Vector，全方法锁）与 LinkedList**，官方推荐。
- **PriorityQueue**：数组隐式**二叉最小堆**（i 的子节点 `2i+1/2i+2`，offer 上浮、poll 换顶下沉，均 O(log n)），默认自然序可传 Comparator；`peek` 恒为堆顶最小，**迭代器按数组存储序、不保证有序**（高频陷阱）；默认容量 11、扩容按档位翻倍或 1.5 倍（OpenJDK 实现）。`PriorityBlockingQueue`：同款堆 + 单锁 + 条件等待，阻塞世界的对应物。
| 阻塞队列 | 结构 | 锁 | 容量 | 特性 |
|---|---|---|---|---|
| ArrayBlockingQueue | 循环数组 | **一把锁 + notEmpty/notFull 两个 Condition** | 必须构造指定 | 内存可预算（线程池有界队列首选） |
| LinkedBlockingQueue | 链表 | **takeLock/putLock 两把锁**读写分离 | 默认 `Integer.MAX_VALUE` | 吞吐高；"默认无界"= OOM 隐患，务必显式给容量 |
| SynchronousQueue | 不存储元素 | 直接交接 | 0 | 每个 take 必等对应 put；`newCachedThreadPool` 用它 |
| DelayQueue | 按到期时间的堆 | 单锁 + Leader-Follow | 无界 | 到期才 poll 得出；定时任务组件基础 |
| LinkedTransferQueue | 链表 | CAS+锁混合 | 无界 | LBQ 超集，多 `transfer()` 等强交接语义 |

## 十六、集合与 Stream 的性能陷阱
- **并行流看可分裂性**：`ArrayList`/数组/`IntStream.range`/`HashSet` 的 spliterator 能廉价对半拆；`LinkedList` 找中点必须遍历（每次拆分 O(n)）、`Stream.iterate`（JDK 9 前）不可拆——对它们 `parallelStream` 常比串行还慢。
- **`Collectors.toList()` 不保证返回类型、可变性**（当前给 ArrayList 但契约没写）：不可变用 `Stream.toList()`（JDK 16）或 `Collectors.toUnmodifiableList()`（JDK 10），要可变可序列化用 `Collectors.toCollection(ArrayList::new)`；批量删除用 `removeIf()`，避免手动循环 `remove(i)` 的 O(n²) 挪动（原理见十四节）。

## 十七、生产选型速查表
| 场景 | 选什么 | 理由 |
|---|---|---|
| 单线程/方法内键值 | `HashMap` | 最快，允许 null |
| 并发读写键值 | `ConcurrentHashMap` | 桶锁+CAS，读近乎无锁 |
| 需要插入序/访问序 | `LinkedHashMap` | 双向链表贯穿，顺带 LRU |
| 需要排序、范围查询 | `TreeMap` | O(log n) + `subMap`/`ceilingKey` |
| 本地 LRU 缓存 | `LinkedHashMap(accessOrder)` 覆写 `removeEldestEntry` | 十行可用；量大上 Caffeine |
| 去重 | `HashSet`（内部包 HashMap，value 共享哑元） | O(1) 判重 |
| 常规列表 / 读多写少列表 | `ArrayList`（预分配） / `CopyOnWriteArrayList` | 缓存友好 / 无锁读快照迭代 |
| 栈 / 队列 | `ArrayDeque` | 循环数组两端 O(1)，快于 Stack/LinkedList |
| 优先级任务 | `PriorityQueue` / `PriorityBlockingQueue` | 二叉堆 |
| 生产者-消费者缓冲 | `LinkedBlockingQueue`（**显式给容量**） | 读写两锁分离、吞吐高 |

## 十八、高频面试题速答
> **Q：HashMap 底层结构？** A：JDK 8：数组+链表+红黑树；`(n-1) & (h ^ (h>>>16))` 定桶，冲突挂链，链长 ≥8 且表长 ≥64 树化。
> **Q：put 全流程？** A：扰动 hash → 懒初始化 → 空桶直放 → 判同（hash→`==` 短路→equals）覆盖或尾插 → 够条件树化 → `++size > threshold` 则 resize。
> **Q：容量为什么 2 的幂？** A：`(n-1)&hash` 与取模等价且更快、低位均匀；扩容的高低位拆链也依赖它。
> **Q：树化阈值为什么是 8？** A：源码注释泊松分布——理想哈希链长到 8 概率约千万分之一，到 8 即分布被破坏或遭恶意碰撞；树化是防退化兜底（O(n)→O(log n)），链表常态更省内存。
> **Q：1.7 vs 1.8 HashMap？** A：1.7 构造即分配数组、扰动多轮移位、**头插**（并发扩容成环死循环）；1.8 懒初始化、一次 `>>>16`、**尾插**（不成环但仍不安全）、新增树化、扩容高低位拆链免重算 hash。
> **Q：ConcurrentHashMap 怎么保证线程安全？** A：JDK 8 起无 Segment：空桶 CAS、非空桶 synchronized 锁头节点、val volatile 读无锁、baseCount+CounterCell 分散计数、ForwardingNode 多线程协助扩容；**key/value 禁 null** 因为 `get==null` 的二义性在并发下无法用 containsKey 复查消除。
> **Q：ArrayList 扩容？** A：首次 add 分配 10；不足时 **1.5 倍**（`old + (old>>1)`）+ `Arrays.copyOf` 全量拷贝。
> **Q：CME 何时抛？** A：迭代器 `next()/remove()` 时比对 modCount 与 expectedModCount，不等才抛（延迟检查、best-effort）；正解 `iterator.remove()` 或 `removeIf`。
