# 04 · 缓存一致性实战与踩坑

> 缓存与 DB 双写没有完美方案，只有**概率上最优**的方案 + 兜底。本篇用时序推演讲清每种方案为什么行/不行。
> 总纲见 `../redis/README.md#五缓存与数据库一致性`；穿透/击穿/雪崩见该文第四节。

---

## 一、四种写法时序推演（谁为什么不行）

设：线程 A 写，线程 B 读。

### ① 先更新缓存，再更新 DB ❌

```text
A: 更新缓存=新值 → (此时 B 读到新值) → A 更新 DB 失败/宕机
结果：缓存是新的，DB 是旧的，且无人修正 → 长期脏
```

淘汰：写 DB 都可能失败，缓存先行必然引入"缓存超前"。

### ② 先删除缓存，再更新 DB ❌（看似直觉，实际最差）

```text
A: 删缓存 → [还没更新 DB]
B: 读缓存 miss → 读 DB（旧值 100）→ 回填缓存=100
A: 更新 DB = 200
结果：DB=200，缓存=100，**脏数据会活到 TTL 过期**
```

问题在于"删缓存"与"更新 DB"之间的窗口，读请求会把**旧值回填**。窗口越大（DB 写越慢）越容易发生。

### ③ 先更新 DB，再删除缓存 ✅（Cache Aside，默认选择）

```text
不一致窗口分析：
B: 读缓存 miss → 读 DB（旧值 100）
A: 更新 DB = 200，删缓存
B: 回填缓存 = 100   ← 只有"读 DB 在 A 更新前、回填在 A 删除后"这个极小窗口才脏
```

发生条件苛刻（读 DB 到回填的间隔，要恰好横跨 A 的"更新+删除"全过程，且回填比 A 的两步都慢），概率极低；且缓存有 TTL 兜底。**这就是业界默认方案的原因：不是绝对一致，是脏窗口概率最小 + 有兜底**。

### ④ 更新 DB + 更新缓存（双写）❌

两个写操作并发（A 先 B 后写缓存顺序颠倒）必然出现旧值覆盖新值；还要多付一次写缓存成本。除非消费前值计算昂贵（如复杂聚合），否则不用。

## 二、延迟双删：修正方案②，但有边界

```java
// 用于"先删缓存再更新 DB"的补救
public void update(User u) {
    redis.delete(key);
    userMapper.update(u);
    // 延迟再删一次，清掉并发期间被回填的旧值
    scheduler.schedule(() -> redis.delete(key), 500, MILLISECONDS);
}
```

**三个细节决定它靠不靠谱**：

1. **延迟多久？** 应 ≥ "一次读 DB + 回填"的耗时。拍脑袋 500ms 在慢查询场景下完全不够——**延迟时间不可靠是这个方案的固有缺陷**。
2. 延迟删除失败怎么办？（第二次删挂了照样脏）→ 需要重试队列。
3. **结论**：能用方案③就不要绕去方案②+双删。双删主要出现在历史代码与"必须先删"的场景。

## 三、方案③的三个实战补丁

### 补丁 1：删除缓存失败 → 重试

```java
public void update(User u) {
    userMapper.update(u);
    try {
        redis.delete(key);
    } catch (Exception e) {
        // 本地重试仍失败 → 丢进 MQ 异步重试 / 记录到失效表定时扫
        mqSender.send(CACHE_EVICT_TOPIC, key);
    }
}
```

### 补丁 2：读从库的主从延迟问题

写走主库、删缓存后，读请求从**从库**读到旧值回填缓存。解决：
- 删缓存延迟到"从库同步完成之后"（不可控）；
- 或删两次（提交后立即删 + 延迟再删）；
- 或对强一致读走主库（`../mysql/22-读写分离.md#22-4`）。

### 补丁 3：强一致场景干脆加锁串行化

对一致性要求接近强一致的热点数据（如库存），放弃"旁路缓存"，改用：
- 读写都走 DB（乐观锁），缓存只放"几乎不变"的数据；
- 或读写都用分布式锁串行化（性能代价大，见 `../redis/README.md#六分布式锁`）。

**认清定位**：Cache Aside 给的是"最终一致（秒级）"，要更强一致就别用普通缓存方案。

## 四、订阅 binlog 的方案（Canal）：什么时候值得上

```text
DB 变更 → Canal 伪装从库订阅 binlog → 投递 MQ → 消费者删除/更新缓存
```

优点：
- 应用代码零侵入（写代码的人根本不用管缓存失效）。
- 删除操作有 MQ 重试，可靠性高。
- 天然规避"应用更新 DB 后进程挂了没删缓存"。

代价与坑：
- **多一整条链路要运维**（Canal Server + MQ + 消费者）。
- binlog 的顺序与业务顺序：同一行按 binlog 顺序删没问题，但**要按主键分区保证单行有序**，乱序会删了新的又回填旧的。
- 消费端还是要幂等（见 `05-接口幂等与防重实战.md`）。

**适用判断**：缓存数据多、失效点分散、团队已经运维 MQ → 值得；就几个热点接口 → 方案③足够。

## 五、大 key 与热 key（另一类一致性无关但必考的实战坑）

### 大 key

- 危害：单命令阻塞（删 10MB 的 key 卡住其他请求）、迁移/备份变慢、内存倾斜。
- 排查：

```bash
redis-cli --bigkeys                # 线上采样（用从库执行）
redis-cli -i 0.1 --scan | xargs redis-cli memory usage   # 精确但慢
```

- 处理：大 Hash 按 field 拆分（`user:1001:cart:0..9`）；大 List/Set 分页存储；删除大 key 用 `UNLINK`（异步）而非 `DEL`。

### 热 key

- 危害：单分片 CPU 打满（见 `02-高并发库存与秒杀实战.md` 坑 3）。
- 处理：**本地缓存挡一层**（Caffeine + 短 TTL，容忍秒级旧值）、key 加随机后缀多副本、读写分离多从库。

## 六、选型决策表

| 场景 | 方案 |
|------|------|
| 一般业务读写（容忍秒级不一致） | **方案③：先更新 DB，再删缓存**（+删除重试） |
| 写后立刻读同一条数据 | 读主库 / 读写锁串行化 |
| 缓存多、失效点分散、有 MQ | Canal + binlog 订阅 |
| 历史代码必须"先删后更" | 延迟双删（清楚它的局限） |
| 库存/秒杀类计数 | 不走普通缓存一致性，Redis 原子扣减 + DB 兜底（`02` 篇） |
