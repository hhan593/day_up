# 02 · 高并发库存与秒杀实战

> 秒杀是并发问题的集大成者：超卖、热点、限流、幂等、最终一致全在里面。
> 理论见 `../concurrency/README.md`、`../redis/README.md`；幂等配合见 `05-接口幂等与防重实战.md`。

---

## 一、先把超卖复现出来

```java
// ❌ 经典 check-then-act，10 个线程扣 1 件库存，能卖出 3 件
public boolean deduct(Long goodsId) {
    Stock stock = stockMapper.selectById(goodsId);   // 读到 stock=1
    if (stock.getCount() > 0) {
        stock.setCount(stock.getCount() - 1);        // 三个线程都算出 0
        stockMapper.updateById(stock);               // 三次都覆盖写入 → 卖 3 件
        return true;
    }
    return false;
}
```

本质：**读-改-写不是原子操作**。所有防超卖方案，本质都是把这三个动作变成原子。

---

## 二、六种防超卖方案对比

| 方案 | 原子性来源 | 性能 | 适用 | 坑 |
|------|-----------|------|------|-----|
| ① `synchronized` | JVM 锁 | 差（单机锁） | 单机低并发 | 集群下失效 |
| ② DB 乐观锁（条件更新） | 行锁 + WHERE | 中 | **中小并发首选** | 热点行更新冲突 |
| ③ DB 悲观锁 `for update` | 行锁 | 中低 | 强一致小场景 | 锁等待、死锁 |
| ④ Redis Lua 预扣 | Redis 单线程 | **高** | 高并发秒杀 | 扣了不买需回补 |
| ⑤ Redis + MQ 异步 | Redis 预扣 + 异步落库 | **最高** | 大促 | 一致性靠对账 |
| ⑥ 队列串行化 | 单消费者 | 中 | 简单削峰 | 吞吐受限于消费者 |

### ② DB 乐观锁——中小并发的默认答案（最容易被低估）

```sql
-- 一条 SQL 完成判断+扣减，数据库行锁保证原子，绝不可能超卖
update tb_stock set count = count - 1
where goods_id = 1001 and count > 0;
-- 影响行数 = 1 → 扣成功；= 0 → 已售罄
```

```java
public boolean deduct(Long goodsId) {
    return stockMapper.deduct(goodsId) > 0;
}
```

> **为什么不是所有场景都用它**：热点行（所有请求挤在同一行）在几千 QPS 以上时行锁竞争严重。瓶颈不在正确性，在吞吐——所以才需要 Redis 预扣。

## 三、生产级方案：Redis 预扣 + MQ 异步落库

### 架构

```text
请求 → 限流 → 查库存缓存(读) → Redis Lua 原子预扣 ─成功→ 发 MQ → 消费者 DB 落单
                                  │失败
                                  └→ 直接返回售罄
```

### Lua 脚本（判断 + 扣减原子执行）

```lua
-- KEYS[1]=库存key  ARGV[1]=购买数量  ARGV[2]=用户ID（去重）
-- 1. 防重复下单
if redis.call('sismember', KEYS[2], ARGV[2]) == 1 then
    return -1
end
-- 2. 库存判断+扣减（单线程内原子）
local stock = tonumber(redis.call('get', KEYS[1]) or '0')
if stock < tonumber(ARGV[1]) then
    return 0
end
redis.call('decrby', KEYS[1], ARGV[1])
redis.call('sadd', KEYS[2], ARGV[2])
return 1
```

```java
public SeckillResult seckill(Long goodsId, Long userId) {
    Long r = redisTemplate.execute(seckillScript,
            List.of("stock:" + goodsId, "buyer:" + goodsId),
            "1", String.valueOf(userId));
    if (r == null || r == 0) return SeckillResult.SOLD_OUT;
    if (r == -1) return SeckillResult.DUPLICATE;
    // 预扣成功 → 发消息异步落库（削峰）
    mqSender.send(ORDER_TOPIC, new OrderMsg(goodsId, userId));
    return SeckillResult.QUEUED;   // 前端轮询/推送结果
}
```

### 消费端落库（幂等 + 乐观锁兜底）

```java
@KafkaListener(topics = ORDER_TOPIC)
public void onOrder(OrderMsg msg) {
    // 1. 幂等：唯一索引兜底（见 05 篇）
    try {
        orderMapper.insert(...);                          // 订单号唯一索引
    } catch (DuplicateKeyException e) {
        log.warn("重复消息，忽略: {}", msg.getOrderId());
        return;
    }
    // 2. DB 层乐观锁二次兜底（Redis 与 DB 万一不一致）
    stockMapper.deduct(msg.getGoodsId());
}
```

## 四、这个方案的坑（都是真实事故点）

### 坑 1：Redis 扣了，MQ 丢了 → 少卖

- 现象：Redis 库存已扣、用户显示排队中，但订单永远没生成。
- 防御：发 MQ 用**事务消息或本地消息表**（`../mq/README.md#四可靠投递`）；再兜一层**定时对账**——扫 Redis 已扣集合与订单表比对，缺单补发。

### 坑 2：用户超时未支付 → 库存要回补

- 预扣成功 ≠ 最终购买。15 分钟未支付要回滚库存。
- 方案：延迟消息（RocketMQ 延迟级别 / RabbitMQ 死信，见 `../mq/README.md#七延迟死信`）触发关单 + `incrby` 回补 + 移除去重集合。
- **细节**：回补的 `srem` 和 `incrby` 要放同一个 Lua 里原子执行，否则中途宕机会出现"能重复购买但不占库存"。

### 坑 3：热点 key 把 Redis 单分片打满

- Cluster 模式下一个 key 只落一个分片，10w QPS 挤一个节点。
- 方案：**库存分段**——把 10000 件拆成 10 个 key（`stock:1001:0..9`），请求随机落段；某段售罄后合并到其他段。

### 坑 4：库存预热没做 / 缓存击穿

- 活动开始瞬间大量请求穿透到 DB。**开始前把库存 set 进 Redis**；热点 key 永不过期（活动生命周期管理）。

### 坑 5：限流缺位

- 预扣再快也扛不住 100w QPS。**入口先限流**（网关令牌桶 + 应用内 Sentinel），把流量削到系统能承受的范围。超出的直接返回"活动太火爆"，这是产品体验问题不是技术失败。

### 坑 6：防重集合只加不清

- `buyer:goodsId` 集合会无限膨胀。活动结束后异步清理，或改用带 TTL 的 bitmap/hash。

## 五、压测清单（上线前必做）

| 项目 | 验证点 |
|------|--------|
| 超卖 | 并发压到库存 0，核对订单数 = 库存数，**绝不能多** |
| 少卖 | 对账脚本：Redis 已扣数 - 成功订单数 ≈ 未支付取消数，不能有凭空消失 |
| 重复购买 | 同一用户并发点 100 次，只能成功 1 单 |
| 回补 | 下单不支付等超时，库存准确回来 |
| 售罄后的用户体验 | 售罄请求毫秒级返回，不拖垮下游 |
| Redis 故障演练 | 挂掉主节点，看是否快速失败而非雪崩到 DB |
