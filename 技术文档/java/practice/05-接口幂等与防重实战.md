# 05 · 接口幂等与防重实战

> 幂等不是单点技术，是**前后端 + 存储 + 链路**的组合拳。本篇按"重复从哪来 → 单点方案 → 组合方案"展开，全部带可落地代码。
> 理论见 `../distributed/README.md#五幂等设计`；MQ 消费幂等见 `../mq/README.md#五消费幂等`。

---

## 一、重复从哪来（对号入座）

| 来源 | 特征 | 防御层 |
|------|------|--------|
| 用户狂点按钮 | 同一会话、间隔极短 | 前端防抖 + 后端 token/锁 |
| 网络超时重试 | 同一请求体，调用方不知是否成功 | 幂等 token / 唯一索引 |
| MQ 重复投递 | at-least-once 语义必然发生 | 消费端唯一键 |
| 定时任务重跑/补偿 | 间隔可能几小时 | 状态机 + 去重表 |
| 恶意刷单 | 伪造请求 | 服务端强校验，别信前端 |

**原则：前端的一切防重都只是体验优化，后端必须独立兜底。**

---

## 二、单点方案与代码

### 1. 唯一索引（最后的防线，永远要有）

```sql
alter table tb_order add unique index uk_order_no (order_no);
```

```java
@Transactional(rollbackFor = Exception.class)
public void createOrder(OrderCmd cmd) {
    try {
        orderMapper.insert(build(cmd));       // order_no 唯一索引
    } catch (DuplicateKeyException e) {
        log.info("重复下单拦截: {}", cmd.getOrderNo());
        return;                               // 幂等返回，不报错
    }
}
```

> **细节**：捕获 `DuplicateKeyException` 后**返回成功或查询已有单返回**，而不是抛错——调用方（MQ 重试）要的是"这单已处理过"，报错会触发无意义重试。
> **为什么它最重要**：token 会过期、锁会失效、Redis 会挂，唯一索引是**数据库层的绝对兜底**，不依赖任何中间件。

### 2. Token 机制（防表单重复提交标准解法）

```text
流程：进入页面 → 申请 token（存 Redis）→ 提交时携带 → 服务端原子校验并删除 → 处理业务
```

```java
// 申请
public String applyToken() {
    String token = UUID.randomUUID().toString();
    redis.opsForValue().set("idem:" + token, "1", Duration.ofMinutes(5));
    return token;
}

// 校验+删除必须原子（Lua），否则并发两请求都能通过"查存在"
private static final String DEL_IF_EQ =
    "if redis.call('get', KEYS[1]) then return redis.call('del', KEYS[1]) else return 0 end";

public void submit(String token, OrderCmd cmd) {
    Long ok = redis.execute(new DefaultRedisScript<>(DEL_IF_EQ, Long.class),
                            List.of("idem:" + token));
    if (ok == null || ok == 0) {
        throw new BizException("请勿重复提交");
    }
    orderService.createOrder(cmd);   // 里面仍有唯一索引兜底
}
```

**细节坑**：校验与删除必须是**一个原子操作**。`if (exists) del` 两步写法在并发下两个请求都能通过——这是 token 方案最常见的事故写法。

### 3. 状态机（业务天然幂等，优先用）

```sql
-- 只有"待支付"才能流转到"已支付"，重复回调直接 0 行
update tb_order set status = 'PAID', pay_time = now()
where order_no = #{no} and status = 'PAYING';
```

```java
int rows = orderMapper.markPaid(no);
if (rows == 0) {
    log.info("状态已流转，重复回调忽略: {}", no);   // 幂等
}
```

> 支付回调、审批流、订单流转这类**有明确状态**的场景，状态机是最优雅的幂等——不需要额外存储。

### 4. 分布式锁（防并发穿透，不承担幂等主体）

```java
// Redisson：同一业务键加锁，把并发变成串行
RLock lock = redisson.getLock("lock:order:" + cmd.getUserId());
if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) {
    throw new BizException("操作太频繁");
}
try {
    orderService.createOrder(cmd);
} finally {
    lock.unlock();
}
```

**定位要清楚**：锁解决的是"**并发瞬间**重复"，锁过期后重试到达还是会重复——**锁只做并发收敛，幂等靠唯一索引/状态机兜底**。两者是搭档不是替代。

### 5. 去重表 / Redis SETNX（消息消费场景）

```java
// 简单场景用 Redis 短期去重
Boolean first = redis.opsForValue()
    .setIfAbsent("mq:done:" + msg.getMessageId(), "1", Duration.ofHours(24));
if (Boolean.FALSE.equals(first)) return;   // 已处理过

// 更可靠用去重表（DB 层，消息ID唯一索引）
```

Redis 去重键丢了会重复处理 → 消费逻辑本身仍要幂等（DB 唯一索引兜底）。

## 三、组合方案：一个下单接口的完整防御

```text
1. 前端：提交后按钮置灰（体验层）
2. 网关/应用：用户级限流（防刷）
3. 入口：token 原子校验删除（防表单重复提交）
4. 业务：分布式锁 userId 收敛并发
5. 落库：order_no 唯一索引（绝对兜底）
6. 状态机：订单流转 where status=旧状态
```

逐层递进，每层独立成立，**任何一层失效都不会造成脏数据**——这是幂等设计的正确姿势。

## 四、方案对比速查

| 方案 | 可靠性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| 前端防抖 | 低（可绕过） | — | 低 | 仅体验优化 |
| 唯一索引 | **最高（DB兜底）** | 高 | 低 | 一切有唯一键的写入，**必选** |
| Token+Lua | 高 | 高 | 中 | 表单/支付类防重复提交 |
| 状态机 | 高 | **最高** | 低（随业务自带） | 有状态流转的业务，**优先** |
| 分布式锁 | 中（过期即失效） | 中 | 中 | 并发收敛，不承担幂等主体 |
| Redis SETNX 去重 | 中 | 高 | 低 | MQ 消费短期去重 |

---

## 五、常见踩坑

1. **只做了 Redis 去重，没有 DB 兜底**——Redis 重启/主从切换丢 key，重复请求直达 DB。
2. **唯一索引建错字段**——用自增 id 唯一当然永远不冲突；要用**业务键**（订单号、外部流水号）。
3. **幂等接口返回值不一致**——重复请求应返回与首次相同的结果（或明确的"已处理"），而不是 500。MQ 消费者抛错会无限重试。
4. **锁与幂等混为一谈**——"我加了分布式锁" ≠ "我幂等了"。锁过期窗口内的重试照样穿透。
5. **HTTP 语义用错**——对外 API 该 PUT/DELETE 幂等语义的用 POST，客户端重试放大重复。
