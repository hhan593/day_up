# 01 · 线上故障排查实战手册

> 场景驱动的排查 SOP：每个故障给出「现象 → 排查链路（可复制的命令）→ 高频根因 → 修复」。
> 理论背景见 `../jvm/README.md`；命令细节见 `../java-middle/37-JVM调优与故障排查.md`。

## 场景一：CPU 100%

### 排查链路（背下来，五步定位）

```bash
# 1. 找到进程
top                          # 找到 CPU 最高的 Java 进程，记下 PID，如 12345

# 2. 找到进程内最耗 CPU 的线程
top -Hp 12345                # 记下线程 ID，如 12378

# 3. 线程 ID 转十六进制（jstack 里是十六进制）
printf "%x\n" 12378          # 输出 304a

# 4. 抓线程栈，搜十六进制 ID
jstack 12345 | grep -A 30 "0x304a"

# 5. 栈顶就是罪魁祸首的业务代码行
```

### 高频根因（按出现概率排序）

| 根因 | 栈的特征 | 典型代码 |
|------|---------|---------|
| **死循环** | 业务方法自环 | `while (true)` 漏了退出条件、链表成环遍历 |
| **正则回溯灾难** | `java.util.regex.Pattern` 栈顶 | `"(a+)+$"` 匹配超长字符串，NPA 灾难 |
| **频繁 GC** | 栈里全是 GC 线程（`GC Thread#`） | 转场景四排查内存 |
| **序列化/加密热点** | `JSON.parse`/`MessageDigest` | 大对象反复转换、循环里加密 |
| **自旋/CAS 竞争** | `Unsafe.compareAndSwap` 长期占用 | 高竞争下的自旋锁 |

> **实战经验**：抓栈要抓**三次、间隔几秒**。单次栈可能刚好抓在偶然路径上；三次栈顶都一样才可信。

## 场景二：内存泄漏与 OOM

### 前提：必须提前打开的两个开关（出事时才来得及）

```bash
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/
-Xlog:gc*:file=/data/logs/gc.log:time,uptime:filecount=5,filesize=50M
```

> 没开这两个开关的 OOM 排查 = 事后盲猜。**这是上生产前的必做项**，见 `07-SpringBoot生产配置清单.md`。

### 排查链路

```bash
# 1. 先看是不是真泄漏：jstat 看 Old 区趋势
jstat -gcutil 12345 2000 10
#  关注 O 列：每次 FGCT 后 Old 回落越来越少、最终贴着 100 → 泄漏
#  如果 FGCT 频繁但 O 回落正常 → 大对象抖动，不是泄漏

# 2. 抓堆快照
jmap -dump:live,format=b,file=/data/heap.hprof 12345
#  生产大堆建议用 HeapDumpOnOutOfMemoryError 的自动 dump，jmap 会停顿

# 3. MAT 打开 hprof → Leak Suspects / Dominator Tree
#    看支配树里最大的对象，沿 GC 引用链找到"是谁引用着它"
```

### 高频泄漏源（都是真实事故常客）

| 泄漏源 | 细节 |
|--------|------|
| **ThreadLocal 未 remove** | 线程池线程长存，Entry 的 value 强引用累积；**用户数据串号**比 OOM 更先发生（见 `../concurrency/README.md#九threadlocal`） |
| **静态集合只增不减** | `static Map` 当缓存没有淘汰策略 |
| **连接/流未关闭** | 用 try-with-resources；连接池泄漏表现为场景五 |
| **类加载器泄漏** | 热部署/动态生成类（Groovy、反射代理）撑爆 Metaspace |
| **大量 `String.intern()`** | 常量池膨胀 |

### Metaspace 撑爆特例

现象：`OutOfMemoryError: Metaspace`，堆却很空。
根因：动态代理/字节码生成（CGLIB、Groovy 脚本热更新）+ 没有 `-XX:MaxMetaspaceSize` 上限。
处理：加上限 + 排查谁在无节制生成类。

## 场景三：接口突然变慢

### 分层定位（从外到内，每层都有计时证据）

```text
用户感知慢
 ├─ 网关层：网关日志里 upstream 耗时 vs 网关自身耗时
 ├─ 应用层：应用访问日志里的总耗时；拆解——
 │    ├─ Arthas trace：定位方法内哪一步慢
 │    └─ 常见：锁等待、线程池排队、GC 停顿（对照 GC 日志时间点）
 └─ DB 层：慢查询日志（../mysql/19-日志.md）
```

### Arthas 三板斧（在线诊断，不重启）

```bash
# 1. 耗时分解：这个方法内部每一层的耗时
trace com.demo.OrderService createOrder '#cost > 200'

# 2. 观察入参/返回值/异常（不写日志也能看）
watch com.demo.OrderService createOrder '{params, returnObj, throwExp}' -x 2

# 3. 看方法为什么走了慢分支
jad com.demo.OrderService        # 反编译确认线上跑的真是这个版本
```

> **实战经验**：先 `jad` 确认线上代码版本再排查逻辑。「我本地没问题」的 80% 原因是线上跑的不是你以为的版本。

### 隐蔽慢因清单

| 慢因 | 识别 |
|------|------|
| **日志同步写盘** | 高 QPS 下同步日志成为瓶颈 → 异步 appender |
| **锁竞争** | jstack 里大量线程 BLOCKED 在同一把锁 |
| **线程池排队** | 拒绝策略/队列长度，见 `09-线程池生产实践.md` |
| **GC 停顿** | 接口慢的时间点与 GC 日志的 stop-the-world 时间吻合 |
| **DNS/外部依赖抖动** | 甩锅前先确认：给外部调用加超时与监控 |

## 场景四：频繁 FullGC

```bash
jstat -gcutil 12345 1000
# 看：FGC 次数增速、O(Old) 水位、FGCT(累计停顿)
```

| 模式 | 判断 |
|------|------|
| Old 缓慢爬升，FGC 后回落一点点 | **泄漏**（场景二流程） |
| FGC 后 Old 回落到很低，但很快又满 | **大对象/缓存放量**：查 `jmap -histo` 里 byte[]/集合 |
| Metaspace 水位高 | 动态类生成 |
| 显式 System.gc() | 代码里搜 `System.gc`（RMI/Dubbo 老版本会触发） |

## 场景五：连接池耗尽

现象：请求卡住然后超时，日志出现 `Connection is not available, request timed out after 30000ms`。

```bash
# HikariCP 默认 maximumPoolSize 只有 10 —— 大多数事故就是没配它
```

排查链路：

```bash
# 1. 看应用日志：是不是拿连接超时
# 2. DB 侧看连接与锁：
select * from information_schema.innodb_trx;        -- 有没有长事务占着连接
show processlist;                                    -- 连接都在干什么
# 3. 应用侧 jstack：大量线程 WAITING 在 getConnection
```

高频根因：

| 根因 | 细节 |
|------|------|
| **长事务** | `@Transactional` 方法里调了外部 HTTP/RPC——连接被霸占数秒，池瞬间被吸干（**事务内不做远程调用**，铁律） |
| 池太小 | 默认 10 根本不够；参考公式 `连接数 ≈ 核心数 * 2 + 有效磁盘数` 起步，再压测调 |
| 慢 SQL | 连接被慢查询占用 → 治理 SQL |
| 泄漏 | 手工 `DriverManager.getConnection` 没关 |

## 场景六：磁盘满 / 日志暴涨

```bash
df -h                          # 哪个分区满
du -h --max-depth=2 /data 2>/dev/null | sort -rh | head
ls -lh /data/logs/             # 通常是日志或 dump 文件
```

- 日志没配滚动切割（logback `RollingFileAppender` + `maxHistory`）。
- 堆 dump 忘了清理。
- **清理被打开的日志文件用 `> file` 清空，不要直接 `rm`**（rm 后空间不释放，进程还握着句柄）。

## 排查心法（比命令更重要）

1. **先看监控，再上机器**：有没有变更（发布/配置/流量）？90% 的故障跟着变更走。
2. **保留现场再重启**：先 dump（堆/线程/日志拷贝），再考虑重启止血。
3. **证据链完整**：每一层的时间点能对上（请求时间 = 日志时间 = GC 停顿时间）才下结论。
4. **一次只改一个变量**：同时改参数和代码，好不了也不知道谁治好的。
5. **故障复盘写进团队 wiki**：同样的坑不踩第二次，这是实战经验复利的来源。
