## 一、为什么用 MQ

- **异步**：下单后发短信/积分异步处理，主流程快返回。
- **解耦**：生产者不依赖消费者，新增消费者零侵入。
- **削峰**：突发流量先入队，下游按能力消费（保护 DB）。
- **最终一致**：通过事件驱动保持多服务数据同步。

---

## 二、核心概念

- **Producer / Consumer**：生产/消费消息。
- **Broker**：消息服务器。
- **Topic / Queue**：消息分类/队列。
- **Exchange（RabbitMQ）**：路由规则（direct/fanout/topic/headers）。
- **Partition（Kafka）**：物理分片，提供并发与顺序能力。
- **Consumer Group**：组内竞争消费（Kafka 一个 partition 只被组内一个消费者消费）。
- **Offset / Ack**：消费位点 / 确认机制。

## 三、常见 MQ 对比

| MQ | 特点 | 适用 |
|----|------|------|
| Kafka | 高吞吐、分区、持久日志、流式 | 日志、大数据、高并发 |
| RocketMQ | 事务消息、低延迟、阿里系 | 电商、金融、分布式事务 |
| RabbitMQ | 丰富路由、易用、 Erlang | 企业应用、复杂路由 |

## 四、可靠投递

- **生产端**：
  - 发送确认（Confirm 机制）：Broker 收到才 ack。
  - 失败重试 + 本地消息表/事务消息兜底。
- **Broker 端**：
  - 持久化（刷盘）+ 多副本（ISR/主从）防丢。
- **消费端**：
  - 手动 Ack（处理完再确认），处理失败不入队或进重试队列。
- RocketMQ **事务消息**：半消息 + 本地事务 + 回查，保证"本地 DB 与消息"一致。

---

## 五、消费幂等

- 原因：网络重试、rebalance 重投，消息可能重复。
- 解法：
  - **业务唯一键**：订单号去重表（`UNIQUE` 约束）。
  - **幂等 token**：消费前查 Redis `SETNX` 标记。
  - **状态机**：仅处理期望状态（如"待支付→已支付"）。

```java
if (redis.setnx("mq:" + msgId, "1", 24h) == 0) return;  // 已处理
// 业务处理
```

## 六、顺序消费

- Kafka：同一 **partition** 内消息有序 → 把需有序的业务键（如订单ID）按 `hash` 路由到固定 partition。
- 代价：牺牲分区并行度；全局顺序几乎不可行，按业务局部顺序即可。

---

## 七、延迟 / 死信

- **延迟消息**：RocketMQ 原生支持（18 个延迟级别）；RabbitMQ 用死信 TTL 实现；Kafka 借助时间轮/外部调度。
- **死信队列（DLQ）**：消费多次失败的消息转入，避免阻塞主流，便于人工排查。
- 场景：订单 30 分钟未支付自动关单（延迟消息经典案例）。

## 八、常见面试考点

1. **MQ 解决什么问题？** → 异步、解耦、削峰、最终一致。
2. **如何保证不丢消息？** → 生产 Confirm + Broker 持久化多副本 + 消费手动 Ack。
3. **如何保证不重复消费？** → 消费幂等（唯一键/幂等 token/状态机）。
4. **如何保证顺序？** → 同业务键路由到同 partition/queue。
5. **消息积压怎么办？** → 加消费者/临时扩容、提升消费能力、跳过非关键。
6. **事务消息原理？** → 半消息 + 本地事务 + 回查（RocketMQ）。
7. **Kafka 高吞吐原因？** → 顺序写盘、零拷贝、批量、压缩、partition 并行。
8. **RabbitMQ 交换机类型？** → direct/fanout/topic/headers。
