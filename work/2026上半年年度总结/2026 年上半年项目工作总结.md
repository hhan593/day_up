# 2026 年上半年项目工作总结

2026 年上半年，整体工作围绕多个业务系统的建设、迭代和交付展开，覆盖客服工单、数据小程序、电子签、智能客服、经营管理平台、物业管理系统等项目。上半年既有从 0 到 1 的新项目搭建，也有既有系统的持续优化和业务适配，工作内容集中在前端业务开发、移动端小程序建设、数据看板、权限体系、第三方系统集成、工程化配置和交付问题修复等方面。

总体来看，上半年项目推进节奏较快，多个系统完成了关键业务链路建设和核心功能落地，支撑了客服处理、经营分析、电子合同签署、物业工单闭环、数据驾驶舱展示等实际业务场景。同时，在高频迭代过程中也暴露出提交规范、测试覆盖、配置管理、接口契约、文档沉淀和核心业务模型稳定性等方面的不足，需要在后续工作中持续改进。

## 一、上半年主要工作回顾

### 1. 客服工单系统持续完善，提升业务处理效率

上半年，客服工单系统主要围绕工单创建、来电建单、工单处理、任务单拉单、业务字段配置和首页数据看板进行功能完善。项目在 5 月和 6 月进入较密集的业务迭代阶段，累计完成约 122 次提交，覆盖 170 多个文件。

在业务流程方面，重点优化了订单创建弹窗、字段映射、表单重置、错误处理、投诉时间处理、历史相似工单展示、工单升级等能力，使工单创建和来电建单流程更加完整。针对工单处理环节，补充了退费信息展示、处理表单退费字段、转发理由必填校验、直接完结能力，并调整投诉问题描述、投诉诉求等校验规则，进一步贴合客服实际处理场景。

在配置化能力方面，持续增强 BusinessFieldsRenderer，支持更多字段类型、级联选择、动态标签和多业务线字段配置，降低不同业务类型表单的重复开发成本。项目还新增或完善了小兔驾考、微信券、出租车、充电、车主客、平安等业务类型表单和详情展示，提升了工单系统对多业务线的承载能力。

此外，上半年还推进了 ETC 拉单查询、防抖逻辑、手机号限制、任务单列表展示等能力优化，并重构首页报表模块，对接首页数据接口，补充时间范围筛选、业务子页面路由、空状态处理、图表和表格展示等功能，为客服管理和运营监控提供了更直观的数据入口。

### 2. 小兔数据小程序持续扩展，数据看板能力进一步增强

小兔数据小程序上半年围绕 ETC 客车与货车、微信券、智慧停车、ETC 助缴等数据看板进行了大量功能建设和展示优化。

ETC 客车与货车模块持续完善收入、发行、通行等核心页面，补充增值服务收入总览、服务费、企业消耗订单、延保服务等数据展示能力，并在货车模块中新增收入、发行、通行相关组件。项目在数据展示细节上持续打磨，补充了单位、千分位、趋势、TopRate、空值兜底、图例展示等能力，提升了数据看板的可读性。

微信券模块扩展了保险、运营商、其他、银行等数据概览组件，支持发券数量、发券金额、核销数量、核销金额等统计展示和下载，并持续修复导出日期、标签页时间筛选、统计类型映射等问题。

智慧停车模块从 0 到可用，完成真实 API 接入，移除 mock 数据，新增停车数据统计、临停实收趋势、车主增长、项目排名、缴费率和实收排名切换等功能。ETC 助缴模块也在 5 月底启动建设，并在 6 月完善真实数据展示，覆盖助缴成功趋势、代收方式统计、封闭停车场助缴明细、车主排行、服务商排行、路侧订单统计等场景。

在基础能力方面，小程序重构了首页和我的页面，新增个人中心、登录登出、底部导航、自定义标签页展开面板、用户信息接口、权限字符、无权限提示、token 七日滑动续签等能力。公共组件层面，优化了卡片、表格、图表、TopBar、TopTable、日期选择器等组件，并补充数字格式化、日期处理、统计类型映射、请求级 timeout 等工具能力。

### 3. 电子签项目完成主体功能建设，合同签署链路基本成型

电子签项目上半年完成了从 0 到 1 的主体功能建设。项目基于 uni-app、Vue3、TypeScript、Pinia、Wot UI、UnoCSS 搭建小程序端开发框架，补充多环境配置、微信小程序构建脚本、分包配置、manifest 配置、静态资源、路由拦截、登录态存储、HTTP 请求封装等基础能力。

登录与认证体系方面，实现并持续调整了登录逻辑、未登录态展示、手机号登录、企业注册、企业认证、员工认证、腾讯电子签集成认证等流程，并完善个人信息、企业信息、企业创建人、联系电话、联系地址等管理页面。

合同核心业务是上半年投入最大的模块。项目完成了合同列表、合同详情、合同发起、合同签署、合同预览、合同下载、合同收藏、草稿箱、撤销合同、再发一次、签署邀请、分享链接、二维码下载等功能，并进一步增强企业版发起合同、动态签署、企业对企业签署、PDF 类型支持、文件上传、签署区域设置、坐标转换、签署截止时间、生效和到期时间校验、多位置签署等能力。

组织架构与权限方面，完成组织架构、部门管理、员工添加和编辑、角色新增和编辑、角色详情、角色同步腾讯电子签、成员管理、部门树选择、负责人切换、企业管理员身份检查等功能。订单与套餐方面，实现加量包购买、下单、订单列表、订单详情、订单状态刷新、超时订单自动关闭、退款状态字段、我的加量包等能力，为后续商业化套餐购买流程奠定基础。

项目还完成了首页、模板列表、模板详情、模板文件下载、更多模板、使用指南、关于我们等页面，并将应用名称调整为“恒信签”。工程质量方面，补充了 SonarQube、eslint、commitlint、husky、lint-staged、类型检查脚本等工具，API 类型定义也在逐步完善。

### 4. 智能客服项目完成聊天主流程建设，打通客服集成基础能力

智能客服项目上半年可追溯提交集中在 6 月，主要完成了项目初始化到智能客服聊天可用的核心建设。

项目基于 Vue 3、Vite、TypeScript、Pinia、Vue Router 搭建前端基础框架，同时包含后端服务、Dockerfile、Nginx 配置、Socket/WebSocket 调试页面、OpenSpec 方案文档等内容。前端完成聊天视图、消息状态管理、聊天 API、Socket 适配层、聊天服务封装等主流程能力。

第三方客服集成方面，项目包含智齿客服相关 OpenSpec，并在后端目录中建设 sobot 模块、callback controller、token service、chat gateway 等能力，说明上半年重点之一是打通前端在线客服、后端服务和第三方客服能力。

Socket 通信方面，项目针对后端 Netty-SocketIO 进行了版本兼容调整，将 socket.io-client 从 v4 降级到 v2，并重构连接认证流程，新增 HMAC-SHA256 签名认证。消息体验方面，修复移动端首条回复展示不完整问题，优化媒体消息处理、URL 检测、消息去重、流式渲染，并优化转人工路径。

FAQ 能力方面，将 FAQ 从内联实现重构为独立组件和接口方案，新增 FAQ 业务列表、卡片、弹窗、分组、问题列表和类型定义，并将 FAQ 方案 ID 从 query 参数调整为 route params。项目还新增推荐相关问题弹窗，将 sessionId 调整为后端下发，并在页面头部补充应用名称、头像、欢迎语和 matchSource 标签展示，使系统从“能聊”进一步向“业务配置化展示”演进。

### 5. 经营管理平台持续支撑财务、权限、用友同步等业务迭代

经营管理平台上半年主要集中在 1 月至 3 月，当前分支统计共有 84 个提交，其中非合并提交 62 个，涉及 150 个文件，整体变更规模较大。

财务付款、发票、凭证相关链路持续修复和优化，包括付款申请提交审核回显、预付核销数据回显、备注回填、采购发票校验、合同到期日填充、凭证推送记录、凭证详情展示、收入时间月份格式化等内容。项目还调整了实时收款账单、应收账单、订单明细、预付核销等财务链路字段，保障财务业务流程的准确性。

用友同步能力方面，新增或完善客商信息推送、第三方结算单位推送、客商推送日志、用友同步日志、产品分类同步日志等功能，支持一级和二级产品分类同步，并补充业务系统掩码密钥配置。

企微、小程序、权限体系方面，新增微信小程序用户访问权限配置、接口白名单管理，优化权限树勾选策略、全选逻辑、按钮权限控制和权限配置弹窗体验，支持企微扫码登录绑定本地系统账号，并在用户管理中增加企微账号显示、绑定校验和筛选能力。

通知任务模块方面，新增任务管理、发送记录、接收人编辑、人员选择、企微用户选择等能力，并优化已选企微账号缓存和筛选逻辑。ETC 与数据后台报表方面，新增 ETC 货车后台管理代码，包含收入报表、发行报表、通行报表的列表、详情、编辑、导入等页面，并持续修复导出、字典值映射、字段展示等问题。

### 6. 物业管理系统完成多端主体建设，形成工单业务闭环

物业管理系统上半年开发集中在 3 月底至 4 月底，期间完成 185 个提交，主要改动覆盖后端、微信小程序端和 PC 管理端。项目整体完成了从 0 到 1 的主体建设。

基础建设方面，项目搭建 FastAPI 后端、Vue 管理端、微信小程序端，编写需求、架构、API、部署等文档，并建立 Docker、Nginx、部署脚本和环境配置等基础设施。后端完成用户、角色、权限、部门、公告、工单等基础模块 API，增加统一响应、异常处理、鉴权、Redis、数据库模型、初始化 SQL、Alembic 迁移、限流、结构化日志、文件上传等能力。

微信小程序端完成首页、公告、个人中心、工单列表、工单详情、工单创建、评价、手机号绑定、用户信息维护、反馈、设置、关于等页面，并建设图片上传组件、空状态组件、工单卡片组件。管理端完善用户管理、部门管理、字典管理、菜单管理、权限管理、公告管理、考勤管理、反馈管理、小程序用户管理、工单管理、登录日志和操作日志等功能。

工单系统是项目核心，上半年支持工单创建、查看、接单、处理、完成、评价、转派，补充工单分类、子分类、投诉类处理、匿名提交、提交人姓名自定义、多状态筛选、处理记录目标姓名解析、图片上传、地址补充等能力，并多次调整派单规则，包括自动派单、依次派单和定时任务自动派单。

企业微信能力方面，项目接入企微扫码登录，修复回调、二维码 iframe、跳转方式、appId/appSecret、userId 获取等问题，并增加企业微信消息推送、工单分配通知、企微打卡记录同步等能力。消息提醒方面，支持小程序订阅消息、匿名用户完单提醒和企微应用消息通知。部署方面，完善 Docker 镜像构建、部署脚本、生产部署配置，并处理 MySQL 字符集、Redis 密码、uploads 挂载、国内镜像源等问题。

## 二、工作成果与亮点

### 1. 多个项目完成关键业务闭环

上半年最突出的成果，是多个项目都完成了较完整的业务链路建设。电子签项目形成了合同发起、签署、预览、下载、撤销、再发、邀请、组织权限、订单套餐等主体能力；物业管理系统形成了后端、管理端、小程序端和工单闭环；智能客服项目完成了聊天、FAQ、推荐问题、Socket 鉴权和第三方客服集成基础；客服工单系统持续增强了来电建单、工单处理、任务单拉单和多业务线字段配置能力。

这些工作不仅是页面和接口的堆叠，更是围绕实际业务流程建立可运行、可交付、可继续迭代的系统基础，为后续业务扩展提供了承载平台。

### 2. 数据看板和经营分析能力明显增强

小兔数据小程序围绕 ETC 客车、ETC 货车、微信券、智慧停车、ETC 助缴等场景持续建设数据看板，补充趋势、排行、统计、下载、权限控制、日期筛选、空值展示等能力。客服工单系统也重构首页报表模块，对接首页数据接口，提供时间范围筛选和业务子页面入口。

这些工作提升了业务数据的可视化程度，使运营和管理人员能够更快了解业务状态、发现趋势变化，也为后续经营分析和数据决策打下基础。

### 3. 配置化和组件化能力有所沉淀

上半年多个项目都在推进公共能力沉淀。客服工单系统通过 BusinessFieldsRenderer 推进业务字段配置化；小兔数据小程序沉淀了图表、表格、数据卡片、日期选择器、数字格式化、统计类型映射等公共组件和工具；电子签项目逐步完善 API 类型定义、工程化脚本和基础页面能力；智能客服项目将 FAQ 从内联实现重构为独立组件和接口方案。

这些沉淀降低了后续重复开发成本，也为多业务线、多页面、多场景的快速迭代提供了基础。

### 4. 第三方系统集成能力持续增强

上半年涉及较多第三方系统和外部能力集成，包括腾讯电子签、智齿客服、用友、企业微信、微信登录、小程序订阅消息等。各项目围绕认证、权限、消息推送、数据同步、合同签署、扫码登录等场景做了大量联调和适配。

虽然这些集成过程暴露出不少问题，但也积累了外部系统接入、鉴权流程处理、回调联调、权限同步、消息通知等经验，为后续类似项目提供了可复用的实践基础。

### 5. 工程化意识逐步增强

多个项目补充了 TypeScript、eslint、commitlint、husky、lint-staged、SonarQube、类型检查、构建脚本、Docker、Nginx、环境配置、分包优化等工程能力。虽然部分工具尚未完全落地为强约束，但相较单纯业务开发，上半年已经开始重视工程质量、构建交付、代码扫描和部署稳定性。

## 三、存在的问题和不足

### 1. 提交规范不稳定，影响问题追溯和复盘效率

多个项目都存在提交信息不规范的问题，例如提交信息仅为“1”“提交”，或存在拼写错误、异常符号、重复前缀、描述过于笼统等情况。经营管理平台和物业管理系统还存在较多合并提交、重复修复提交和变更范围较散的提交。

这类问题会直接影响后续问题定位、需求追溯、版本说明生成和工作复盘。尤其在多个项目并行、多人协作和交付节奏较快的情况下，提交历史如果不能准确反映变更意图，会增加维护成本。

### 2. 自动化测试覆盖不足，核心链路回归风险较高

从各项目提交记录和素材来看，上半年主要以功能开发和问题修复为主，测试补充不明显。客服工单创建、字段映射、退费、相似工单、合同签署、订单支付、认证、权限、FAQ、Socket 连接、消息流式渲染、物业工单派单、企微登录、数据格式化等关键链路，都存在较高回归风险。

目前大量问题依赖人工验证和上线后修复，容易在接口字段、日期格式、权限判断、0 值展示、单位换算、移动端兼容、第三方回调等边界场景中反复出现。

### 3. 配置和敏感信息管理需要加强

多个项目存在环境配置频繁切换、测试和生产地址被提交、`.env` 文件进入仓库、密钥相关内容出现在提交记录中的情况。智能客服、物业管理系统、电子签等项目都涉及环境变量、第三方密钥、接口域名、企微配置等敏感或易错内容。

配置管理不稳定会带来协作混乱、发布风险和安全风险。对于已经提交过的真实密钥，应按泄露处理，及时轮换，并检查远端仓库历史。

### 4. 接口契约和 mock 数据一致性不足

小兔数据小程序的智慧停车、ETC 助缴等模块经历了 mock 数据、真实接口接入、字段修复、路径修复、单位修复、0 值修复等过程。客服工单系统首页看板也经历了从 mock、组件拆分、接口对接到空状态和筛选处理的多轮调整。

这说明部分复杂模块在开发前期，接口格式、字段规则、数据边界和页面结构还不够明确。mock 与真实接口契约不一致，会导致联调阶段成本增加，也容易把大量问题推迟到上线前后集中暴露。

### 5. 核心业务模型沉淀不足

上半年不少业务功能推进速度很快，但部分核心模型还没有完全稳定。客服工单系统的动态表单和业务字段配置仍在频繁调整；物业管理系统的派单规则、按钮权限、匿名工单、状态流转多次变化；电子签项目的合同签署涉及日期、PDF、坐标、签署方、权限、认证方式、企业和个人差异等复杂逻辑；智能客服项目的 Socket 鉴权、FAQ、推荐问题、sessionId 归属也经历了重构。

这些问题并不单纯是代码问题，本质上是业务状态、权限矩阵、字段模型、异常流程和集成边界还需要进一步抽象和固化。

### 6. 文档沉淀和工程治理仍偏后置

部分项目虽然补充了 README、API 文档、设计文档、测试说明和方案文档，但从后续大量调整看，文档与实际实现之间可能存在滞后。智能客服 README 偏模板化，客服工单首页数据格式文档偏后置，物业管理系统文档可能需要与实际接口和业务流程重新对齐。

工程治理方面，部分项目存在调试代码残留、模板示例未清理、lint-staged 未真正执行检查、锁文件管理不统一、临时脚本进入版本记录等情况，说明质量门禁还没有完全成为稳定流程。

## 四、经验教训复盘

### 1. 快速交付必须配套最小质量闭环

上半年多个项目都体现出“交付快、修复密”的特点。快速推进业务功能是必要的，但如果缺少最小测试、验收清单、接口契约确认和发布前检查，问题就会在联调、上线或用户使用阶段集中暴露，反而增加整体成本。

后续对于核心链路，应至少建立“接口字段确认、边界数据验证、权限场景验证、移动端真机验证、发布前配置检查”的最小闭环。即使短期内无法建设完整自动化测试，也应先形成固定检查清单和关键用例。

### 2. 第三方集成要前置验证关键路径

腾讯电子签、智齿客服、用友、企业微信等外部系统接入中，鉴权、回调、权限、签名、环境地址、用户身份映射往往是最容易出问题的部分。上半年多个项目在这些环节发生了反复修复。

后续接入第三方系统时，应优先验证认证、回调、异常返回、环境切换、权限边界和线上部署路径，而不是等页面功能基本完成后再集中联调。关键流程可先做最小 demo 或联调脚本，提前暴露协议和环境问题。

### 3. 复杂业务应先沉淀状态机、权限矩阵和字段模型

工单、合同签署、权限配置、派单、数据看板等模块都有较强业务规则。如果只按页面逐个推进，短期可以快速交付，但后续容易出现逻辑分散、重复判断、边界不清、修复牵一发动全身的问题。

后续对于复杂业务，应优先明确状态流转、角色权限、字段来源、异常分支、可见性规则和操作约束，并尽量沉淀为统一模型或公共函数。这样可以减少页面级重复判断，也能为测试用例设计提供依据。

### 4. 数据展示类问题适合组件化和规范化解决

上半年数据看板中多次出现 0 值误判、金额单位错误、百分比精度、千分位、空值展示、图表空数据、长数字截断、日期格式等问题。这些问题如果每个页面单独处理，很容易重复出现。

后续应将数字格式化、金额单位、百分比、空值兜底、趋势展示、图表注册、日期范围、下载参数等能力沉淀为公共工具、公共组件和展示规范，并补充组件级测试或示例数据校验。

### 5. 提交和文档不是附加工作，而是协作基础

提交信息、README、接口说明、环境说明、变更记录直接影响多人协作、后续维护和问题追溯。上半年多个项目都暴露出提交信息过于随意、文档后置、临时内容进入仓库的问题。

后续应将提交规范、分支规范、环境配置规范、文档更新和发布检查纳入日常开发流程，减少依赖个人记忆和口头同步。

## 五、后续改进方向

1. **统一提交规范和分支管理**

   推行更稳定的 commit message 规范，避免“1”“提交”等无效描述。对于需求、修复、重构、配置、文档等类型，应清晰说明变更范围和目的。减少无意义合并提交和大范围混合提交，提高代码历史可读性。

2. **补齐核心链路测试和验收清单**

   优先为高风险流程补充测试或验收用例，包括工单创建和处理、字段映射、合同签署、订单支付、认证权限、Socket 连接、FAQ、派单规则、企微登录、数据格式化和导出下载等。短期可先落地人工验收清单，中长期逐步建设单元测试、组件测试和端到端测试。

3. **加强环境配置和敏感信息治理**

   明确开发、测试、生产环境变量来源，避免接口地址和密钥直接提交到仓库。对历史中可能泄露的密钥进行排查和轮换。发布前增加配置检查，确保构建模式、接口地址、权限配置、第三方回调地址正确。

4. **前置接口契约和数据模型确认**

   对数据看板、动态表单、第三方集成等模块，开发前应先确认接口 schema、字段含义、空值规则、单位、权限、分页、下载参数等内容。mock 数据应尽量与真实接口保持一致，减少后续切换成本。

5. **沉淀公共组件、工具函数和业务模型**

   将反复出现的数据展示、表单渲染、权限判断、状态流转、文件上传、日期处理、金额格式化、空状态、图表配置等能力沉淀为公共组件和工具函数。对于工单、合同、派单、权限等复杂业务，逐步沉淀状态机、权限矩阵和统一类型模型。

6. **完善文档和交付资料**

   对重点项目补充可维护的 README、启动方式、环境变量说明、接口依赖、部署流程、第三方接入说明、核心业务流程图和常见问题。对已经废弃的旧方案、模板示例、调试文件及时清理，避免新成员接手时产生误解。

7. **持续推进工程质量门禁落地**

   对已有的 eslint、commitlint、husky、lint-staged、SonarQube、类型检查等工具进行梳理，确保它们真正参与提交、构建或发布流程。对于锁文件、依赖管理、代码扫描、格式化规则，应形成统一约束，减少因工具链不一致造成的问题。

## 六、总结

2026 年上半年，整体工作量较大、项目覆盖面广，既支撑了已有系统的业务迭代，也完成了多个新项目的主体建设。客服工单系统提升了多业务线工单处理能力，小兔数据小程序增强了数据看板和经营分析能力，电子签项目完成合同签署主链路建设，智能客服项目打通聊天和客服集成基础，经营管理平台持续支撑财务、权限、用友同步等业务，物业管理系统完成多端建设并形成工单闭环。

从结果看，上半年工作的主要价值在于把多个关键业务系统从需求推进到可用、可交付、可持续迭代的状态，为业务运营、客户服务、合同管理、物业管理和数据分析提供了系统支撑。

同时也要看到，上半年暴露出的不足具有共性：提交规范不稳定、自动化测试不足、配置安全治理不够、接口契约前置不足、复杂业务模型沉淀不够、文档和质量门禁偏后置。后续工作需要在继续保障业务交付的同时，更加重视工程质量、测试验证、配置安全、组件沉淀和文档规范，逐步从“快速完成需求”提升到“稳定、高质量、可维护地交付系统”。
