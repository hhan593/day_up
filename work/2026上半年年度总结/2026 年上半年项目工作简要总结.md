# 项目1.工单系统


  2026 年上半年，项目主要围绕客服工单系统前端进行功能完善和业务适配，重点集中在 工单创建、来电建单、工单处理、任务单拉单、业务字段配置和首页数据看板 等模块。

  上半年共完成约 122 次提交，主要工作集中在 5 月和 6 月。整体变更覆盖 170 多个文件，说明项目在这半年进入了较密集的业务迭代阶段。

  ## 主要工作内容

  1. 完善工单创建和来电建单流程
     优化订单创建弹窗、字段映射、表单重置、错误处理、投诉时间处理、历史相似工单展示和工单升级能力。

  2. 推进业务字段配置化
     增强 BusinessFieldsRenderer，支持更多字段类型、级联选择、动态标签和多业务线字段配置，降低不同业务表单的维护成本。

  3. 接入和优化多业务类型
     新增或完善小兔驾考、微信券、出租车、充电、车主客、平安等业务类型表单和详情展示。

  4. 优化工单处理体验
     增加工单详情退费信息、处理表单退费字段、转发理由必填校验、直接完结能力，并调整投诉问题描述、投诉诉求等校验规则。

  5. 改进任务单和拉单能力
     优化 ETC 拉单查询、防抖逻辑、手机号限制、任务单列表展示及相关字段文案。

  6. 建设首页数据看板
     重构首页报表模块，对接首页数据接口，新增时间范围筛选、业务子页面路由、空状态处理，并优化图表和表格展示。

  7. 完善通用体验和基础能力
# 不足
  7. 1. 提交信息不够规范
     部分提交信息只有 1，也有少量提交信息带有多余符号，后续回溯问题和整理工作成果时不够直观。

  8. 业务迭代集中，重构压力较大
     5 月和 6 月改动非常密集，说明需求推进较快，但也容易带来代码耦合、重复逻辑和测试遗漏风险。

  9. 动态表单能力仍在演进中
     上半年虽然推进了 BusinessFieldsRenderer 和业务字段配置化，但多业务线表单仍频繁调整，说明配置模型可能还没有完全稳定。

  10. 首页看板经历了多轮调整
     首页从 Mock 数据、组件拆分、接口对接到空状态和筛选处理，迭代链路较长，说明前期接口格式和页面结构可能还不够明确。

  11. 环境配置变更较频繁
     .env.development、vite.config.js 多次改动，开发代理、本地 nginx、远程 API 地址来回切换，可能影响协作和环境稳定性。

  12. 部分功能有试错和回滚
     例如 GET 请求节流功能最终被还原，说明一些通用能力上线前验证还不够充分。

  13. 自动化测试体现不足
     从提交记录看，主要是功能和修复类提交，未明显看到测试补充。对于工单创建、字段映射、退费、相似工单等高频业务流程，后续可以加强测试覆盖。

  14. 文档补充偏后置
     首页数据格式文档在功能推进后才补充和迁移，说明部分复杂模块的接口约定、字段规则和业务配置说明还可以更早沉淀。

  过程中暴露的不足

  8. 提交规范不稳定
      - 有 featfeat、refactorrefactor、修改>问题、1、带 emoji 和不带 emoji 混用等提交信息。
      - 后续复盘、自动生成 changelog、按类型统计都会受影响。

  9. 功能上线后修复密集
      - 智慧停车和 ETC 助缴上线后，紧接着出现大量字段、接口路径、0 值误判、权限、日期格式、单位、布局问题。
      - 说明开发阶段的接口联调、边界数据验证和真机验证还不够充分。

  10. 权限和登录逻辑前期设计不够收敛
      - 上半年多次围绕权限字符、无权限展示、权限响应式、权限接口替换、token 续签、微信登录重复请求做修复。
      - 这类基础能力影响面广，说明一开始缺少统一的权限/会话设计边界。

  11. 数据展示边界问题较多
      - 多次修复 0 被显示为 --、金额单位错误、百分比精度、字段取反、长数字截断、空数据图表不注册等。
      - 这些问题适合沉淀为公共格式化函数、展示规范和组件级测试用例。

  12. mock 到真实接口切换成本偏高
      - 智慧停车和 ETC 助缴都有“新增 mock/移除 mock/修复真实接口”的过程。
      - 说明 mock 数据结构和真实接口契约之间存在偏差，建议后续用统一类型定义或接口 schema 约束。

  13. 环境切换存在提交痕迹
      - 记录里有正式环境、测试环境 API 地址切换相关提交。
      - 这类配置最好通过环境变量或构建模式控制，减少误提交和发布风险。

  14. 大文件/大范围改动较多
      - 日期选择器、智慧停车、ETC 助缴、依赖锁文件、uni_modules 等都有较大规模改动。
      - 大提交会提高 review 难度，也容易把业务逻辑、样式、配置、格式化混在一起。

  15. 自动化验证迹象不足
      - 从提交记录看，更多是人工修复 UI、字段、权限和真机白屏问题，缺少明显的测试补充提交。
      - 建议至少补齐工具函数、权限判断、数据格式化、请求层 timeout、核心看板数据转换的单元测试。

1. **提交信息不够规范**
    
    - 出现了 `featfeat`、`refactorrefactor`、`修改>问题`、`1` 等提交信息。

2. **上线后修复比较密集**
    
    - 智慧停车和 ETC 助缴上线后，连续出现接口字段、路径、日期格式、0 值误判、单位、权限、布局等修复。
    - 说明前期联调、边界数据验证和验收清单还可以更扎实。
3. **权限和登录体系前期不够统一**
    
    - 上半年多次修复权限字符、无权限状态、权限响应式、权限接口、token 续签、微信登录重复请求。

4. **数据展示边界处理不足**

5. **mock 和真实接口存在偏差**
    
    - 智慧停车、ETC 助缴都有从 mock 到真实接口后再集中修复的过程。
    - 后续可以用接口类型、schema 或联调契约减少这种返工。
6. **环境配置切换风险较高**
    
    - 记录里有测试环境、正式环境 API 地址切换的提交。
    - 这类配置最好依赖 `.env`、构建模式或 CI 参数，避免手动改代码带来发布风险。
7. **大提交偏多，review 成本高**
    
    - 智慧停车、ETC 助缴、日期选择器、依赖锁文件等都有大范围改动。
    - 大提交容易混合业务、样式、配置和重构，后续排查问题会比较费劲。
8. **自动化测试体现不明显**
    
    - 从提交记录看，更多是功能开发后人工修复。
    - 建议补充工具函数、权限判断、请求层、日期筛选、数据格式化、核心看板数据转换的测试。
