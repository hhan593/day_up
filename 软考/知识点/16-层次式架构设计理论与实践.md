# 16 — 层次式架构设计理论与实践（第二版）

## 1. 层次式架构概述

### 1.1 定义与核心思想

**层次式架构（Layered Architecture）**：将系统按照水平方向切分为若干层，每层承担特定职责，上层依赖下层，下层对上层透明。

**核心思想**：
- **关注点分离**：每层只关注自己的职责
- **单向依赖**：上层依赖下层（严格分层）或上层允许跨层（松散分层）
- **接口抽象**：层间通过接口交互，隐藏实现细节
- **可替换性**：任一层可被替换，只要接口不变

### 1.2 层次架构的优缺点

| 优点 | 缺点 |
|------|------|
| 关注点分离，降低复杂度 | 性能开销（层层传递） |
| 标准化层间接口，利于团队并行开发 | 层数确定困难 |
| 可替换性（更换某一层不影响其他） | 级联修改风险 |
| 可测试性（层可独立测试） | 简单系统可能过度设计 |
| 易于理解和维护 | 不适用于所有场景（如高吞吐数据流） |

## 2. 经典分层架构模式

### 2.1 二层C/S架构（Client/Server）

```
┌─────────────────┐         ┌───────────────┐
│   Client（客户端） │ ←──→   │  Server（服务器）│
│   表示逻辑+业务逻辑 │         │  数据管理       │
└─────────────────┘         └───────────────┘
```

**胖客户端 vs 瘦客户端**：

| 类型 | 客户端职责 | 服务器职责 | 适用 |
|------|-----------|-----------|------|
| **胖客户端** | 表示+业务逻辑 | 数据管理 | 桌面应用、内部系统 |
| **瘦客户端** | 仅表示 | 业务逻辑+数据管理 | 早期Web |

**C/S架构的局限性**：
- 客户端直接连接数据库，安全性差
- 安装维护成本高（每台机器都要安装客户端）
- 不易扩展，连接数有限
- 升级困难（客户端需同步更新）

### 2.2 三层B/S架构（Browser/Server）

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  表示层        │ →  │  业务逻辑层    │ →  │  数据访问层    │
│  (Presentation)│    │  (Business)   │    │  (Data)       │
└──────────────┘    └──────────────┘    └──────────────┘
   用户界面             业务规则             数据库/文件
```

**三层职责**：

| 层 | 别称 | 职责 | 典型技术（Java EE） |
|------|------|------|------|
| **表示层** | UI层/Web层 | 用户交互，数据展示和输入 | HTML/CSS/JS, JSP, Servlet, Thymeleaf, React/Vue |
| **业务逻辑层** | BLL/服务层 | 核心业务规则、流程控制 | Java/Spring, EJB, C#/.NET, Python/Django |
| **数据访问层** | DAL/持久层 | 数据持久化、CRUD操作 | JDBC/JPA/MyBatis, Entity Framework, ORM |

**三层架构优点**：
- 逻辑清晰分层，各司其职
- 可并行开发（定义好接口后）
- 业务逻辑可被多个前端复用
- 变更影响范围可控

### 2.3 B/S 三层架构的几种变体形式（第二版重点）

| 变体形式 | 说明 | 特点 |
|---------|------|------|
| **基于Web服务的B/S** | 业务逻辑封装为Web服务（SOAP/REST） | 支持跨平台调用 |
| **基于EJB的B/S** | 业务逻辑使用EJB组件 | 企业级事务、安全、分布式 |
| **基于COM+的B/S** | 业务逻辑使用COM+组件（.NET平台） | Windows平台集成 |
| **基于CORBA的B/S** | 使用CORBA组件 | 异构系统互操作 |
| **基于Spring的B/S** | 使用Spring框架管理各层 | IoC/DI、AOP、模块化 |

### 2.4 四层架构（DDD 风格）

```
┌──────────────┐
│  用户接口层     │  ← Controller, REST API, RPC Interface
│  (Interface)  │
├──────────────┤
│  应用层        │  ← 应用服务、事务管理、权限校验
│  (Application)│
├──────────────┤
│  领域层        │  ← 领域模型、领域服务、业务规则
│  (Domain)     │
├──────────────┤
│  基础设施层     │  ← 持久化、消息、日志、工具
│  (Infrastructure)│
└──────────────┘
```

**四层与三层区别**：将三层中的"业务逻辑层"进一步拆分为应用层（编排、事务）和领域层（核心业务规则）。

### 2.5 N层/多层架构

现代大型系统常见的多层划分：

```
客户端层（Browser/App）
    ↕
接入层（CDN, DNS, 反向代理）
    ↕
网关层（API Gateway）
    ↕
应用服务层（Microservices）
    ↕
领域服务层（Domain Services）
    ↕
基础设施层（Cache, MQ, DB, Search）
```

## 3. 表示层设计（第二版重点章节）

### 3.1 MVC、MVP、MVVM模式

**常考：MVC 与 三层架构 的区别与联系**

| 维度 | MVC模式 | 三层架构 |
|------|---------|---------|
| **粒度** | 表示层内部的设计模式 | 整个系统的宏观架构 |
| **关注点** | 用户交互分离（输入→处理→输出） | 系统职责水平切分 |
| **层级** | 属于表示层内部 | 跨整个系统 |
| **M/Model** | UI状态数据 | — |
| **V/View** | 界面展示 | — |
| **C/Controller** | 用户输入处理 | — |

**关键结论**：MVC是表示层内部模式，三层是整个系统的架构。两者不矛盾，MVC通常在表示层中使用。

**MVC / MVP / MVVM 对比**：

| 模式 | V ↔ M 通信 | 适用场景 | 典型框架 |
|------|-----------|---------|---------|
| **MVC** | Controller 协调 | 传统Web应用 | Spring MVC, ASP.NET MVC |
| **MVP** | Presenter 双向绑定 | 复杂UI交互 | GWT, early Android |
| **MVVM** | 数据绑定（自动同步） | 响应式前端 | Vue, React+Hooks, Angular |

### 3.2 表示层设计模式

| 模式 | 说明 | 角色 |
|------|------|------|
| **前端控制器（Front Controller）** | 统一入口处理所有请求 | DispatcherServlet, Nginx |
| **页面控制器（Page Controller）** | 每个页面有一个控制器 | 传统PHP, ASP.NET Page |
| **视图助手（View Helper）** | 封装视图逻辑的辅助类 | JSP标签库, Helpers |
| **组合视图（Composite View）** | 页面由多个子视图组成 | 模板引擎（Tiles, Layout） |
| **拦截过滤器（Intercepting Filter）** | 请求处理链中的可插拔过滤器 | Servlet Filter, Middleware |

### 3.3 表示层主流技术

| 技术 | 平台 | 说明 |
|------|------|------|
| **Servlet/JSP** | Java EE | 最基础，Servlet处理逻辑，JSP展示 |
| **JSF（JavaServer Faces）** | Java EE | 基于组件的MVC框架，事件驱动 |
| **Spring MVC** | Spring | 最流行的Java Web框架 |
| **Struts** | Java EE | 早期MVC框架，逐渐被Spring MVC替代 |
| **ASP.NET MVC** | .NET | 微软MVC实现 |
| **React / Vue / Angular** | 前端 | SPA框架，客户端MVC/MVVM |

## 4. 业务逻辑层设计（第二版重点章节）

### 4.1 业务逻辑层设计模式

| 模式 | 说明 | 适用场景 | 示例 |
|------|------|---------|------|
| **事务脚本（Transaction Script）** | 一个过程处理一个请求，直接执行SQL | 简单业务逻辑 | 简单CRUD系统 |
| **表模块（Table Module）** | 一个对象代表整个数据表，包含操作该表的所有方法 | 数据集操作 | ADO.NET DataSet |
| **领域模型（Domain Model）** | 用对象模型表达业务规则，包含数据和行为 | 复杂业务规则 | DDD, Hibernate实体 |
| **服务层（Service Layer）** | 在领域模型之上建立统一的服务接口层 | 需要多种调用方式 | Spring @Service |

**四种模式的对比**：

| 维度 | 事务脚本 | 表模块 | 领域模型 | 服务层 |
|------|---------|--------|---------|--------|
| 复杂度 | 低 | 中 | 高 | 中-高 |
| 代码量 | 少 | 中 | 多 | 多（+接口） |
| 业务表达力 | 弱 | 中 | 强 | 强 |
| 可维护性 | 差 | 中 | 好 | 好 |
| 与ORM配合 | 不需要 | RecordSet | 天然匹配 | JPA/Hibernate |

### 4.2 业务逻辑层技术选型

| 技术 | 说明 | 特点 |
|------|------|------|
| **EJB（Enterprise JavaBean）** | Java EE重容器方案 | 分布式事务、安全、集群，但重 |
| **Spring Bean** | 轻量级方案 | IoC容器管理，AOP支持，流行 |
| **COM+/MTS** | .NET平台 | Windows事务服务 |
| **工作流引擎** | 流程编排 | Activiti, Camunda, Flowable |

## 5. 数据访问层设计（第二版重点章节）

### 5.1 数据访问层设计模式

| 模式 | 说明 | 示例 |
|------|------|------|
| **DAO（Data Access Object）** | 封装数据源访问，隔离业务层与持久化细节 | UserDao, OrderDao |
| **Repository** | DDD风格的持久化抽象，以集合语义操作 | OrderRepository |
| **Data Mapper** | 对象与数据库表之间的映射层 | MyBatis Mapper, Entity Framework |
| **Active Record** | 数据对象自身包含CRUD方法 | Laravel Eloquent, Rails ActiveRecord |
| **Table Data Gateway** | 一个对象代表一个表，包含SQL | Spring JdbcTemplate |
| **Row Data Gateway** | 一个对象代表一行数据 | 原始JDBC RowSet |

**DAO 与 Repository 的区别**：

| 维度 | DAO | Repository |
|------|-----|-----------|
| 抽象级别 | 数据表级（贴近SQL） | 聚合根级（贴近领域） |
| 所属架构 | 三层架构 | DDD四层架构 |
| 方法语义 | CRUD（insert/update/delete） | 集合操作（add/remove/find） |
| 返回值 | 数据对象 | 领域对象 |

### 5.2 ORM（对象关系映射）

**ORM原理**：将关系数据库的表映射为程序中的对象，实现对象与关系的自动转换。

| ORM框架 | 平台 | 特点 |
|---------|------|------|
| **Hibernate** | Java | 全自动ORM，JPA标准实现 |
| **MyBatis** | Java | 半自动，SQL可控，灵活度高 |
| **JPA** | Java | Java持久化API标准 |
| **Entity Framework** | .NET | 微软ORM方案 |
| **SQLAlchemy** | Python | Python最流行的ORM |

### 5.3 数据库连接池

**为什么需要连接池**：数据库连接创建/销毁成本高，连接池复用连接，减少开销。

| 连接池 | 平台 |
|--------|------|
| **HikariCP** | Java（Spring Boot默认） |
| **Druid** | Java（阿里，监控功能强） |
| **DBCP/C3P0** | Java（早期） |
| **Proxool** | Java |

### 5.4 数据架构规划与设计

| 维度 | 内容 |
|------|------|
| **读写分离** | 主库写、从库读，提升读性能 |
| **分库分表** | 垂直拆分（按业务） / 水平拆分（按数据行） |
| **数据缓存** | Redis/本地缓存加速热数据 |
| **NoSQL互补** | RDB存核心数据，NoSQL存海量/非结构化数据 |

## 6. 层次架构设计原则

### 6.1 核心设计原则

| 原则 | 说明 |
|------|------|
| **单向依赖** | 上层依赖下层，下层不知道上层存在 |
| **接口隔离** | 每层只暴露必要接口，隐藏内部实现 |
| **层内高内聚** | 同层内的组件功能紧密相关 |
| **层间松耦合** | 通过接口/抽象类而非具体实现通信 |
| **迪米特法则** | 跨越层时使用DTO/VO转换，不让数据对象跨越多层 |
| **依赖倒置** | 高层定义接口，低层实现接口（IoC/DI） |

### 6.2 严格分层 vs 松散分层

| 维度 | 严格分层 | 松散分层 |
|------|---------|---------|
| 调用规则 | 只能调用相邻下层 | 可跨层调用 |
| 优点 | 依赖关系清晰、替换层容易 | 减少中间层传递开销 |
| 缺点 | 可能产生大量委托代码 | 依赖关系复杂化 |
| 典型应用 | 网络协议栈（OSI模型） | 企业应用（Spring多层） |

### 6.3 层次间的数据传递

| 模式 | 说明 | 适用 |
|------|------|------|
| **直接传递实体** | 持久层实体直接返回给表示层 | 简单系统（不推荐） |
| **DTO/VO传递** | 每层定义自己的数据传输对象 | 企业级系统 |
| **命令/查询分离** | CQRS方式，读写数据模型分离 | 复杂查询+更新场景 |

**DTO vs VO vs Entity**：

| 对象类型 | 层次 | 用途 |
|----------|------|------|
| **Entity** | 持久层 | 与数据库表映射 |
| **DTO** | 跨层传输 | 在层间传递数据 |
| **VO** | 表示层 | 页面展示所需数据 |
| **BO** | 业务层 | 封装业务逻辑的对象 |
| **PO** | 持久层 | 持久化对象（= Entity） |
| **POJO** | 通用 | 普通Java对象，不依赖框架 |

## 7. 中间件与层次架构（第二版重点章节）

### 7.1 中间件的定义与分类

**中间件（Middleware）**：位于操作系统与应用之间的系统软件，为分布式应用提供标准化的服务。

**按功能分类**：

| 类型 | 功能 | 示例 |
|------|------|------|
| **远程过程调用（RPC）中间件** | 远程方法调用 | gRPC, Dubbo, Thrift |
| **消息中间件（MOM）** | 异步消息传递 | Kafka, RabbitMQ, RocketMQ |
| **数据库中间件** | 分库分表、读写分离 | ShardingSphere, MyCat |
| **事务中间件** | 分布式事务 | Seata, Atomikos |
| **Web中间件/应用服务器** | Web容器、应用托管 | Tomcat, WebLogic, JBoss |
| **缓存中间件** | 分布式缓存 | Redis, Memcached |

### 7.2 中间件在层次中的位置

```
表示层（Tomcat/Jetty/Nginx）
    ↕
业务逻辑层（Spring容器/EJB容器）
    ↕
中间件层（MQ/缓存/事务/RPC）
    ↕
数据访问层（数据库中间件/ORM）
    ↕
数据层（MySQL/Redis/ES）
```

### 7.3 应用服务器 vs Web服务器

| 类型 | 功能 | 示例 |
|------|------|------|
| **Web服务器** | 处理HTTP请求，静态资源 | Apache HTTPD, Nginx |
| **Servlet容器** | 运行Servlet/JSP | Tomcat, Jetty |
| **应用服务器** | 完整Java EE规范（EJB, JMS等） | WebLogic, WebSphere, JBoss/WildFly |

## 8. 领域驱动设计（DDD）分层

### 8.1 DDD四层架构详解

| 层 | 职责 | 依赖规则 | 关键概念 |
|------|------|---------|---------|
| **接口层（Interfaces）** | 处理外部请求，协议适配 | 依赖应用层和领域层 | Controller, DTO, Facade |
| **应用层（Application）** | 任务编排、事务控制、权限 | 依赖领域层和基础设施层 | Application Service, Unit of Work |
| **领域层（Domain）** | 核心业务规则（心脏层） | **不依赖任何层** | Entity, Value Object, Aggregate, Domain Service, Repository接口 |
| **基础设施层（Infrastructure）** | 技术实现 | 实现领域层定义的接口 | Repository实现, Message, Cache |

**DDD分层核心原则**：**领域层不依赖任何外部层**，所有外部依赖通过接口倒置注入。

### 8.2 依赖倒置在分层中的应用

```
传统分层（每层依赖下一层）：
表示层 → 业务层 → 数据层

依赖倒置分层：
表示层 → 业务层 ← 数据层（实现业务层定义的接口）
           ↑
      定义接口(IPaymentRepository)
      数据层实现(MySqlPaymentRepository)
```

### 8.3 DDD战术设计关键概念

| 概念 | 说明 |
|------|------|
| **实体（Entity）** | 有唯一标识，可变的对象 |
| **值对象（Value Object）** | 无标识，不可变，通过属性值来识别 |
| **聚合（Aggregate）** | 一组相关对象的集合，有聚合根 |
| **聚合根（Aggregate Root）** | 聚合的入口，外部只通过聚合根访问聚合 |
| **领域服务（Domain Service）** | 不属于任何实体/值对象的领域操作 |
| **领域事件（Domain Event）** | 领域中发生的有意义事件 |
| **资源库（Repository）** | 聚合的持久化抽象，像集合一样操作 |
| **工厂（Factory）** | 复杂对象的创建（组装聚合） |
| **限界上下文（Bounded Context）** | 领域模型的边界，一个BC内模型统一 |

## 9. 层次架构与其他架构风格的关系

### 9.1 六边形架构（端口与适配器）

```
          ┌──────────────────────┐
  HTTP →  │  端口(Port)           │  → DB
  MQ   →  │       ↓              │  → Cache
  RPC  →  │   应用核心(领域)       │  → Search
  UI   →  │       ↑              │  → External API
          │  端口(Port)           │
          └──────────────────────┘
```

**六边形架构精髓**：业务逻辑在中心，所有外部依赖都是平等的"适配器"。

### 9.2 洋葱架构（Onion Architecture）

```
   ┌────────────────────┐
   │   基础设施           │
   │  ┌──────────────┐  │
   │  │  应用服务      │  │
   │  │ ┌──────────┐ │  │
   │  │ │ 领域模型  │ │  │
   │  │ │ (核心)    │ │  │
   │  │ └──────────┘ │  │
   │  └──────────────┘  │
   └────────────────────┘
   依赖方向：外层 → 内层（永远指向核心）
```

### 9.3 整洁架构（Clean Architecture）

Robert C. Martin 提出的四层同心圆：

```
  实体层（Enterprise Business Rules）  ← 最核心
    ↖
  用例层（Application Business Rules）
    ↖
  接口适配层（Interface Adapters）
    ↖
  框架与驱动层（Frameworks & Drivers）  ← 最外层
```

| 原则 | 说明 |
|------|------|
| **依赖规则** | 依赖只能从外向内，内层不知道外层 |
| **抽象规则** | 越内层越抽象，越外层越具体 |
| **跨越边界** | 通过接口实现依赖倒置 |

### 9.4 层次 + 微服务

每个微服务内部采用分层架构（小三层/小四层），微服务之间通过API/消息通信。

### 9.5 BFF（Backend for Frontend）模式

```
[移动端App] → BFF-Mobile → [订单服务]
[Web前端]   → BFF-Web    → [用户服务]
[第三方]    → BFF-Partner → [商品服务]
```

**BFF解决**：不同前端对数据格式/粒度要求不同，BFF为每种前端提供专属后端。

### 9.6 层次架构的反模式

| 反模式 | 现象 | 后果 |
|--------|------|------|
| **跨层污染** | 表示层直接操作数据库 | 业务逻辑散落各处，难以维护 |
| **逆向依赖** | 下层调用上层 | 循环依赖、部署困难 |
| **过度分层** | 简单的CRUD穿越5-6层 | 大量重复委托代码 |
| **泄漏的抽象** | 底层技术细节穿透到上层 | 换技术栈改动巨大 |
| **上帝层** | 某一层包含过多职责 | 层定义模糊，回到单体 |

## 10. 层次架构中的横切关注点

### 10.1 什么是横切关注点

**横切关注点（Cross-cutting Concerns）**：同时出现在多层中的功能，如日志、安全、事务、缓存。

### 10.2 AOP（面向切面编程）

```
[Controller]  [Service]  [Repository]  [External Call]
     ↑            ↑           ↑               ↑
     └────────────┴───────────┴───────────────┘
                     │
              [AOP切面层]
          日志 | 事务 | 安全 | 性能监控
```

**AOP关键概念**：

| 概念 | 说明 |
|------|------|
| **切面（Aspect）** | 横切关注点的模块化，包含通知+切点 |
| **通知（Advice）** | 切面在特定切点执行的动作（Before/After/Around） |
| **切点（Pointcut）** | 匹配连接点的表达式（何处执行） |
| **连接点（Join Point）** | 程序执行中的点（方法调用、异常抛出） |
| **织入（Weaving）** | 将切面应用到目标对象的过程 |

## 11. 层次架构的测试策略

### 11.1 测试金字塔

```
        ┌─────┐
        │ E2E │  ← 少量，全链路验证
       ┌┴─────┴┐
       │ 集成测试│  ← 中等数量，层间交互验证
      ┌┴───────┴┐

      └─────────┘
```

### 11.2 针对各层的测试方法

| 层 | 测试类型 | 工具 |
|------|---------|------|

- **单层隔离**：Mock下层，专注测试本层逻辑

## 12. 层次架构的性能优化

### 12.1 层级穿透优化

| 策略 | 说明 |
|------|------|
| **聚合查询** | 一次调用返回完整数据，减少往返（避免N+1问题） |
| **批量操作** | 批量增删改代替逐条操作 |
| **异步处理** | 非实时路径异步化，减少层次间的同步等待 |
| **缓存各层** | 浏览器缓存→CDN→应用缓存→分布式缓存→数据库 |

### 12.2 层间通信优化

- **DTO精简**：只传递必要字段，不用全量Entity
- **对象映射**（MapStruct/ModelMapper）：避免手动逐字段复制
- **合并查询**：将多个服务调用合并为一次请求（GraphQL/BFF模式）
- **延迟加载**：按需加载关联数据

## 13. 第二版新增/强化考点速查

### 13.1 三层架构职责速记

```
表示层：处理用户交互（Controller/View）
业务层：处理业务规则（Service）
数据层：处理数据持久化（Repository/DAO）
```

### 13.2 分层设计关键决策

| 决策 | 选项 | 权衡 |
|------|------|------|
| 分层数 | 2/3/4/N层 | 层数多→更灵活但更复杂 |
| 分层严格度 | 严格/松散 | 严格→易替换，松散→少委托 |
| 数据传递 | Entity/DTO/VO | Entity→简单，DTO→解耦好 |
| 依赖方向 | 正向/倒置 | 倒置→领域层纯净，但增加接口量 |

### 13.3 DDD分层关键一句话

**领域层是心脏，不依赖任何外部——所有依赖通过接口倒置注入领域层。**

### 13.4 MVC vs 三层架构（高频考点）

| 问题 | 答案 |
|------|------|
| MVC属于哪层？ | **表示层**内部的设计模式 |
| MVC的每个字母在三层中对应哪里？ | 不一一对应！MVC全部在表示层 |
| 三层架构的表示层可以用什么？ | MVC / MVP / MVVM 都行 |

### 13.5 业务逻辑层设计模式选择口诀

```
简单CRUD → 事务脚本
表格操作 → 表模块
复杂业务 → 领域模型
多协议调用 → 加服务层
```

### 13.6 数据访问层模式选择

```
简单系统 → DAO + JDBC
中等系统 → DAO + MyBatis
复杂领域 → Repository + JPA/Hibernate
DDD项目 → Repository（基于聚合）
```

### 13.7 常考中间件在层次中的角色

| 中间件 | 所在层次 | 作用 |
|--------|---------|------|
| **Tomcat** | 表示层（Web容器） | 运行Servlet/JSP |
| **Nginx** | 表示层（反向代理） | 负载均衡、静态资源 |
| **Spring容器** | 业务层 | IoC管理、AOP |
| **RabbitMQ/Kafka** | 业务-数据之间 | 削峰、解耦、异步 |
| **Redis** | 跨层（缓存层） | 数据缓存、Session共享 |
| **MyBatis/Hibernate** | 数据访问层 | ORM映射 |
| **ShardingSphere** | 数据访问层 | 分库分表 |

## 14. 真题高频考点速记

| 考点 | 关键点 |
|------|--------|
| 三层架构的层次和职责 | 表示层（交互）、业务层（规则）、数据层（持久化） |

| ORM | 对象-关系映射，解决阻抗不匹配 |
| 连接池 | 复用数据库连接，避免反复创建/销毁 |
| 中间件分类 | RPC、消息、数据、事务、Web |
| AOP | 横切关注点分离（日志、事务、安全） |
| 反模式 | 跨层污染、逆向依赖、过度分层 |
