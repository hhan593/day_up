# 16 — 层次式架构设计理论与实践

## 1. 层次式架构概述

### 1.1 定义与核心思想

**层次式架构（Layered Architecture）**：将系统按照水平方向切分为若干层，每层承担特定职责，上层依赖下层，下层对上层透明。

**核心思想**：
- **关注点分离**：每层只关注自己的职责
- **单向依赖**：上层依赖下层（严格分层）或上层允许跨层（松散分层）
- **接口抽象**：层间通过接口交互，隐藏实现细节
- **可替换性**：任一层可被替换，只要接口不变

**与 [05-软件架构核心概念.md](05-软件架构核心概念.md) 3.2.3 节互补，此为系统架构设计师"第二版"完整章节。**

### 1.2 层次架构的优缺点

| 优点 | 缺点 |
|------|------|
| 关注点分离，降低复杂度 | 性能开销（层层传递） |
| 标准化层间接口，利于团队并行开发 | 层数确定困难 |
| 可替换性（更换某一层不影响其他） | 级联修改风险 |
| 可测试性（层可独立测试） | 简单系统可能过度设计 |
| 易于理解和维护 | 不适用于所有场景（如高吞吐数据流） |

## 2. 经典分层架构模式

### 2.1 二层C/S架构（Client/Server）

```
┌─────────────────┐         ┌───────────────┐
│   Client（客户端） │ ←──→   │  Server（服务器）│
│   表示逻辑+业务逻辑 │         │  数据管理       │
└─────────────────┘         └───────────────┘
```

**胖客户端 vs 瘦客户端**：

| 类型 | 客户端职责 | 服务器职责 | 适用 |
|------|-----------|-----------|------|
| **胖客户端** | 表示+业务逻辑 | 数据管理 | 桌面应用、内部系统 |
| **瘦客户端** | 仅表示 | 业务逻辑+数据管理 | 早期Web |

**C/S架构问题**：客户端直接连接数据库，安装维护成本高，安全性差。

### 2.2 三层B/S架构（Browser/Server）

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  表示层        │ →  │  业务逻辑层    │ →  │  数据访问层    │
│  (Presentation)│    │  (Business)   │    │  (Data)       │
└──────────────┘    └──────────────┘    └──────────────┘
   用户界面             业务规则             数据库/文件
```

**三层职责**：

| 层 | 别称 | 职责 | 技术 |
|------|------|------|------|
| **表示层** | UI层/Web层 | 用户交互，数据展示和输入 | HTML/CSS/JS, JSP, Thymeleaf, React/Vue |
| **业务逻辑层** | BLL/服务层 | 核心业务规则、流程控制 | Java/Spring, C#/.NET, Python/Django |
| **数据访问层** | DAL/持久层 | 数据持久化、CRUD操作 | JDBC/JPA/MyBatis, ADO.NET, ORM |

**三层架构优点**：逻辑清晰分层、可并行开发（定义好接口后）、业务逻辑可被多个前端复用。

### 2.3 四层架构（DDD 风格）

```
┌──────────────┐
│  用户接口层     │  ← Controller, REST API, RPC Interface
│  (Interface)  │
├──────────────┤
│  应用层        │  ← 应用服务、事务管理、权限校验
│  (Application)│
├──────────────┤
│  领域层        │  ← 领域模型、领域服务、业务规则
│  (Domain)     │
├──────────────┤
│  基础设施层     │  ← 持久化、消息、日志、工具
│  (Infrastructure)│
└──────────────┘
```

**四层与三层区别**：将三层中的"业务逻辑层"进一步拆分为应用层（编排、事务）和领域层（核心业务规则）。

### 2.4 N层/多 层架构

现代大型系统常见的多 层划分：

```
客户端层（Browser/App）
    ↕
接入层（CDN, DNS, 反向代理）
    ↕
网关层（API Gateway）
    ↕
应用服务层（Microservices）
    ↕
领域服务层（Domain Services）
    ↕
基础设施层（Cache, MQ, DB, Search）
```

## 3. 层次架构设计原则

### 3.1 核心设计原则

| 原则 | 说明 |
|------|------|
| **单向依赖** | 上层依赖下层，下层不知道上层存在 |
| **接口隔离** | 每层只暴露必要接口，隐藏内部实现 |
| **层内高内聚** | 同层内的组件功能紧密相关 |
| **层间松耦合** | 通过接口/抽象类而非具体实现通信 |
| **迪米特法则** | 跨越层时使用DTO/VO转换，不让数据对象跨越多层 |
| **依赖倒置** | 高层定义接口，低层实现接口（IoC/DI） |

### 3.2 严格分层 vs 松散分层

| 维度 | 严格分层 | 松散分层 |
|------|---------|---------|
| 调用规则 | 只能调用相邻下层 | 可跨层调用 |
| 优点 | 依赖关系清晰、替换层容易 | 减少中间层传递开销 |
| 缺点 | 可能产生大量委托代码 | 依赖关系复杂化 |
| 典型应用 | 网络协议栈（OSI模型） | 企业应用（Spring多层） |

### 3.3 层次间的数据传递

| 模式 | 说明 | 适用 |
|------|------|------|
| **直接传递实体** | 持久层实体直接返回给表示层 | 简单系统（不推荐） |
| **DTO/VO传递** | 每层定义自己的数据传输对象 | 企业级系统 |
| **命令/查询分离** | CQRS方式，读写数据模型分离 | 复杂查询+更新场景 |

**DTO（Data Transfer Object）** vs **VO（View Object）** vs **Entity**：

| 对象类型 | 层次 | 用途 |
|----------|------|------|
| Entity | 持久层 | 与数据库表映射 |
| DTO | 跨层传输 | 在层间传递数据 |
| VO | 表示层 | 页面展示所需数据 |

## 4. 主流平台的层次架构实现

### 4.1 Java EE / Spring 分层

```
Controller（@Controller/@RestController）  ← 表示层
      ↓
Service（@Service）                       ← 业务逻辑层
      ↓
Repository/Dao（@Repository）             ← 数据访问层
      ↓
Entity/Model                              ← 数据模型
```

**Spring 分层关键注解与概念**：
| 层 | 注解 | 职责 |
|------|------|------|
| 表示层 | @Controller, @RestController | HTTP请求处理、参数校验 |
| 业务层 | @Service, @Transactional | 业务编排、事务管理 |
| 数据层 | @Repository, @Mapper | 数据库操作封装 |
| 横切 | @Aspect, @Component | AOP切面（日志/安全/事务） |

**Spring MVC 请求流程**：
```
请求 → DispatcherServlet → HandlerMapping → Controller
                                        → Interceptor
     ← ViewResolver ← ModelAndView ← 返回
```

### 4.2 .NET 平台分层

```
表示层：ASP.NET MVC / Blazor
    ↓
业务层：Class Library / WCF Service
    ↓
数据层：Entity Framework / ADO.NET
    ↓
数据库：SQL Server
```

### 4.3 前端分层架构

现代前端也采用分层架构：

```
组件层（React/Vue Components）     ← 表示
    ↕
状态管理层（Redux/Vuex/Pinia）     ← 状态
    ↕
服务层（API Service）              ← 通信
    ↕
工具层（Utils/Helpers）            ← 基础设施
```

## 5. 领域驱动设计（DDD）分层

### 5.1 DDD四层架构详解

| 层 | 职责 | 依赖规则 | 关键概念 |
|------|------|---------|---------|
| **接口层（Interfaces）** | 处理外部请求，协议适配 | 依赖应用层和领域层 | Controller, DTO, Facade |
| **应用层（Application）** | 任务编排、事务控制、权限 | 依赖领域层和基础设施层 | Application Service, Unit of Work |
| **领域层（Domain）** | 核心业务规则（心脏层） | **不依赖任何层** | Entity, Value Object, Aggregate, Domain Service, Repository接口 |
| **基础设施层（Infrastructure）** | 技术实现 | 实现领域层定义的接口 | Repository实现, Message, Cache |

**DDD分层核心原则**：**领域层不依赖任何外部层**，所有外部依赖通过接口倒置注入。

### 5.2 依赖倒置在分层中的应用

```
传统分层（每层依赖下一层）：
表示层 → 业务层 → 数据层

依赖倒置分层：
表示层 → 业务层 ← 数据层（实现业务层定义的接口）
           ↑
      定义接口(IPaymentRepository)
      数据层实现(MySqlPaymentRepository)
```

## 6. 层次架构与其他架构风格的关系

### 6.1 层次 + 微服务

每个微服务内部采用分层架构（小三层/小四层），微服务之间通过API/消息通信。

### 6.2 层次 + 事件驱动

层次架构负责静态结构，事件驱动负责动态交互。

### 6.3 层次 + SOA

SOA的分层参考架构本身就是层次式架构与面向服务结合（见[15-面向服务架构](15-面向服务架构设计理论与实践.md)第3节）。

### 6.4 层次架构的反模式

| 反模式 | 现象 | 后果 |
|--------|------|------|
| **跨层污染** | 表示层直接操作数据库 | 业务逻辑散落各处，难以维护 |
| **逆向依赖** | 下层调用上层 | 循环依赖、部署困难 |
| **过度分层** | 简单的CRUD穿越5-6层 | 大量重复委托代码 |
| **泄漏的抽象** | 底层技术细节穿透到上层 | 换技术栈改动巨大 |
| **上帝层** | 某一层包含过多职责 | 层定义模糊，回到单体 |

## 7. 层次架构的性能优化

### 7.1 层级穿透优化

| 策略 | 说明 |
|------|------|
| **聚合查询** | 一次调用返回完整数据，减少往返（避免N+1问题） |
| **批量操作** | 批量增删改代替逐条操作 |
| **异步处理** | 非实时路径异步化，减少层次间的同步等待 |
| **缓存各层** | 浏览器缓存→CDN→应用缓存→分布式缓存→数据库 |

### 7.2 层间通信优化

- DTO精简：只传递必要字段，不用全量Entity
- 对象映射（MapStruct/ModelMapper）：避免手动逐字段复制
- 合并查询：将多个服务调用合并为一次请求（GraphQL/BFF模式）

## 8. 常考考点速查

### 8.1 三层架构职责速记

```
表示层：处理用户交互（Controller/View）
业务层：处理业务规则（Service）
数据层：处理数据持久化（Repository/DAO）
```

### 8.2 分层设计关键决策

| 决策 | 选项 | 权衡 |
|------|------|------|
| 分层数 | 2/3/4/N层 | 层数多→更灵活但更复杂 |
| 分层严格度 | 严格/松散 | 严格→易替换，松散→少委托 |
| 数据传递 | Entity/DTO/VO | Entity→简单，DTO→解耦好 |
| 依赖方向 | 正向/倒置 | 倒置→领域层纯净，但增加接口量 |

### 8.3 DDD分层关键一句话

**领域层是心脏，不依赖任何外部——所有依赖通过接口倒置注入领域层。**
