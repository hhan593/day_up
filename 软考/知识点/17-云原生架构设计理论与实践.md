# 17 — 云原生架构设计理论与实践

> 与 [08-微服务与云原生架构.md](08-微服务与云原生架构.md) 互补，08侧重技术实现，17侧重**设计方法论与架构理论**

## 1. 云原生架构设计基础

### 1.1 云原生的定义与核心理念

**CNCF 云原生定义**：云原生技术有利于各组织在公有云、私有云和混合云等动态环境中，构建和运行可弹性扩展的应用。

**云原生设计四大核心理念**：

| 理念 | 说明 |
|------|------|
| **不可变基础设施** | 服务器部署后不再修改，变更通过替换实例实现 |
| **声明式设计** | 描述期望状态而非执行步骤（Kubernetes YAML） |
| **自愈与韧性** | 系统自动检测和恢复故障（Reconciliation Loop） |
| **弹性伸缩** | 根据负载自动调整资源（HPA/VPA/KEDA） |

**云原生与传统的本质差异**：

| 维度 | 传统架构 | 云原生架构 |
|------|---------|-----------|
| 设计假设 | 基础设施可靠 | 基础设施不可靠（Design for Failure） |
| 扩展方式 | 垂直扩展（升级硬件） | 水平扩展（增加实例） |
| 交付方式 | 手工部署、低频 | 自动化CI/CD、高频 |
| 状态管理 | 有状态（服务器即宠物） | 无状态（服务器即牲畜） |
| 配置管理 | 配置文件硬编码 | 环境变量+配置中心 |
| 故障处理 | 避免故障 | 容忍故障、快速恢复 |

**宠物 vs 牲畜比喻**：
- **宠物模式**：服务器有名字，坏了要精心修复 → 传统运维
- **牲畜模式**：服务器有编号，坏了直接替换 → 云原生

## 2. 云原生架构设计原则

### 2.1 核心设计原则

| 原则 | 说明 | 实践 |
|------|------|------|
| **韧性设计（Resilience）** | 系统能在部分组件故障时继续运行 | 重试、熔断、降级、超时、舱壁 |
| **弹性设计（Elasticity）** | 根据负载自动扩缩 | HPA（水平）、VPA（垂直）、KEDA |
| **可观测设计（Observability）** | 从外部输出推断内部状态 | Metrics + Traces + Logs 三支柱 |
| **自动化设计（Automation）** | 一切皆自动化，减少人工操作 | CI/CD、GitOps、IaC |
| **安全设计（Security）** | 内建安全，DevSecOps | 零信任、最小权限、mTLS |
| **无状态设计** | 计算节点无状态，状态外置 | Session存Redis、文件存对象存储 |

### 2.2 云原生设计模式

| 模式 | 说明 | 解决什么问题 |
|------|------|-------------|
| **Sidecar** | 部署辅助容器与应用容器同一Pod | 日志收集(Istio-proxy)、配置刷新 |
| **Ambassador** | 代理容器代表应用连接外部服务 | 连接池管理、TLS卸载 |
| **Adapter** | 转换应用输出为标准格式 | 日志标准化、监控标准化 |
| **Circuit Breaker** | 熔断不可用服务，快速失败 | 防止级联故障 |
| **Bulkhead** | 隔离资源，限制故障范围 | 防止某服务耗尽所有线程 |
| **Leader Election** | 多个副本中选出一个Leader执行特殊任务 | 定时任务避免重复执行 |
| **Saga** | 分布式事务的补偿模式 | 跨服务数据一致 |
| **CQRS** | 读写分离数据模型 | 读写不同的性能优化策略 |
| **Event Sourcing** | 状态由事件序列恢复 | 完整审计、时间旅行 |

| 设计维度 | 对应要素 | 设计意义 |
|----------|---------|---------|

## 3. 云原生架构设计方法

### 3.1 应用分解设计

**分解模式**：

| 模式 | 说明 | 适用 |
|------|------|------|
| **按业务能力分解** | 按限界上下文拆分 | 最常用 |
| **按子域分解** | 核心域/支撑域/通用域差异化设计 | DDD驱动 |
| **按交易模式分解** | 按读写比例/一致性要求拆分 | 性能优先 |
| **按变更速率分解** | 将频繁变更部分独立 | 演进优先 |
| **Strangler Fig分解** | 从单体逐步抽离 | 遗留系统迁移 |

**分解粒度判断标准**：

| 适中的服务 | 过大的服务 | 过小的服务 |
|-----------|-----------|-----------|
| 2 Pizza Team可维护 | 多团队协调修改 | 单个函数即服务 |
| 独立部署且有意义 | 部署需多方同步 | 修改需联动N个服务 |
| 数据独立 | 共享数据库 | 一个API即一个服务 |

### 3.2 服务通信设计

| 通信模式 | 同步性 | 适用 | 挑战 |
|----------|--------|------|------|
| **请求-响应（REST/gRPC）** | 同步 | 查询、命令 | 级联延迟、可用性耦合 |
| **异步消息** | 异步 | 事件通知 | 最终一致性、消息顺序 |
| **请求-异步回调** | 混合 | 长任务 | 回调管理复杂度 |
| **发布-订阅** | 异步 | 一对多通知 | 事件风暴、调试困难 |
| **CQRS** | 混合 | 读写分离场景 | 数据延迟 |

**通信协议选型决策**：
```
需要浏览器直接调用？
├── 是 → REST/GraphQL (HTTP)
└── 否 → 内部服务间通信
    ├── 需要高性能+强类型 → gRPC (Protobuf)
    ├── 需要解耦+削峰 → 消息队列
    └── 通用场景 → REST + JSON
```

### 3.3 数据架构设计

| 模式 | 说明 | 挑战 |
|------|------|------|
| **数据主权** | 每服务独立数据库 | 跨服务数据查询 |
| **Saga** | 分布式事务的补偿模式 | 实现复杂度 |
| **CQRS** | 读写分离 | 最终一致性延迟 |
| **事件溯源** | 事件作为数据源 | 事件模型设计复杂 |
| **API组合** | 在API层拼装多服务数据 | 服务依赖和延迟 |
| **数据库中间件** | Sharding-Proxy/ShardingSphere | 运维复杂度 |

### 3.4 弹性与韧性设计

**弹性伸缩层次**：

| 层 | 手段 | 技术 |
|------|------|------|
| 实例层 | 水平扩缩 | HPA, KEDA |
| 集群层 | 节点扩缩 | Cluster Autoscaler |
| 资源层 | 预留实例/竞价实例 | Spot Instance |
| 地理位置层 | CDN、多地域 | Global Load Balancer |

**韧性设计模式**：

| 模式 | 说明 |
|------|------|
| **超时（Timeout）** | 等待响应的最大时间 |
| **重试（Retry）** | 临时故障后重新请求（需幂等） |
| **熔断器（Circuit Breaker）** | 故障积累达阈值后快速失败 |
| **舱壁（Bulkhead）** | 隔离线程池/连接池 |
| **限流（Rate Limiting）** | 控制请求速率 |
| **降级（Degradation）** | 关闭非核心功能保核心 |
| **健康检查** | 自动摘除不健康节点 |

## 4. 云原生架构的底层设计支撑

### 4.1 GitOps 设计

**GitOps**：以 Git 作为唯一真实源（Single Source of Truth），通过声明式配置管理基础设施和应用部署。

```
开发者 Push → Git（声明式配置）
                │
                ↓
       GitOps Controller（ArgoCD/FluxCD）
                │
                ↓ watch & sync
       Kubernetes 集群（实际状态 → 期望状态）
```

**GitOps 核心理念**：环境配置 = Git仓库中的文件；部署 = Controller让集群匹配Git中的配置。

### 4.2 不可变基础设施设计

传统运维 = 配置管理工具（Ansible/Puppet）持续修改服务器状态（配置漂移风险）
云原生 = 替换实例，从不修改（Immutable Infrastructure）

**实现路径**：
1. 镜像（打包=不可变）→ 2. 实例（创建=可销毁）→ 3. 替换（更新=创建新+销毁旧）

### 4.3 声明式API与控制循环

```
声明式：YAML描述期望状态
    ↓
Kubernetes Controller：
  当前状态 ≠ 期望状态？ → 是 → 执行操作（调谐/Reconcile）
                        → 否 → 什么都不做
```

**控制循环（Reconciliation Loop）**：Observe → Diff → Act 的无限循环，是 Kubernetes 自愈能力的核心。

## 5. 云原生安全架构设计

### 5.1 4C安全模型

```
Cloud（云基础设施安全）
  ├── Cluster（集群安全）
  │     ├── Container（容器安全）
  │     │     └── Code（代码安全）
```

### 5.2 零信任安全模型

| 原则 | 说明 |
|------|------|
| **永不信任，始终验证** | 每次请求都验证身份、权限和风险 |
| **最小权限** | 仅授予当前操作所需的最小权限 |
| **微隔离** | 东西向流量也需认证授权 |
| **持续验证** | 实时风险评分和会话监控 |

**技术实现**：
- mTLS（双向TLS）：服务间通信加密+身份认证
- IAM：细粒度身份与访问管理
- Policy as Code（OPA/Gatekeeper）：策略即代码

### 5.3 安全左移（Shift Left）

在开发生命周期早 期嵌入安全检查：

```
威胁建模 → 代码安全扫描 → 镜像漏洞扫描 → 集群合规检查 → 运行时安全检测
  (设计阶段)    (编码阶段)      (构建阶段)      (部署阶段)      (运行阶段)
```

**DevSecOps 工具链**：SAST/DAST、容器漏洞扫描（Trivy）、镜像签名验证（Cosign）、运行时安全（Falco）。

## 6. 云原生可观测性设计

### 6.1 可观测性三支柱

| 支柱 | 数据 | 回答的问题 | 代表工具 |
|------|------|-----------|---------|
| **Metrics** | 数值指标（CPU/内存/QPS） | 系统有什么问题？ | Prometheus + Grafana |
| **Traces** | 分布式调用链 | 问题出在哪一环？ | Jaeger, Zipkin, SkyWalking |
| **Logs** | 事件记录 | 发生了什么细节？ | ELK, Loki, Fluentd |

### 6.2 可观测性设计模式

| 模式 | 说明 |
|------|------|
| **RED指标** | Rate(请求速率) + Errors(错误率) + Duration(延迟)，衡量服务质量 |
| **USE指标** | Utilization + Saturation + Errors，衡量资源健康 |
| **四大黄金信号** | 延迟、流量、错误、饱和（Google SRE） |
| **分布式追踪** | TraceID全链路传递，OpenTelemetry标准化 |
| **健康检查API** | /healthz（进程状态）、/readyz（流量就绪） |
| **结构化日志** | JSON格式日志，字段标准化 |

### 6.3 OpenTelemetry——可观测性标准

**OpenTelemetry** 统一了 Telemetry 采集标准：API + SDK + Collector，与后端存储解耦。目前是CNCF孵化项目，已成为事实标准。

## 7. 服务网格（Service Mesh）设计

> 08已介绍基础概念，此处补充架构设计视角

### 7.1 Service Mesh 架构决策

| 决策 | 选项 | 权衡 |
|------|------|------|
| Sidecar范围 | 全集群 vs 按命名空间 | 统一管控 vs 渐进迁移 |
| 流量管理粒度 | 服务级 vs 请求级 | 管理简便 vs 灵活 |
| Ingress集成 | 统一Gateway vs 独立Gateway | 一致体验 vs 隔离性 |
| 可观测 | 遥测采样率 | 100%完整但开销大 vs 采样高效但丢失信息 |

### 7.2 Service Mesh 应用场景速查

| 场景 | Mesh 能力 |
|------|----------|
| 灰度发布 | 按Header/Cookie/权重路由流量 |
| 蓝绿部署 | 一键切换全部流量 |
| 故障注入 | 注入延迟/错误测试应用韧性 |
| 服务间加密 | 自动mTLS，零代码改动 |
| 金丝雀发布 | 小流量验证新版本 |
| 弹性测试 | 断路器和限流配置 |

## 8. 常考考点速查

### 8.1 云原生设计原则一句话

| 原则 | 一句话 |
|------|--------|
| 不可变基础设施 | 不改服务器，只替换实例 |
| 声明式API | 定义"应该是什么"，系统自己达到 |
| 自愈 | 期望状态 ≠ 实际状态→自动修复 |
| 韧性 | 部分故障系统仍运行 |
| 弹性 | 负载变化自动扩缩 |

### 8.2 设计模式速记

| 模式 | 作用 |
|------|------|
| Sidecar | 附加辅助功能到Pod |
| Ambassador | 代理外部连接 |
| Circuit Breaker | 熔断故障服务 |
| Bulkhead | 隔离资源防扩散 |
| CQRS | 读写分离模型 |
| Event Sourcing | 事件作为数据源 |

### 8.3 可观测性速记

```
Metrics → 数值（什么有问题？）
Traces → 调用链（哪里出问题？）
Logs → 详情（为什么出问题？）
```
