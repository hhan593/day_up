# 07 — 分布式系统与中间件

## 1. 分布式系统基础

### 1.1 分布式系统定义

由多个自治计算单元通过网络互联，协调完成共同任务，对用户呈现为单一系统的系统。

### 1.2 CAP 定理

分布式系统最多同时满足 CAP 中的两个：

| 属性 | 含义 |
|------|------|
| **C（一致性）** | 所有节点在同一时刻看到相同数据 |
| **A（可用性）** | 每个请求都能获得非错误的响应（不保证是最新数据） |
| **P（分区容忍性）** | 系统在任意网络分区故障下仍能运行 |

**常见取舍**：
- **CP系统**：保证一致性和分区容忍，放弃可用性（如ZooKeeper、etcd）
- **AP系统**：保证可用性和分区容忍，放弃强一致性（如Eureka、Cassandra）
- **CA系统**：理论上存在，但网络分区不可避免，实际中很少

### 1.3 BASE 理论

对 CAP 中 AP 方案的补充：

| 属性 | 含义 |
|------|------|
| **BA（Basically Available）** | 基本可用：系统出现故障时允许损失部分可用性 |
| **S（Soft State）** | 软状态：允许系统存在中间状态，不要求强一致性 |
| **E（Eventually Consistent）** | 最终一致性：经过一段时间后，数据最终达到一致 |

**BASE vs ACID**：
- ACID 是数据库事务的经典原则（原子性、一致性、隔离性、持久性）
- BASE 是分布式系统对弱一致性的务实方案

## 2. 分布式一致性协议

### 2.1 一致性分类

| 类型 | 含义 |
|------|------|
| **强一致性** | 写入后，任意后续读都能读到最新值 |
| **弱一致性** | 不保证能读到最新值 |
| **最终一致性** | 如果不再更新，最终所有副本会达到一致 |
| **因果一致性** | 有因果关系的更新按顺序被看到 |
| **读你所写一致性** | 用户总能读取自己写入的数据 |
| **单调读一致性** | 一旦读到某版本数据，后续不会读到更旧版本 |

### 2.2 Paxos 协议

- **目标**：在不可靠节点环境中就一个值达成一致
- **角色**：Proposer、Acceptor、Learner
- **两阶段**：
  - Phase 1（Prepare）：Proposer 发 Prepare(n) → Acceptor 承诺不接受编号 < n 的提案
  - Phase 2（Accept）：Proposer 发 Accept(n, v) → Acceptor 接受（若未承诺更高编号）
- **约束**：多数派（> N/2）接受即达成一致

### 2.3 Raft 协议

Raft 将一致性分解为三个子问题：

| 子问题 | 机制 |
|--------|------|
| **领导者选举** | 使用随机超时，Term递增，获得多数票的成为Leader |
| **日志复制** | Leader 接收请求 → 复制到 Follower → 多数确认 → 提交 |
| **安全性** | 选举限制（只有包含所有已提交日志的节点才能当选） |

Raft vs Paxos：Raft更适合教学和实现，逻辑更清晰可理解。

### 2.4 Zab 协议（ZooKeeper）

类似 Paxos，专门为 ZooKeeper 设计：
- 原子广播（消息发送与接收顺序一致）
- 崩溃恢复

### 2.5 两阶段提交（2PC）

分布式事务的经典协议：

```
Phase 1（准备阶段）：
  协调者 → 所有参与者：询问可否提交
  参与者  → 协调者：YES/NO

Phase 2（提交阶段）：
  如果所有YES → 协调者通知所有参与者提交
  如果任一NO  → 协调者通知所有参与者回滚
```

**问题**：协调者单点故障、阻塞式（参与者锁定资源等协调者决策）。

### 2.6 三阶段提交（3PC）

在 2PC 基础上引入超时机制和预提交阶段：

```
CanCommit → PreCommit → DoCommit
```

**改进**：减少阻塞概率，但仍无法完全解决网络分区下的数据一致性。

## 3. 负载均衡

### 3.1 负载均衡算法

| 算法 | 说明 | 特点 |
|------|------|------|
| **轮询（Round Robin）** | 按顺序逐个分配 | 简单、适合等性能节点 |
| **加权轮询** | 按权重比例分配 | 适合性能不等的节点 |
| **最少连接** | 分配给当前连接数最少的节点 | 适合长连接场景 |
| **源IP哈希** | 对客户端IP哈希选节点 | 会话保持 |
| **一致性哈希** | 环形哈希空间 | 节点增减时影响最小 |
| **随机** | 随机选一个节点 | 简单 |

### 3.2 分层负载均衡

```
用户 → DNS → L4（Nginx/LVS/HAProxy） → L7（API Gateway） → 应用服务器
```

- **L4（传输层）**：基于IP和端口，效率高但功能少
- **L7（应用层）**：基于URL/Header/参数，灵活但开销大

## 4. 消息中间件

### 4.1 消息队列核心概念

| 概念 | 说明 |
|------|------|
| **生产者（Producer）** | 发送消息的应用 |
| **消费者（Consumer）** | 接收处理消息的应用 |
| **队列（Queue）** | 存储消息的缓冲区 |
| **主题（Topic）** | 消息的逻辑分类（发布-订阅模式） |
| **Broker** | 消息中转服务 |

### 4.2 消息模式

| 模式 | 说明 |
|------|------|
| **点对点（P2P）** | 一个消息被一个消费者消费一次（Queue） |
| **发布-订阅（Pub-Sub）** | 一个消息被多个订阅者消费（Topic） |
| **请求-响应** | 生产者发送请求并等待响应 |
| **死信队列（DLQ）** | 无法处理的消息存放到专门的队列 |

### 4.3 消息可靠性保障

| 要点 | 说明 |
|------|------|
| **消息持久化** | 磁盘存储防止Broker崩溃丢失 |
| **生产者确认** | Broker确认收到消息后生产者再发送下一条 |
| **消费者确认** | 消费者处理后向Broker确认，失败则重发 |
| **事务消息** | 生产者和本地事务绑定（如RocketMQ） |

### 4.4 RocketMQ vs Kafka vs RabbitMQ

| 特性 | RabbitMQ | Kafka | RocketMQ |
|------|----------|-------|----------|
| 语言 | Erlang | Java/Scala | Java |
| 吞吐量 | 中等 | 极高 | 高 |
| 延迟 | 微秒级 | 毫秒级 | 毫秒级 |
| 事务消息 | 不支持 | 不支持 | 支持 |
| 消息回溯 | 不支持 | 支持 | 支持 |
| 适用场景 | 实时、可靠性优先 | 日志、流处理、大数据 | 电商、金融、事务消息 |

## 5. 分布式缓存

### 5.1 缓存模式

| 模式 | 说明 |
|------|------|
| **Cache Aside** | 业务代码控制读/写，查缓存→缓存没有查DB→回写缓存；先更新DB再删缓存 |
| **Read/Write Through** | 缓存层代理读写DB，业务只和缓存交互 |
| **Write Behind** | 异步批量写入DB，写延迟低但有数据丢失风险 |

### 5.2 缓存常见问题

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询不存在的数据，每次都打到DB | 布隆过滤器、缓存空值 |
| **缓存击穿** | 热点key过期，大量请求打到DB | 互斥锁、永不过期+异步更新 |
| **缓存雪崩** | 大量key同时过期 | 过期时间加随机值、多级缓存、熔断降级 |
| **数据一致性** | 缓存与DB数据不一致 | Cache Aside+延迟双删、订阅binlog更新 |

### 5.3 缓存淘汰策略

| 策略 | 说明 |
|------|------|
| **LRU** | 最近最少使用（Least Recently Used） |
| **LFU** | 最少频率使用（Least Frequently Used） |
| **FIFO** | 先进先出 |
| **TTL** | 设置过期时间（Time To Live） |
| **RANDOM** | 随机淘汰 |

## 8. 限流与熔断

### 8.1 限流算法

| 算法 | 说明 | 优缺点 |
|------|------|--------|
| **计数器（固定窗口）** | 统计一个时间窗口内的请求数 | 简单但有临界问题（窗口切换瞬间突破限流） |
| **滑动窗口** | 将时间窗口细分多个小格，随时间滑动 | 精确，实现复杂一些 |
| **漏桶（Leaky Bucket）** | 固定速率输出请求，进桶不受限 | 平滑流量，不允许突发 |
| **令牌桶（Token Bucket）** | 以固定速率生成令牌，请求需获取令牌 | 允许突发（桶容量=最大突发） |

**令牌桶 vs 漏桶**：

| 维度 | 令牌桶 | 漏桶 |
|------|--------|------|
| 流量整形 | 允许一定突发 | 严格匀速 |
| 空闲期 | 积累令牌，供突发使用 | 漏桶空转，不积累"配额" |
| 典型应用 | API限流，网关（Sentinel） | 流量整形的防火墙 |

**令牌桶参数**：
```
r = 令牌生成速率（如 100/s）
b = 桶容量（如 200个令牌）
→ 正常处理100/s，突发200 + 持续补充100
```

### 8.2 熔断与降级

**熔断（Circuit Breaker）状态机**：
```
Closed（闭合：正常调用）→ [失败达阈值] → Open（断开：直接拒绝）
Open → [冷却时间到达] → Half-Open（半开：放少量请求试探）
Half-Open → [成功] → Closed | [失败] → Open
```

**熔断器配置参数**：
| 参数 | 说明 | 典型值 |
|------|------|--------|
| 错误阈值 | 触发熔断的失败次数/比例 | 50%错误率 |
| 时间窗口 | 统计错误的时间窗口 | 10秒 |
| 冷却时间 | 从Open到Half-Open的等待 | 30秒 |
| 试探请求数 | Half-Open阶段放行的请求数 | 3个 |
| 最小请求数 | 触发统计分析的最少请求数 | 20个 |

**降级**：系统高峰期或有故障时，关闭非核心功能（如推荐、排行榜），保证核心服务（下单、支付）可用。

**降级策略**：
| 策略 | 说明 | 示例 |
|------|------|------|
| 页面降级 | 简化页面功能 | 去掉推荐专区 |
| 服务降级 | 降低服务质量 | 用本地缓存替代远程查询 |
| 读降级 | 读取旧数据 | 读缓存而非实时计算 |
| 写降级 | 异步化或延迟写 | 评论异步审核后发布 |

**限流 vs 熔断 vs 降级**：
- 限流：主动控制流量，预防过载（事前防御）
- 熔断：被动响应故障，快速失败保护下游（事中保护）
- 降级：暂时牺牲非核心功能，保证核心体验（事中牺牲）

## 9. 分布式共识算法

### 9.1 Paxos

**Paxos** 是 Lamport 提出的解决分布式一致性的经典算法。

**角色**：
| 角色 | 职责 |
|------|------|
| **Proposer** | 提出提案 |
| **Acceptor** | 接受或拒绝提案 |
| **Learner** | 学习已被接受的提案 |

**Basic Paxos 两个阶段**：
```
Phase 1: Prepare
  Proposer → Acceptor: Prepare(n)  // n为全局递增的提案号
  Acceptor: 若n>之前最高Prepare号，回复Promise(已接受的最高提案)，否则拒绝

Phase 2: Accept
  Proposer: 从多数Acceptor获得Promise后，发送Accept(n, value)
            value = Promise中最高的已接受值（如果有），否则用自己提议的值
  Acceptor: 若n≥承诺过的最高Prepare号，接受提案，否则拒绝
```

**Multi-Paxos**：Basic Paxos 的工程优化，选举Leader后只执行一次Phase 1，后续只需Phase 2。

### 9.2 Raft

**Raft**：以可理解性为首要目标设计的共识算法，将问题分解为独立子问题。

**三个核心子问题**：
1. **Leader选举**：节点有 Follower/Candidate/Leader 三种状态，领导失效触发新选举
2. **日志复制**：Leader接收客户端请求，复制日志到Followers，多数确认后提交
3. **安全**：选举时限制只有包含所有已提交日志的节点能成为Leader

**Raft vs Paxos**：
| 维度 | Paxos | Raft |
|------|-------|------|
| 可理解性 | 难（经典论文难读懂） | 易（以可理解性为设计目标） |
| 实现复杂度 | 高 | 中 |
| Leader | Multi-Paxos中引入 | 核心概念 |
| 日志连续性 | 允许空洞 | 严格连续 |
| 实际使用 | Chubby, Spanner | etcd, Consul, TiKV |

**随机超时**：Raft 的选举超时是随机的（如150-300ms），防止多个Candidate同时竞争（分裂投票）。

### 9.3 ZAB（ZooKeeper Atomic Broadcast）

| 维度 | ZAB | Raft |
|------|-----|------|
| 消息递交 | 广播式 | 日志复制 |
| 恢复模式 | 选举期间 | Leader重选 |
| 设计目的 | ZK集群 | 通用共识 |

## 10. 消息中间件补充

### 10.1 消息传递语义

| 语义 | 含义 | 实现 |
|------|------|------|
| **At most once** | 最多一次（可能丢） | 发送即忘 |
| **At least once** | 至少一次（可能重复） | 发送+重试 |
| **Exactly once** | 恰好一次（最理想，最难） | 幂等消费+事务消息 |

**实现 Exactly Once 的条件**：
- 生产者：消息发送 + 事务（或幂等发送）
- Broker：去重（如Kafka的幂等Producer + 事务）
- 消费者：幂等处理（如基于消息ID去重）+ 手动提交Offset + 业务逻辑幂等

### 10.2 消息消费者模式

| 模式 | 说明 | 适用 |
|------|------|------|
| **队列模式（Queue）** | 多个消费者竞争消息，每条消息一个处理者 | 负载均衡 |
| **发布-订阅（Pub-Sub）** | 一个消息投递给所有订阅者 | 广播通知 |
| **消费者组** | 组间广播、组内竞争（Kafka模型） | 灵活分组消费 |

### 10.3 消息顺序性

| 级别 | 说明 |
|------|------|
| **全局顺序** | 所有消息严格有序（性能最差） |
| **分区有序** | 同一分区/Key内部有序（Kafka/RocketMQ默认） |
| **无顺序** | 无序消费 |

**保证有序的条件**：同一Key的消息发到同一分区 + 单线程消费该分区。

### 10.4 消息可靠性

**生产者可靠性**：同步发送+重试 / 异步发送+回调+重试 / 事务消息（如RocketMQ半消息+回调确认）。

**Broker可靠性**：集群复制（同步刷盘 vs 异步刷盘）、多副本（ISR机制）。

**消费者可靠性**：手动提交偏移量（处理完业务再提交）、幂等消费。​
