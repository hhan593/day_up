# 06 — 架构设计方法与评估

## 1. 架构设计过程

### 1.1 架构设计的输入与输出

**输入**：
- 需求文档（SRS）
- 质量属性需求（性能、安全、可用性、可修改性等）
- 技术约束（平台、语言、遗留系统、法规）
- 组织约束（预算、工期、团队能力）

**输出**：
- 架构视图文档（4+1）
- 架构决策记录（ADR）
- 原型/技术验证
- 架构评估报告

### 1.2 架构设计的一般流程

```
需求分析(架构上有意义的需求)
    → 架构综合(候选架构方案生成)
    → 架构评估(候选方案对比)
    → 架构细化(选定方案的具体化)
    → 架构验证(确认满足需求)
    → 架构文档化
```

## 2. 基于属性的架构设计方法（ADD）

ADD（Attribute-Driven Design）是SEI提出的以质量属性驱动的架构设计方法。

### 2.1 ADD 核心步骤

1. **确认功能需求、质量属性需求和约束**
2. **选择待设计系统的一个元素**（第一次迭代选整个系统）
3. **识别该元素的架构驱动因子**（最重要的质量属性需求）
4. **选择满足架构驱动因子的设计概念**（战术+模式）
5. **实例化架构元素，分配职责**
6. **定义所实例化元素的接口**
7. **验证和细化设计**（满足驱动因子要求）
8. **重复2-7直到满足所有需求**

### 2.2 ADD 中的架构驱动因子

- 驱动因子是那些对架构有决定性影响的需求
- 优先级最高的质量属性场景通常就是驱动因子
- 例如：并发10000TPS（性能驱动）、99.99%可用（可用性驱动）、未来5年可扩展（可修改性驱动）

## 3. 架构评估方法

### 3.1 SAAM（Scenario-based Architecture Analysis Method）

**最早**的基于场景的架构分析方法。

**核心步骤**：
1. 描述架构（在SAAM层面）
2. 开发场景（功能场景+变更场景）
3. 分类场景（直接场景/间接场景）
4. 执行场景评估（评估每个场景对架构的影响）
5. 揭示场景交互（发现间接场景=需要修改架构）
6. 形成总体评估

**特点**：
- 同时考虑功能场景和变更场景
- 关注架构对修改的适应性
- **结构简单，可操作性强**

---

### 3.2 ATAM（Architecture Tradeoff Analysis Method）

ATAM是SAAM的演进，**专门关注质量属性权衡**。

**核心参与者**：
- **评估团队**（3-5位外部专家）
- **项目决策者**（项目经理、客户代表）
- **架构干系人**（开发、测试、运维、安全）

**ATAM 的9个步骤**：

**阶段一：介绍和展示**
1. 介绍ATAM方法
2. 介绍业务驱动因子
3. 介绍待评估架构

**阶段二：调查与分析（核心阶段）**
4. 识别架构方法（梳理架构中的关键设计决策）
5. 生成质量属性效用树
6. 分析架构方法（针对高优先级场景分析风险/非风险/敏感点/权衡点）

**阶段三：测试**
7. 头脑风暴并排定场景优先级
8. 分析架构方法（对头脑风暴产生的高优先级场景）
9. 结果总结

**核心产出**：风险列表、非风险列表、敏感点、权衡点

### 3.3 效用树（Utility Tree）

**结构**：
```
根节点（效用）
├── 质量属性1（如性能）
│   ├── 场景(高,高)：10000用户并发，响应时间<2秒
│   ├── 场景(高,中)：5000TPS，CPU<70%
│   └── 场景(中,低)：启动时间<30秒
├── 质量属性2（如可修改性）
│   ├── 场景(高,高)：增加新支付方式<3人天
│   └── 场景(中,中)：替换数据库<20人天
└── 质量属性3（如安全性）
    └── 场景(高,高)：SQL注入防护，渗透测试通过
```

- **二元组(重要性，实现难度)**：H,M,L三档，关注高重要性的场景
- 每个场景应是具体的、可测试的质量属性需求
- 分析时聚焦 (H,H) 和 (H,M) 场景

### 3.4 ATAM 关键概念

| 概念 | 含义 | 示例 |
|------|------|------|
| **敏感点（Sensitivity Point）** | 一个架构决策的微小变化会导致某个质量属性显著变化 | 缓存大小对响应时间的敏感度 |
| **权衡点（Tradeoff Point）** | 一个架构决策改善一个质量属性但降低另一个 | 加密提高安全性但降低性能 |
| **风险（Risk）** | 可能导致问题的架构决策 | "数据库单点可能无法满足可用性要求" |
| **非风险（Non-Risk）** | 经过验证的良性架构决策 | "使用长连接池满足并发要求" |
| **场景** | 质量属性需求的具体实例 | "高峰时段1000用户同时下单" |

### 3.5 架构评估方法对比

| 特征 | SAAM | ATAM |
|------|------|------|
| 分析目标 | 功能分解+变更影响 | 质量属性分析+权衡 |
| 场景类型 | 功能场景+变更场景 | 质量属性效用树 |
| 输出 | 场景交互图 | 风险/非风险/敏感点/权衡点 |
| 侧重点 | 可修改性 | 多质量属性权衡 |
| 复杂度 | 低 | 高 |

## 4. 架构综合与质量属性战术

### 4.1 质量属性战术总览

**战术（Tactics）**：影响质量属性响应的基本设计决策。

```
架构策略 → 架构战术 → 架构模式 → 架构风格
(最细粒度)                   (最粗粒度)
```

### 4.2 可用性战术（Availability Tactics）

```
                      ┌─ 检测故障 ────┐
                      │  心跳          │
可用性战术 ──────────┤   Ping/Echo     │
                      │  异常检测       │
                      │  条件监控       │
                      │                │
                      ├─ 恢复故障 ────┐│
                      │  主动冗余      ││
                      │  被动冗余      ││
                      │  备件          ││
                      │  影子操作      ││
                      │  状态再同步    ││
                      │  检查点/回滚   ││
                      │               ││
                      └─ 预防故障 ────┘│
                         从事务中移除   │
                         事务(ACID)    │
                         过程监视       │
```

### 4.3 可修改性战术（Modifiability Tactics）

| 类别 | 战术 | 说明 |
|------|------|------|
| **局部化修改** | 语义一致性、预期期望的变更、泛化、限制可能的选择 | 将修改限制在最小范围内 |
| **防止连锁反应** | 信息隐藏、维持现有接口、限制通信路径、仲裁者 | 修改不应扩散到其他模块 |
| **推迟绑定时间** | 运行时注册、配置文件、多态、组件替换、遵守定义协议 | 将决策从编译时推迟到运行时 |

### 4.4 性能战术（Performance Tactics）

| 类别 | 战术 | 说明 |
|------|------|------|
| **资源需求** | 提高计算效率、减少计算开销、管理事件速率 | 减少需要处理的工作量 |
| | 控制采样频率、限制执行时间、队列大小限制 | |
| **资源管理** | 引入并发、增加可用资源、维护数据多副本 | 增加处理能力 |
| | 优化资源分配和调度 | |
| **资源仲裁** | FIFO、固定优先级、动态优先级、时限优先 | 决定谁先用资源 |

### 4.5 安全性战术（Security Tactics）

| 类别 | 战术 | 说明 |
|------|------|------|
| **抵抗攻击** | 认证用户、授权用户、维护数据机密性（加密）、维护数据完整性、限制暴露、限制访问 | 阻止攻击发生 |
| **检测攻击** | 入侵检测系统、审查追踪 | 发现攻击 |
| **从攻击中恢复** | 恢复状态、识别攻击者（审计跟踪保证不可抵赖） | 攻击发生后的恢复 |

**AAA**：Authentication（认证）、Authorization（授权）、Accounting（审计）

### 4.6 可测试性战术

| 战术 | 说明 |
|------|------|
| 记录/回放 | 捕获系统交互数据，用于复现和测试 |
| 将接口与实现分离 | 通过抽象接口进行模块化测试 |
| 专门的测试途径 | 测试钩子、测试接口 |
| 内部监视器 | 暴露内部状态用于断言和检查 |

### 4.7 易用性战术

| 战术 | 说明 |
|------|------|
| 分离用户界面 | MVC/MVP/MVVM |
| 支持用户主动 | 撤销/重做、用户模型一致性（WYSIWYG） |
| 支持系统主动 | 输入提示、自动完成、输入检验 |

## 5. 架构决策记录（ADR）

### 5.1 ADR模板

```markdown
# ADR-{序号}: {标题}

**状态**：提议/已接受/已废弃/已替代

**上下文**：
描述需要做出决策的技术背景和约束条件。

**决策**：
明确陈述做出的架构决策。

**后果**：
描述决策带来的正面和负面影响。
```

### 5.2 ADR 的作用

- 记录关键决策及其理由
- 方便新成员理解架构为什么是这样的
- 为未来重新评估提供上下文
- 架构评审时作为重要参考

## 6. 架构重构

### 6.1 何时需要架构重构

- 质量属性持续不满足
- 技术债务累积到影响生产力
- 新技术带来显著优势
- 业务模式发生根本变化

### 6.2 重构策略

- **增量重构**：每次迭代改进一部分（推荐，低风险）
- **绞杀者模式（Strangler Fig）**：逐步建立新系统代理旧系统
- **大爆炸重构**：全面重写（高风险，不推荐）

## 7. CBAM——成本效益分析方法

> 系统架构设计师考点：扩展ATAM的经济性评估方法

### 7.1 CBAM 概述

**CBAM（Cost Benefit Analysis Method）**：在ATAM基础上增加了经济学维度，对架构策略的成本和收益进行量化分析。

**CBAM 核心问题**：多个架构策略都能满足质量属性要求，但哪个性价比最高？

### 7.2 CBAM 分析步骤

```
1. 整理场景和架构策略（从ATAM输出中获取）
2. 精化场景，关联质量属性响应目标（精确到数值）
3. 确定每个场景的"效用"（Utility）——不同质量属性响应水平对业务的价值
4. 预测每个架构策略对场景的响应水平改进
5. 计算每个策略的综合收益（效用提升值）
6. 估算每个策略的成本
7. 计算 ROI = 效益 / 成本，按ROI排序选择
```

### 7.3 CBAM 关键概念

| 概念 | 说明 |
|------|------|
| **效用（Utility）** | 质量属性响应水平对业务的价值 |
| **效用曲线** | 从响应水平到效用的映射曲线（通常非线性） |
| **ROI** | 策略的效用增益 / 策略的实施成本 |
| **最佳响应水平** | 边际效用 = 边际成本的点 |

**效用曲线示例——性能响应时间**：
```
效用
 │  高  ●──────────────────
 │     ╱
 │  中╱
 │  ╱
 │ 低●──────────────
 └──┬────┬────┬────→ 响应时间
   50ms 200ms 1s  5s

解读：响应时间从5s降到200ms，效用从"低"提升到"中"；再降到50ms，效用仅"中"→"高"
→ 超过200ms的优化边际效用递减
```

## 8. ARID——主动设计评审

### 8.1 ARID 概述

**ARID（Active Reviews for Intermediate Designs）**：一种用于评审部分设计（尚未完成全部设计）的方法，结合了**评审**和**场景走查**。

**与ATAM的区别**：ATAM评估完整架构的质量属性，ARID评审**未完成的设计片段**的适用性和正确性。

### 8.2 ARID 流程

1. **准备阶段**：准备设计描述、设计种子场景
2. **会议阶段**：
   - 设计师展示设计要点（5-10分钟）
   - 评审员使用场景走查设计（主动参与，不是被动听）
   - 识别设计问题，而非解决问题
3. **报告阶段**：问题清单和评审结论

### 8.3 评估方法全景对比

| 特征 | SAAM | ATAM | CBAM | ARID |
|------|------|------|------|------|
| 评估对象 | 完整架构 | 完整架构 | 架构策略 | 部分/中间设计 |
| 核心关注 | 可修改性 | 多质量属性权衡 | 成本-收益 | 设计正确性/适用性 |
| 场景来源 | 功能+变更 | 效用树 | ATAM场景 | 设计师预定义 |
| 经济分析 | 无 | 无 | 有（ROI/效用曲线） | 无 |
| 干系人参与 | 中 | 高 | 高+财务视角 | 中 |
| 复杂度 | 低 | 高 | 中高 | 低 |
| 适用阶段 | 早期评估 | 深度评估 | 策略选择 | 设计过程中 |

## 9. 领域驱动设计（DDD）与架构设计

### 9.1 DDD 与架构设计的关系

DDD 提供了一种从业务领域出发驱动架构设计的方法论。

**战略设计**（影响架构层面）：
| 概念 | 说明 | 架构意义 |
|------|------|---------|
| **限界上下文（Bounded Context）** | 领域模型的适用范围和边界 | → 微服务拆分边界 |
| **上下文映射（Context Map）** | 不同限界上下文之间的关系 | → 服务间集成模式 |
| **子域（Subdomain）** | 核心域/支撑域/通用域 | → 架构投资优先级 |

**上下文映射的集成模式**：

| 模式 | 架构含义 |
|------|---------|
| **共享内核（Shared Kernel）** | 两个上下文共享部分模型 → 共享库（谨慎使用） |
| **客户-供应商** | 上游决定接口，下游接受 → 服务层级调用 |
| **防腐层（ACL）** | 下游建立保护层隔离上游模型 → 适配器+翻译 |
| **开放主机服务（OHS）** | 上游提供标准化API → REST/gRPC API |
| **发布语言（PL）** | 使用标准化文档交换 → 领域事件/消息 |
| **分离方式** | 各自独立不集成 → 完全解耦 |

### 9.2 DDD 战术设计对架构的细化

**聚合（Aggregate）设计原则**：
1. 小聚合优于大聚合（减小事务范围）
2. 通过ID引用其他聚合，不直接持有引用
3. 最终一致性代替跨聚合强一致事务
4. 一个聚合对应一个Repository

**事件风暴（Event Storming）**：与业务专家一起用便利贴建模，识别领域事件→命令→聚合→限界上下文。架构师可以从中获取架构拆分线索。

## 10. 架构设计中的决策框架

### 10.1 架构决策的四个层次

| 层次 | 问题 | 示例 |
|------|------|------|
| **战略决策** | 用什么架构风格？怎么分解系统？ | 单体→微服务，用什么消息中间件 |
| **战术决策** | 怎样满足每个质量属性？ | 用缓存/队列/索引优化性能 |
| **技术决策** | 用哪个具体技术产品？ | Redis vs Memcached, Kafka vs RocketMQ |
| **工程决策** | 团队如何实现？ | 编码规范，分支策略 |

### 10.2 权衡分析矩阵

当多个质量属性冲突时，使用权衡矩阵：

```
质量属性权衡矩阵：
            性能  安全  可用性  可修改性  成本
性能         —    -+   0      -+      -+
安全         +-   —    -+    -       -
可用性      0    +-   —     -       -
可修改性    +-   +    +     —       -
成本        +-   +    +     +       —

+ = 相互促进   - = 相互冲突   0 = 无影响
双符号 = 主动/被动关系
```

**常见权衡场景**：

| 场景 | 冲突 | 典型折中 |
|------|------|---------|
| 安全性 vs 性能 | 加密增加计算开销 | 敏感数据加密，非敏感数据不加密 |
| 可用性 vs 一致性 | CAP定理 | 金融选择CP，社交选择AP |
| 可修改性 vs 性能 | 抽象层增加性能开销 | 在热点路径减少抽象 |
| 可修改性 vs 成本 | 灵活架构开发成本高 | 核心域投资好架构，通用域/支撑域可以简单些 |

### 10.3 没有免费的午餐——架构权衡本质

每条质量属性的提升都伴随着其他属性或成本的牺牲。架构师的核心价值是**找到适合当前业务场景的最优平衡点**。技术是为业务服务的——10万用户的电商和1000万用户的电商需要的架构不同。
