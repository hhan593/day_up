# 10 — 软件可靠性基础知识

## 1. 软件可靠性基本概念

### 1.1 可靠性的定义

**软件可靠性**：在规定条件下、规定时间内，软件不引起系统失效的概率。

**三层含义**：
- **规定条件**：运行环境、使用方式（操作剖面）
- **规定时间**：软件运行时间（CPU执行时间或日历时间）
- **规定功能**：软件应完成的业务功能

**硬件可靠性 vs 软件可靠性**：

| 维度 | 硬件可靠性 | 软件可靠性 |
|------|----------|-----------|
| 失效原因 | 物理退化、磨损、老化 | 设计缺陷（软件不会磨损） |
| 失效规律 | 浴缸曲线（早期高→稳定→老化高） | 无老化阶段，随时间缺陷被修复 |
| 可靠性增长 | 不可增长（反而下降） | 可通过修复缺陷持续增长 |
| 冗余有效性 | 相同部件冗余有效 | 相同软件冗余不一定有效（会同时失效） |
| 环境因素 | 温度、湿度、振动等影响大 | 运行环境影响小 |

### 1.2 可靠性度量指标

| 指标 | 英文 | 含义 | 公式 |
|------|------|------|------|
| **可靠度** | R(t) | t时间内不失效的概率 | R(t) = P(T > t) |
| **失效率** | λ(t) | t时刻后单位时间内失效的概率（条件概率） | λ(t) = f(t) / R(t) |
| **平均无故障时间** | MTTF | 不可修复系统从工作到首次失效的平均时间 | MTTF = ∫₀^∞ R(t)dt |
| **平均故障间隔时间** | MTBF | 可修复系统两次相邻故障间的平均时间 | MTBF = MTTF + MTTR |
| **平均修复时间** | MTTR | 从故障发生到修复完成的平均时间 | — |
| **可用性** | A | 系统正常工作的时间占比 | A = MTTF / (MTTF + MTTR) = MTTF / MTBF |

> 注：对软件而言，通常不区分 MTTF 和 MTBF，因为软件"修复"是修改代码而非恢复运行。

### 1.3 失效分布函数

**失效概率分布函数** F(t)：t时刻前已失效的概率
```
F(t) = 1 - R(t)
```

**失效概率密度函数** f(t)：F(t)的导数
```
f(t) = dF(t)/dt = -dR(t)/dt
```

**失效率与可靠度关系**：
```
R(t) = exp(-∫₀^t λ(τ)dτ)
```
当失效率为常数 λ 时：R(t) = e^(-λt)，即指数分布。

**浴缸曲线**（硬件失效三阶段）：
```
λ(t)
 │  ▲
 │  │ 早期失效期      │ 偶然失效期      │ 耗损失效期
 │  │ (失效率递减)   │ (失效率恒定)   │ (失效率递增)
 │  │  \              │  ──────        │      /
 │  │   \             │                │     /
 │  │    \____________│________________│____/______
 └──┴──────────────────────────────────────────────→ t
     调试/筛选阶段      正常使用阶段       老化/报废阶段
```

> 软件失效无耗损期，失效率随时间呈递减趋势（缺陷被逐个修复）。

## 2. 软件可靠性设计

> 系统架构设计师核心考点：三大设计策略——避错、容错、检错

### 2.1 避错设计（Fault Avoidance）

在开发过程中**预防**缺陷的引入。

| 技术 | 说明 |
|------|------|
| **形式化方法** | 用数学方法（Z语言、VDM、B方法）进行精确规约和验证 |
| **结构化/模块化设计** | 降低复杂度，提高可理解性 |
| **强类型系统** | 编译器在编译期捕获类型错误 |
| **断言（Assertion）** | 在关键点检查程序状态是否满足预期 |
| **契约式编程** | 前置条件、后置条件、不变式（如Design by Contract） |
| **严格过程管理** | 遵循CMMI、变更控制、同行评审 |
| **静态分析** | 使用工具在编译前发现潜在缺陷 |

### 2.2 容错设计（Fault Tolerance）

系统在存在故障的情况下仍能继续运行（不失效）。

#### 2.2.1 恢复块（Recovery Block）

```
保证测试
    ┌──→ [主块] ──→ 验收测试 ──→ 通过 ──→ 输出
    │                  │ 失败
    │              [备选块1] ──→ 验收测试 ──→ 通过 ──→ 输出
    │                  │ 失败
    │              [备选块2] ──→ 验收测试 ──→ 通过 ──→ 输出
    │                  │ 失败
    └────── 恢复 ←──── 异常/默认值
```

**核心思想**：同一功能由多个不同版本的程序块实现，主块失败时切换到备选块。

**验收测试要求**：能有效检测故障，且自身必须简单可靠。

#### 2.2.2 N版本编程（N-Version Programming, NVP）

```
输入 ──→ [版本1] ──→
        [版本2] ──→ 表决器（Voter）──→ 输出
        [版本3] ──→
```

- 同一需求规格由 N 个独立团队分别实现
- N 个版本同时运行，结果由表决器按多数（或一致）原则决策
- **关键要求**：各版本必须设计独立（Design Diversity）——不同算法、不同团队、不同工具

NVP vs 恢复块：

| 维度 | 恢复块 | N版本编程 |
|------|--------|----------|
| 执行方式 | 顺序执行（主块失败才执行备选） | 并行执行（所有版本同时运行） |
| 裁决机制 | 验收测试 | 表决器投票 |
| 冗余类型 | 时间冗余 | 空间冗余（多个版本并行） |
| 性能影响 | 失败时增加执行时间 | 始终有N倍计算开销 |
| 适用场景 | 偶发故障 | 高可靠性要求的计算（航天、核控） |

#### 2.2.3 防卫式编程（Defensive Programming）

在程序内部包含错误检测和恢复机制。

**典型技术**：
- **参数校验**：对输入参数进行有效性检查
- **空指针检查**：访问前检查指针/引用非空
- **范围检查**：数组索引、枚举值范围
- **超时机制**：对外部调用设置超时
- **重试机制**：临时性故障时重试（如网络请求）
- **健康检查**：定期检查组件是否正常工作

### 2.3 检错设计（Fault Detection）

在运行时检测故障存在但不自动处理。

| 技术 | 说明 |
|------|------|
| **断言（Assertion）** | 代码关键点插入不变量检查 |
| **心跳（Heartbeat）** | 组件周期性发送"我还活着"信号 |
| **看门狗（Watchdog）** | 外部定时器，未收到复位信号则重启系统 |
| **校验码（Checksum/CRC）** | 数据错误检测 |
| **审计日志（Audit Log）** | 记录异常操作和系统状态用于事后分析 |
| **异常处理（Exception）** | 捕获和记录运行时异常 |

## 3. 冗余技术

> 系统架构设计师必考：四种冗余及各自特点

### 3.1 冗余分类

| 冗余类型 | 原理 | 典型应用 |
|----------|------|---------|
| **硬件冗余** | 增加物理硬件备份 | 双机热备、RAID磁盘阵列、双路电源 |
| **软件冗余** | 使用不同版本或不同算法的软件 | N版本编程、恢复块 |
| **信息冗余** | 在数据中添加额外校验信息 | CRC、ECC纠错码、奇偶校验、海明码 |
| **时间冗余** | 重复执行操作以检测或恢复 | 指令复执、事务回滚重试、超时重传 |

### 3.2 硬件冗余级别

| 级别 | 方式 | 说明 |
|------|------|------|
| **N+1冗余** | 1个备用 | 单机故障时切换到备用机 |
| **2N冗余** | 全冗余 | 每个部件都有备份 |
| **双活（Active-Active）** | 两套同时工作 | 负载分摊 + 故障接管 |
| **主备（Active-Standby）** | 一主一备 | 备用机热/暖/冷待命 |

### 3.3 软件冗余要点

**设计多样性（Design Diversity）**是软件冗余有效的前提：
- 相同需求规格
- 不同的实现算法
- 不同的开发团队
- 不同的开发工具/语言
- 不同的测试策略

> 如果N个版本由同一团队用同一方法开发，可能包含相同的设计缺陷（共因失效），冗余无效。

### 3.4 信息冗余——海明码

**海明码**：不仅能检错，还能定位并纠正单比特错误。

**编码规则**：对于 k 位校验码，最多可校验 2^k - 1 位数据（包括校验位自身）。

**校验位位置**：第 1, 2, 4, 8, ... 位（2 的幂次位置）。

**海明距**：两个合法码字之间不同比特位的最小数。海明距为 d，则：
- 可检测 ≤ d-1 个比特错误
- 可纠正 ≤ ⌊(d-1)/2⌋ 个比特错误

## 4. 软件可靠性建模

> 系统架构设计师考点：模型分类、常用模型特点

### 4.1 可靠性模型分类

| 分类维度 | 类别 | 说明 |
|----------|------|------|
| **按时间域** | 日历时间模型 | 以实际日历时间为单位 |
| | 执行时间模型 | 以CPU执行时间为单位（Musa模型） |
| **按失效过程** | 错误计数模型 | 关注发现和修复了多少缺陷 |
| | 非错误计数模型 | 关注失效时间间隔 |
| **按随机性** | 马尔可夫模型 | 失效率取决于当前残留缺陷数 |
| | 非齐次泊淞过程(NHPP) | 累计失效数服从NHPP |
| **按修复假设** | 完美修复 | 修复不引入新缺陷 |
| | 不完美修复 | 修复可能引入新缺陷 |
| **按输入域** | 输入域模型 | 基于输入空间的失效概率 |

### 4.2 经典模型速查

| 模型 | 类型 | 核心假设 | 特点 |
|------|------|---------|------|
| **Jelinski-Moranda (J-M)** | 错误计数/马尔可夫 | 失效间隔服从指数分布，失效率与剩余缺陷数成正比，完美修复 | 最早、最经典的模型 |
| **Goel-Okumoto (G-O)** | NHPP | 累计失效数服从NHPP，失效率随时间指数递减 | 不假设完美修复 |
| **Musa执行时间模型** | 执行时间 | 失效率与残留缺陷数成正比，使用CPU执行时间度量 | 更精确反映软件使用情况 |
| **Littlewood-Verrall** | 贝叶斯 | 修复可能引入新缺陷（不完美修复），可靠性随机增长 | 更符合实际，但计算复杂 |
| **Seeding模型（播种模型）** | 错误计数 | 故意"播种"已知缺陷，通过发现率推算总缺陷数 | 类似"捉放法"估算种群数量 |
| **Schneidewind模型** | NHPP | 仅在测试最后阶段的数据才代表未来可靠性 | 适合多版本演进 |

### 4.3 模型选择考虑因素

- **开发阶段**：早期用NHPP类，晚期用错误计数类
- **数据可用性**：有失效时间间隔数据用J-M类，只有累计值用G-O类
- **应用类型**：安全关键系统选保守估计的模型
- **失效趋势**：失效率稳定选常数模型，递减趋势选NHPP

## 5. 软件可靠性测试与评估

### 5.1 可靠性测试

**目的**：验证软件是否达到可靠性要求（与常规功能测试不同）。

**操作剖面（Operational Profile）**：系统在实际使用中各操作发生的概率分布。

```
操作剖面构建步骤：
1. 识别操作发起者（用户类型、外部系统）
2. 列出每种发起者的所有操作
3. 确定各操作的发生频率/概率
4. 按概率分配测试用例数量
```

**可靠性测试用例设计**：按操作剖面随机抽样生成测试用例，确保测试覆盖真实使用场景。

> 不按操作剖面的测试测得的是"发现缺陷的能力"而非"实际可靠性"。

### 5.2 可靠性评估

| 评估方法 | 说明 |
|----------|------|
| **基于可靠性增长模型** | 收集测试阶段的失效数据，拟合模型，预测当前可靠性 |
| **基于无失效运行时间** | 在给定置信度下，若T时间内无失效，则MTTF≥T |
| **基于错误播种** | 人工注入缺陷（种子），通过检出率估算残留缺陷数 |
| **基于覆盖率** | 利用测试覆盖率（分支覆盖、路径覆盖）评估残留风险 |

### 5.3 可靠性增长

**可靠性增长**：在测试和调试过程中，通过发现和修复缺陷，软件可靠性逐步提高的过程。

**可靠性增长模型三要素**：
1. 失效率随缺陷修复而降低
2. 缺陷的发现率与残留缺陷数和测试强度有关
3. 每次缺陷修复都有可能引入新缺陷（不完美修复）

**可靠性增长测试流程**：
```
执行测试 → 发现失效 → 定位缺陷 → 修复缺陷 → 回归测试 → 继续测试
                                                    ↑______________|
```

## 6. 软件容错与恢复技术

### 6.1 故障-错误-失效链

```
故障(Fault) → 错误(Error) → 失效(Failure)
   │              │              │
 系统内部的    故障表现的    系统对外部
 静态缺陷      异常状态      服务偏离需求
```

**预防策略在三个层面的介入**：
| 层面 | 策略 | 目标 |
|------|------|------|
| 故障预防 | Fault Prevention | 避免引入缺陷 |
| 故障去除 | Fault Removal | 发现并消除已引入的缺陷 |
| 故障容忍 | Fault Tolerance | 缺陷存在时仍能正确运行 |
| 故障预测 | Fault Forecasting | 预测可能发生的故障 |

### 6.2 异常处理模式

| 模式 | 说明 |
|------|------|
| **重试（Retry）** | 操作失败后重新执行（适用于瞬时故障） |
| **回退（Rollback）** | 将状态恢复到故障前的检查点 |
| **降级（Graceful Degradation）** | 关闭非核心功能以维持核心功能 |
| **失效转移（Failover）** | 切换到备用系统/组件 |
| **失效安全（Fail-Safe）** | 无法操作时保持安全状态（如铁路信号变红灯） |
| **补偿事务** | 通过反向操作撤销已完成的部分工作 |

### 6.3 检查点与回滚恢复

```
时间线：
    T1           T2           T3           故障点
────●────────────●────────────●──────────────X──→
 检查点1      检查点2      检查点3      系统崩溃

恢复过程：
────●────────────●────────────●────
 检查点1      检查点2      检查点3   ← 从最近检查点恢复
                                        ← 重新处理T3~故障点间的操作（需日志）
```

**检查点策略**：
- **协调查检点**：所有进程同时保存状态（开销大但恢复简单）
- **独立检查点**：各进程独立保存状态（开销小但恢复复杂，需处理多米诺效应）

### 6.4 分布式系统容错

| 技术 | 说明 |
|------|------|
| **共识算法** | Paxos、Raft：在部分节点故障时保证集群一致性 |
| **状态机复制** | 多副本执行相同操作序列，保持状态一致 |
| **Quorum机制** | 读写需获得多数节点确认（W + R > N） |
| **主备切换** | 主节点故障时从节点接管 |
| **熔断器（Circuit Breaker）** | 远程调用持续失败时快速返回错误，防止级联故障 |
| **舱壁隔离（Bulkhead）** | 隔离资源池，限制故障影响范围 |

## 7. 软件可靠性工程实践

### 7.1 关键系统可靠性要求

| 系统类型 | 可靠性要求 | 典型设计 |
|----------|-----------|---------|
| **安全关键系统**（航空、医疗、核控） | 失效率 < 10^(-9)/小时 | N版本编程 + 形式化验证 |
| **任务关键系统**（金融交易、指挥控制） | 可用性 > 99.99% | 冗余 + 热备 + 容错 |
| **业务关键系统**（ERP、电商） | 可用性 > 99.9% | 集群 + 数据库主备 |
| **一般系统** | 可用性 > 99% | 基本容错机制 |

### 7.2 高可用性度量（"9的个数"）

| 可用性 | 年停机时间 | 俗称 |
|--------|-----------|------|
| 99% (2个9) | 87.6 小时 | — |
| 99.9% (3个9) | 8.76 小时 | — |
| 99.99% (4个9) | 52.56 分钟 | 四个九 |
| 99.999% (5个9) | 5.26 分钟 | 电信级（Carrier Grade） |
| 99.9999% (6个9) | 31.5 秒 | — |

## 8. 常考考点速查

### 8.1 核心公式

| 公式 | 说明 |
|------|------|
| R(t) = e^(-λt) | 恒定失效率下的可靠度（指数分布） |
| MTTF = 1/λ | 恒定失效率下的平均无故障时间 |
| A = MTTF / (MTTF + MTTR) | 可用性计算公式 |
| V(G) = e - n + 2 | McCabe 环路复杂度 |
| R_sys = R₁ × R₂ × ... × Rₙ | 串联系统的可靠度 |
| R_sys = 1 - (1-R₁)(1-R₂)...(1-Rₙ) | 并联系统的可靠度 |

### 8.2 系统可靠性模型

| 结构 | 可靠度公式 | 说明 |
|------|-----------|------|
| **串联系统** | R = ∏Rᵢ | 任一部分失效则系统失效，可靠度 ≤ 最低的部件可靠度 |
| **并联系统** | R = 1 - ∏(1-Rᵢ) | 所有部分都失效系统才失效，可靠度 ≥ 最高的部件可靠度 |
| **串并混合** | 先算并联子系统可靠度，再按串联计算 | — |
| **m/n(G)表决** | R = ΣC(n,i) × R₀^i × (1-R₀)^(n-i) (i=m to n) | n个部件中至少m个正常工作 |

### 8.3 容错技术对比速查

| 技术 | 冗余类型 | 执行方式 | 裁决 | 适用 |
|------|---------|---------|------|------|
| N版本编程 | 软件/空间冗余 | 并行 | 表决器 | 高可靠计算 |
| 恢复块 | 软件/时间冗余 | 顺序 | 验收测试 | 一般容错 |
| 双机热备 | 硬件冗余 | 主备 | 心跳检测 | 服务高可用 |
| 海明码 | 信息冗余 | — | 校验位 | 数据传输/存储 |
| 检查点回滚 | 时间冗余 | 顺序 | — | 长事务、批量处理 |

### 8.4 避错 vs 容错 vs 检错

| 策略 | 时机 | 目标 | 典型技术 |
|------|------|------|---------|
| **避错** | 开发阶段（事前） | 预防缺陷引入 | 形式化方法、强类型、结构化设计 |
| **容错** | 运行阶段（事中） | 含缺陷运行 | NVP、恢复块、冗余 |
| **检错** | 运行阶段（事后检测） | 发现错误存在 | 断言、CRC、看门狗、心跳 |
