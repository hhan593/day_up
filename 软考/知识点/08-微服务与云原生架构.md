# 08 — 微服务与云原生架构

## 1. 微服务架构

### 1.1 单体架构 vs 微服务架构

| 维度 | 单体架构 | 微服务架构 |
|------|---------|-----------|
| 部署 | 整体打包部署 | 每个服务独立部署 |
| 数据 | 单一数据库 | 每个服务独立数据库 |
| 扩展 | 整体扩展 | 按服务粒度扩展 |
| 技术栈 | 统一技术栈 | 每个服务可不同技术栈 |
| 通信 | 进程内调用 | 网络（RPC/HTTP/消息） |
| 故障隔离 | 一个模块崩溃影响全局 | 故障隔离在服务内 |
| 复杂度 | 代码复杂度高 | 分布式系统复杂度高 |
| 团队 | 按职能分工 | 跨职能小团队（每个团队负责1-N个服务） |

### 1.2 微服务拆分原则

- **单一职责**：一个服务只做一件事
- **高内聚低耦合**：服务内高内聚，服务间低耦合
- **按业务能力拆分**（Domain-Driven Design的限界上下文）
- **数据主权**：每个服务拥有自己的数据库
- **团队自治**：一个小团队能独立开发和运维一个服务

### 1.3 微服务架构的核心组件

```
客户端
  │
  ▼
API Gateway ──（路由、认证、限流、日志、聚合）
  │
  ├── 服务A ── 数据库A
  ├── 服务B ── 数据库B
  └── 服务C ── 数据库C
  │
  ▼
基础设施层：
  ├── 注册中心（Nacos/Eureka/Consul）
  ├── 配置中心（Nacos/Apollo/Spring Cloud Config）
  ├── 消息队列（RocketMQ/Kafka）
  ├── 日志收集（ELK/SkyWalking）
  ├── 监控告警（Prometheus + Grafana）
  └── 链路追踪（SkyWalking/Jaeger/Zipkin）
```

## 2. 服务治理

### 2.1 服务注册与发现

- **客户端发现**：客户端从注册中心获取服务列表，自行负载均衡（如Eureka）
- **服务端发现**：客户端通过负载均衡器调用，均衡器查询注册中心（如Nginx+Consul）

### 2.2 配置中心

**核心功能**：
- 配置集中管理
- 动态刷新（无需重启）
- 版本管理
- 灰度发布（不同实例不同配置）
- 权限控制

### 2.3 服务调用与负载均衡

**调用方式**：
- HTTP/REST：通用性强
- RPC：性能好、类型安全
- 异步消息：松耦合、削峰填谷

**客户端负载均衡**：Ribbon（已进入维护模式，被Spring Cloud LoadBalancer替代）

**声明式服务调用**：Feign / OpenFeign

### 2.4 服务容错

**Sentinel/Hystrix 功能对比**：

| 功能 | Hystrix | Sentinel |
|------|---------|----------|
| 熔断 | 支持 | 支持 |
| 限流 | 信号量/线程池 | QPS/并发线程数/响应时间 |
| 降级 | 支持 | 支持 |
| 控制台 | 弱 | 强 |
| 热点参数限流 | 不支持 | 支持 |
| 规则动态修改 | 不支持 | 支持 |
| 状态 | 维护模式 | 活跃 |

### 2.5 服务网关

**API Gateway 功能**：
- **路由转发**：根据URL/Header等规则转发到对应服务
- **认证鉴权**：统一身份认证和权限检查
- **限流熔断**：保护下游服务
- **协议转换**：HTTP ↔ gRPC ↔ WebSocket
- **请求聚合**：将多个服务调用的结果合并返回
- **日志监控**：记录所有请求

## 3. 容器化技术

### 3.1 Docker 核心概念

| 概念 | 说明 |
|------|------|
| **镜像（Image）** | 只读模板，包含运行环境和应用 |
| **容器（Container）** | 镜像的运行实例 |
| **仓库（Registry）** | 镜像存储和分发（Docker Hub / Harbor） |
| **Dockerfile** | 构建镜像的脚本定义 |

### 3.2 虚拟化 vs 容器化

```
传统虚拟化：
  App A | App B
  Guest OS A | Guest OS B
  Hypervisor
  Host OS
  硬件

容器化：
  App A | App B
  Docker Engine
  Host OS
  硬件
```

- 容器共享宿主机内核，启动快（秒级 vs 分钟级），资源占用小
- 虚拟机隔离性更强，每个VM有完整OS

### 3.3 Kubernetes 核心概念

| 概念 | 说明 |
|------|------|
| **Pod** | 最小调度单元，包含一个或多个容器，共享网络和存储 |
| **Service** | 为Pod提供稳定的网络访问入口 |
| **Deployment** | 声明式管理Pod副本和更新策略 |
| **ReplicaSet** | 确保指定数量的Pod副本运行 |
| **ConfigMap/Secret** | 配置信息/密钥管理 |
| **Ingress** | 外部HTTP/HTTPS路由 |
| **Namespace** | 资源隔离的逻辑分区 |
| **StatefulSet** | 有状态应用的Pod管理（如数据库） |
| **DaemonSet** | 每个节点运行一个Pod（如日志收集） |

### 3.4 Kubernetes 架构

```
Master Node：
  ├── API Server（统一入口）
  ├── Scheduler（Pod调度）
  ├── Controller Manager（集群状态管理）
  └── etcd（分布式KV存储，集群状态存储）

Worker Node：
  ├── kubelet（管理Pod生命周期）
  ├── kube-proxy（网络代理和负载均衡）
  └── Container Runtime（如Docker/containerd）
```

## 4. DevOps

### 4.1 DevOps 核心理念

打破开发和运维之间的壁垒，通过自动化实现持续集成和持续交付。

**CALMS 模型**：
- **Culture**：协作文化
- **Automation**：自动化一切
- **Lean**：精益流程
- **Measurement**：度量驱动
- **Sharing**：知识共享

### 4.2 CI/CD

```
代码提交 → 构建 → 单元测试 → 代码扫描 → 制品打包
→ 部署到测试环境 → 自动化测试 → 部署到预发布 → 部署到生产
```

| 概念 | 说明 |
|------|------|
| **CI（持续集成）** | 频繁合并代码到主干，自动构建和测试 |
| **CD（持续交付）** | 代码随时可部署到生产，需要手动批准 |
| **CD（持续部署）** | 代码通过流水线后自动部署到生产 |

### 4.3 发布策略

| 策略 | 说明 |
|------|------|
| **蓝绿部署** | 两套环境（蓝=旧、绿=新），切换路由一键发布 |
| **金丝雀发布** | 少量用户先试新版本，逐步扩大 |
| **滚动更新** | 逐个实例替换，逐步完成更新 |
| **A/B测试** | 不同用户看到不同版本，对比效果 |

## 5. 云原生

### 5.1 云原生五要素（CNCF定义）

1. **容器化**：标准化打包和运行
2. **微服务**：松耦合架构
3. **声明式API**：通过声明期望状态而非写控制流程
4. **服务网格**：将服务通信下沉到基础设施层
5. **不可变基础设施**：配置变更通过替换实例而非修改现有实例

### 5.2 十二要素（12-Factor App）

| 要素 | 说明 |
|------|------|
| I. 基准代码 | 一份代码，多次部署 |
| II. 依赖 | 显式声明依赖关系 |
| III. 配置 | 配置存储在环境变量中 |
| IV. 后端服务 | 将后端服务视为附加资源 |
| V. 构建、发布、运行 | 严格分离构建和运行阶段 |
| VI. 进程 | 无状态进程 |
| VII. 端口绑定 | 通过端口绑定提供服务 |
| VIII. 并发 | 通过进程模型横向扩展 |
| IX. 易处理 | 快速启动和优雅终止 |
| X. 环境等价 | 尽可能保持开发/预发/生产环境相同 |
| XI. 日志 | 将日志作为事件流 |
| XII. 管理进程 | 管理任务作为一次性进程 |

### 5.3 服务网格（Service Mesh）

将服务间的通信层下沉到基础设施（Sidecar模式）：

```
服务A [容器] → [Sidecar Proxy(Envoy)]
    ↕                          ↕
服务B [容器] → [Sidecar Proxy(Envoy)]
```

**功能**：流量管理、服务发现、负载均衡、安全通信（mTLS）、可观察性、故障注入

**主流实现**：Istio、Linkerd

## 6. 架构演进模式

### 6.1 单体 → 微服务演进

```
单体应用
  → 模块化单体（明确模块边界）
  → 宏服务（抽出几个独立部署的大服务）
  → 微服务（按限界上下文拆分）
```

### 6.2 绞杀者模式（Strangler Fig Pattern）

新系统逐步替换旧系统，新旧并存：

```
初期：用户 → 网关 → 旧系统（所有请求）
中期：用户 → 网关 → 旧系统（大部分）
                 → 新服务A（小部分）
后期：用户 → 网关 → 新服务（大部分）
                 → 旧系统（待移除）
```

### 6.3 微服务反模式

| 反模式 | 说明 | 风险 |
|--------|------|------|
| **过早拆分** | 业务不明确时强行拆微服务 | 改造成本远超收益 |
| **烟囱式服务** | 服务间孤岛，数据不流通 | 重复开发、数据不一致 |
| **分布式单体** | 表面微服务但强依赖，不能独立部署 | 兼具两种架构的缺点 |
| **数据湖** | 多个服务共享一个数据库 | 紧耦合、无法独立演进 |
| **过度拆分** | 服务太细，网络开销大于业务逻辑 | 性能差、调试难 |

### 6.4 微内核架构

**核心系统 + 插件**

- **核心系统**：提供最小可用功能、插件管理机制
- **插件**：扩展功能，与核心和其他插件松耦合
- **适用**：需要持续功能扩展的产品（Eclipse、操作系统、产品化平台）

## 7. 性能优化体系

### 7.1 性能指标

| 指标 | 含义 |
|------|------|
| **QPS/TPS** | 每秒查询数 / 每秒事务数 |
| **RT（响应时间）** | 请求到响应的时间间隔 |
| **并发用户数** | 同一时刻与系统交互的用户数 |
| **吞吐量** | 单位时间内处理的请求数 |
| **95/99分位延迟** | 95%/99%的请求在多少时间内完成 |

### 7.2 常见性能优化方向

| 方向 | 技术手段 |
|------|---------|
| **前端优化** | CDN、资源压缩、懒加载、浏览器缓存 |
| **网络** | 减少请求、连接池、HTTP/2多路复用 |
| **应用层** | 缓存（本地/远程）、异步、池化、并行 |
| **数据库** | 索引优化、SQL调优、读写分离、分库分表 |
| **系统层** | 内核参数调优、零拷贝 |

## 8. 高可用架构

### 8.1 高可用衡量

- 可用性 = MTTF / (MTTF + MTTR)
- 99.9%（3个9）= 年不可用约8.76小时
- 99.99%（4个9）= 年不可用约52.56分钟
- 99.999%（5个9）= 年不可用约5.26分钟

### 8.2 高可用技术栈

| 层次 | 技术 |
|------|------|
| DNS | 多IP解析 |
| 接入层 | 反向代理、LVS/Keepalived（VIP漂移）、Nginx主备 |
| 网关层 | API Gateway集群 |
| 服务层 | 多实例+注册中心+负载均衡 |
| 数据层 | 主从复制、读写分离、集群分片 |
| 中间件 | 集群、哨兵模式 |
| 基础设施 | 多机房、多地域 |
