# 01 — 软件工程基础

## 1. 软件工程核心概念

### 1.1 软件的定义与特点

软件 = 程序 + 数据 + 文档。

软件四大特性：
- **复杂性**：软件是逻辑产品而非物理产品，复杂度随规模指数级增长
- **一致性**：软件必须与现有系统、接口、规范保持一致
- **可变性**：软件易于修改，导致持续变更的预期成为常态
- **不可见性**：软件不可视化，难以用几何模型表达

### 1.2 软件工程的定义

软件工程是将系统化的、规范的、可量化的方法应用于软件的开发、运行和维护，即将工程化方法应用于软件。

**软件工程三要素**：方法 + 工具 + 过程。

### 1.3 软件生命周期

各模型对阶段的划分略有差异，核心阶段包括：

```
问题定义 → 可行性研究 → 需求分析 → 概要设计 → 详细设计
→ 编码实现 → 测试 → 部署 → 运行维护 → 退役
```

**各阶段核心产出：**
| 阶段 | 主要产出物 |
|------|-----------|
| 可行性研究 | 可行性分析报告 |
| 需求分析 | 需求规格说明书（SRS） |
| 概要设计 | 概要设计说明书、架构文档 |
| 详细设计 | 详细设计说明书、类/模块设计 |
| 编码实现 | 源代码、单元测试报告 |
| 测试 | 测试计划、测试用例、缺陷报告 |
| 部署 | 部署方案、运维手册 |
| 维护 | 变更记录、升级文档 |

## 2. 软件过程模型

### 2.1 瀑布模型

- **特点**：严格的线性顺序，阶段间有文档驱动的里程碑
- **适用**：需求稳定、规模中小、安全关键系统（航天、医疗、银行核心）
- **变体**：带反馈环的瀑布模型

### 2.2 V模型

- **核心思想**：开发与测试一一对应
- **左侧（开发）**：需求分析 → 概要设计 → 详细设计 → 编码
- **右侧（测试）**：单元测试 ← 集成测试 ← 系统测试 ← 验收测试
- **关键对应关系**：
  - 需求分析 ↔ 验收测试
  - 概要设计 ↔ 系统测试
  - 详细设计 ↔ 集成测试
  - 编码 ↔ 单元测试

### 2.3 增量模型

- **核心**：将系统划分为多个增量构件，每个增量独立开发测试后集成
- **特点**：第一个增量通常是核心功能，后续增量逐步添加能力
- **优势**：核心功能快速交付，每个增量都是一次学习机会
- **适用**：需求基本稳定、工期紧张的项目

### 2.4 螺旋模型

- **核心循环**：制定计划 → 风险分析 → 实施工程 → 客户评估
- **关键特征**：以**风险驱动**为核心
- **风险分析活动**：识别风险、分析风险、制定缓解策略、监控风险
- **适用**：大型、高风险、需求不确定的项目（航天、国防）

### 2.5 敏捷开发

**敏捷宣言四条价值观：**
1. 个体和互动 > 流程和工具
2. 工作的软件 > 详尽的文档
3. 客户合作 > 合同谈判
4. 响应变化 > 遵循计划

**12条原则要点：** 尽早持续交付、欢迎需求变化、频繁交付、业务与开发协作、面对面交流、可持续开发等。

**Scrum 角色与仪式：**
- **三角色**：Product Owner（定义需求优先级）、Scrum Master（保障流程）、开发团队（自组织）
- **五仪式**：Sprint计划会、每日站会、Sprint评审会、Sprint回顾会、Product Backlog梳理
- **三工件**：Product Backlog、Sprint Backlog、可工作增量

**极限编程（XP）五大价值观**：沟通、简单、反馈、勇气、尊重

**XP 核心实践**：
- 计划游戏、小型发布、隐喻
- 简单设计、测试驱动开发（TDD）、重构
- 结对编程、代码集体所有、持续集成
- 每周40小时工作制、现场客户、编码标准

## 3. 软件过程能力成熟度模型

### 3.1 CMMI 成熟度等级

| 等级 | 名称 | 特征 |
|------|------|------|
| 1级 | 初始级 | 过程无序，成功依赖个人能力 |
| 2级 | 已管理级 | 项目级管理，需求、计划、配置、质量有管理 |
| 3级 | 已定义级 | 组织级标准过程，过程标准化 |
| 4级 | 量化管理级 | 过程度量、量化控制 |
| 5级 | 优化级 | 持续改进，缺陷预防 |

### 3.2 CMMI 过程域

CMMI 3级覆盖22个过程域，分为四类：
- **过程管理**（5个）：OPF、OPD、OT、OPP、OID
- **项目管理**（6个）：PP、PMC、SAM、IPM、RSKM、QPM
- **工程**（5个）：RD、TS、PI、VER、VAL
- **支持**（6个）：CM、PPQA、MA、CAR、DAR

## 4. 软件开发方法对比

| 维度 | 结构化方法 | 面向对象方法 | 敏捷方法 |
|------|-----------|-------------|----------|
| 核心思想 | 自顶向下分解 | 对象+消息传递 | 迭代增量+持续反馈 |
| 分析工具 | DFD、ER图、状态图 | 用例图、类图、时序图 | User Story |
| 设计 | 模块化、高内聚低耦合 | 类设计、设计模式 | 简单设计、持续重构 |
| 变更响应 | 较差 | 一般 | 优秀 |
| 文档程度 | 高 | 中高 | 够用就好 |

**其他方法**：
- **原型法**：快速构建原型验证需求，适用于需求模糊的前端项目
- **面向服务方法**：以服务为基本单元，强调松耦合和互操作性
- **领域驱动设计（DDD）**：聚焦核心域模型，战略设计+战术设计
- **模型驱动架构（MDA）**：CIM → PIM → PSM → 代码，模型变换驱动

## 5. 软件重用

### 5.1 重用级别

- **代码级重用**：函数库、类库、组件
- **设计级重用**：设计模式、架构风格、框架
- **分析级重用**：领域模型、需求模式
- **测试级重用**：测试用例、测试脚本

### 5.2 重用形式

- **黑盒重用**：不修改，直接使用（如第三方库）
- **白盒重用**：可修改内部实现（如开源框架定制）
- **组合重用**：组合多个已有组件形成新系统

| 概念 | 定义 |

## 7. 软件项目管理基础

### 7.1 COCOMO 成本估算模型

- **基本COCOMO**：仅用代码行数（KLOC）估算
- **中级COCOMO**：引入15个成本驱动因子（产品属性、硬件属性、人员属性、项目属性）
- **详细COCOMO**：按开发阶段分别考虑成本因子

### 7.2 项目进度管理

**关键路径法（CPM）**：
- 总时差（Total Float）= 最晚开始 - 最早开始
- 关键路径上的活动总时差为0，是决定项目最短工期的路径

**Gantt图**：直观展示任务开始/结束时间和依赖关系

**PERT估算**：
- 期望时间 t = (乐观 + 4×最可能 + 悲观) / 6
- 标准差 σ = (悲观 - 乐观) / 6

### 7.3 团队组织模式

| 模式 | 特点 | 适用场景 |
|------|------|---------|
| 主程序员团队 | 1个主程序员+n个辅助 | 小团队、技术强依赖 |
| 民主团队 | 平等无领导 | 研究型、创新项目 |
| 层级团队 | 分层管理 | 大型项目 |

## 9. 软件风险管理

**风险管理过程**：风险识别 → 风险分析（概率×影响） → 风险计划 → 风险监控

**风险类别**：
- **项目风险**：进度、资源、预算
- **技术风险**：技术方案不可行、性能不达标
- **商业风险**：市场变化、政策法规
- **外部风险**：供应商、合作方

**十大常见风险（Boehm）**：需求变更、进度紧张、人员不足、技术方案不合理、性能问题等。

## 10. 软件构件技术

> 系统架构设计师考点：构件的定义、构件模型标准、构件的获取与复用

### 10.1 构件的定义与特征

**构件（Component）**：软件系统中具有相对独立功能、可明确识别、可复用的基本组成单元。

**构件的核心特征**：

| 特征 | 说明 |
|------|------|
| **可复用** | 可在多个系统中使用，无需或仅需少量修改 |
| **可组装** | 通过接口与其他构件组合形成更大的系统 |
| **可部署** | 作为独立的部署单元 |
| **可替换** | 接口兼容的构件可互相替换 |
| **自包含** | 功能内聚，对外隐藏实现细节 |
| **独立性** | 不依赖特定运行环境、编程语言或上下文 |

**构件 vs 对象**：

| 维度 | 对象（Object） | 构件（Component） |
|------|--------------|------------------|
| 粒度 | 细粒度（一个类） | 粗粒度（一组类/模块） |
| 复用范围 | 通常限于同一项目/语言 | 跨项目、跨语言、跨平台 |
| 依赖 | 与具体实现耦合 | 仅依赖接口 |
| 部署 | 随应用一起编译部署 | 可独立部署和升级 |

### 10.2 构件模型标准

**构件模型**定义了构件的接口规范、组装机制、部署方式和容器服务。

| 标准 | 提出者 | 语言 | 核心组件 |
|------|--------|------|---------|
| **EJB** | Sun/Oracle | Java | Session Bean、Entity Bean、Message-Driven Bean |
| **COM/DCOM** | Microsoft | 语言无关（Windows） | COM组件、DCOM分布式扩展 |
| **.NET组件** | Microsoft | 多语言（CLR） | Assembly（程序集） |
| **CCM** | OMG | 语言无关 | CORBA Component Model |
| **OSGi** | OSGi Alliance | Java | Bundle、Service Registry |

**EJB 容器提供的服务**：声明式事务管理、安全管理、持久化、远程访问、并发控制、生命周期管理。

**COM 核心接口**：`IUnknown`（所有COM组件的根接口，包含 `QueryInterface`、`AddRef`、`Release`）。

**.NET Assembly vs COM**：Assembly 不需要注册表注册（XCopy部署），支持版本并行（Side-by-side），解决了"DLL Hell"问题。

### 10.3 构件的获取方式

| 方式 | 说明 | 优势 | 风险 |
|------|------|------|------|
| **自行开发** | 团队内部开发构件 | 完全可控、匹配需求 | 成本高、周期长 |
| **购买现成构件（COTS）** | 购买第三方商业构件 | 快速获取、成本可控 | 功能可能不匹配、供应商依赖 |
| **开源构件** | 使用开源社区的构件 | 免费、可定制 | 质量参差不齐、许可证合规 |
| **逆向工程提取** | 从遗留系统中提取可复用构件 | 保护投资、复用已有资产 | 技术难度大 |
| **外包定制** | 委托第三方开发 | 专业性强 | 沟通成本、交付质量 |

### 10.4 基于构件的软件开发（CBSD）

**CBSD 核心流程**：
```
构件需求分析 → 构件获取/开发 → 构件鉴定/测试 → 构件组装 → 系统测试 → 演化维护
```

**构件组装方式**：
| 组装方式 | 说明 |
|----------|------|
| **顺序组装** | 已存在构件按顺序调用组合 |
| **层次组装** | 提供构件接口的层次化关联 |
| **叠加组装** | 多个构件叠加实现新功能 |

**CBSD 优势**：缩短开发周期、降低成本、提高质量（构件经过验证）、增强系统灵活性。

**CBSD 挑战**：构件选择困难、构件集成复杂度、构件演化管理、安全性评估。

## 12. 软件维护

> 系统架构设计师考点：软件维护分类、可维护性因素、维护成本

### 12.1 软件维护分类

| 类型 | 占比 | 定义 | 示例 |
|------|------|------|------|
| **纠错性维护** | ~17% | 修正已发现的错误和缺陷 | 修复Bug、修正计算错误 |
| **适应性维护** | ~18% | 适应外部环境变化（硬件/软件平台升级） | 数据库升级、OS升级、JDK版本升级 |
| **完善性维护** | ~60% | 增强已有功能和性能 | 增加新功能、优化性能、改进UI |
| **预防性维护** | ~5% | 预防未来可能的故障 | 重构、文档更新、代码优化 |

> 完善性维护占比最大（~60%），是软件维护的主要形式。

### 12.2 可维护性影响因素

| 因素 | 说明 |
|------|------|
| **可理解性** | 代码和文档是否易于理解 |
| **可测试性** | 修改后是否易于回归测试 |
| **可修改性** | 局部修改是否影响全局 |
| **可靠性** | 修改后是否仍稳定运行 |
| **可移植性** | 系统是否易于迁移到新平台 |

### 12.3 软件维护策略

| 策略 | 说明 |
|------|------|
| **结构化维护** | 有完整文档和设计规范，按流程修改，成本较低 |
| **非结构化维护** | 只有源代码无文档，先逆向理解再修改，成本高 |

**维护成本模型**：维护成本 = 理解代码成本 + 修改代码成本 + 回归测试成本 + 文档更新成本。

## 13. 遗留系统的处置策略

> 系统架构设计师高频考点

对遗留系统的评估从**业务价值**和**技术质量**两个维度进行，形成四种策略：

| | 高技术质量 | 低技术质量 |
|------|-----------|-----------|
| **高业务价值** | **① 改造（Evolve）** | **② 再工程/现代化（Re-engineering）** |
| **低业务价值** | **③ 集成/合并（Integrate）** | **④ 淘汰/废弃（Eliminate）** |

**四种策略详解**：

| 策略 | 条件 | 做法 | 目标 |
|------|------|------|------|
| **改造/演化** | 业务价值高 + 技术质量高 | 局部增强、功能扩展、技术升级 | 使系统持续满足业务需求 |
| **再工程/现代化** | 业务价值高 + 技术质量低 | 全面重构或迁移新技术栈 | 提高技术质量以支撑业务发展 |
| **集成/合并** | 业务价值低 + 技术质量高 | 集成到其他系统，减少独立维护成本 | 复用技术资产 |
| **淘汰/废弃** | 业务价值低 + 技术质量低 | 终止维护，数据迁移，系统下线 | 释放资源，降低TCO |

**遗留系统现代化技术**：
- **封装**：为遗留系统包装新接口（如RESTful API）
- **重构**：改善内部结构但不改变外部行为
- **平台迁移**：从旧平台（大型机）迁移到新平台（云）
- **语言翻译**：从旧语言（COBOL）转换为新语言（Java）

| 可行性研究 | 可行性分析报告 |
| 需求分析 | 需求规格说明书（SRS）、用户故事、用例文档 |
| 概要设计 | 概要设计说明书、架构文档（AD）、接口规范 |
| 详细设计 | 详细设计说明书、数据库设计文档、模块设计文档 |
| 编码 | 源代码（含注释）、README、API文档 |
| 测试 | 测试计划、测试用例、测试报告、缺陷报告 |
| 部署 | 部署方案、运维手册、系统管理员手册 |
| 维护 | 变更日志、版本发布说明（Release Notes）、知识库 |

### 14.3 文档质量属性

- **准确性**：内容与系统实际行为一致
- **完整性**：覆盖所有必要信息
- **一致性**：不同文档之间的描述不矛盾
- **及时性**：与系统版本同步更新
- **可读性**：结构清晰、语言准确、图表适当

## 15. 软件工程标准化

### 15.1 标准分类

| 分类 | 说明 | 典型标准 |
|------|------|---------|
| **国际标准** | ISO/IEC发布的全球性标准 | ISO/IEC 12207（软件生命周期过程）、ISO/IEC 25010（质量模型） |
| **国家标准** | 各国发布的国内标准 | GB/T 8566（中国-软件生存周期过程）、GB 17859（安全等级划分） |
| **行业标准** | 特定行业的标准 | IEEE 830（SRS编写指南）、MIL-STD-498（美军标） |
| **企业标准** | 企业/组织内部标准 | 编码规范、命名约定、内部流程规范 |
| **事实标准** | 市场广泛采用的非正式标准 | RESTful API规范、Git工作流 |

### 15.2 软件工程关键标准速查

| 标准编号 | 标准名称 | 核心内容 |
|----------|---------|---------|
| **ISO/IEC 12207** | 软件生命周期过程 | 定义软件生存周期的过程框架（4类过程组17个过程） |
| **ISO/IEC 25010** | 系统与软件质量模型 | 8大质量特性（替代ISO/IEC 9126） |
| **ISO/IEC 42010** | 系统和软件架构描述 | 架构描述标准（前身为IEEE 1471） |
| **ISO 9001** | 质量管理体系要求 | 通用的质量管理标准 |
| **ISO/IEC 27001** | 信息安全管理体系 | ISMS 信息安全管理要求 |
| **IEEE 830** | SRS推荐实践 | 需求规格说明书的编写指南 |
| **IEEE 1016** | SDD推荐实践 | 软件设计描述的编写指南 |
| **GB/T 8566** | 软件生存周期过程 | 中国软件过程标准（等同采用ISO/IEC 12207） |
| **GB/T 16260** | 软件质量度量 | 对应ISO/IEC 9126 |
| **GB 17859** | 安全保护等级划分标准 | 计算机信息安全保护五级 |
| **GB/T 22239** | 网络安全等级保护（等保） | 等保2.0标准 |

### 15.3 ISO/IEC 12207 软件生命周期过程组

```
过程组:
  ├── 协议过程（获取、供应）
  ├── 组织级项目使能过程
  ├── 技术管理过程（项目管理、风险管理、配置管理、质量保证等）
  └── 技术过程（需求分析、设计、编码、测试、运维等）
```
