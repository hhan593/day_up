# 04 — 软件测试与质量保障

## 1. 软件测试基础

### 1.1 测试定义与目的

测试是为发现错误而执行程序的过程。

**核心观点**：
- 测试证明的是缺陷的存在，而不是没有缺陷
- 穷举测试不可能
- 测试应尽早介入（需求阶段就可以开始测试活动）
- 缺陷具有群集效应（少数模块包含大部分缺陷）
- 杀虫剂悖论（同一组测试反复使用会降低有效性）

### 1.2 测试层级（V模型视角）

```
需求分析 ────────── 验收测试（α测试/β测试）
    │                    │
概要设计 ────────── 系统测试
    │                    │
详细设计 ────────── 集成测试
    │                    │
编码实现 ────────── 单元测试
```

## 2. 测试方法与策略

### 2.1 按是否执行程序分类

| 方法 | 说明 | 常用技术 |
|------|------|---------|
| 静态测试 | 不运行代码，通过检查、评审 | 代码审查、静态分析工具、走查 |
| 动态测试 | 运行代码，输入测试数据检查输出 | 白盒/黑盒测试 |

### 2.2 黑盒测试（功能/数据驱动测试）

不关心内部实现，仅通过输入输出来验证功能。

**黑盒测试方法**：

| 方法 | 说明 | 示例 |
|------|------|------|
| **等价类划分** | 将输入域划分为若干等价类，每类取一个代表值测试。分有效等价类和无效等价类 | 年龄1-120：有效类[1,120]、无效类<1和>120 |
| **边界值分析** | 对等价类的边界值进行测试 | 范围[0,100]：测-1、0、50、100、101 |
| **决策表** | 将条件组合和动作对应，穷举所有规则 | 登录条件组合：用户名存在/不存在 × 密码正确/错误 |
| **因果图** | 输入条件的组合→果，转化为判定表后再设计用例 | 多个输入条件相互影响时 |
| **正交实验法** | 从大量组合中选取代表性样本 | 3因子2水平，用L4(2^3)只需4个用例而非8个 |
| **状态迁移法** | 基于状态图设计测试路径 | 订单状态：待支付→已支付→已发货→已完成 |
| **场景法** | 基于业务流程设计测试路径 | 用户下单完整流程：浏览→加购→结算→支付 |
| **错误推测法** | 基于经验猜测容易出错的点 | 空值、特殊字符、超长输入 |

**等价类划分步骤**：
1. 识别输入条件
2. 为每个条件划分等价类（有效+无效）
3. 为每个等价类编号
4. 设计测试用例：一个用例覆盖多个有效等价类，每个无效等价类单独一个用例

**边界值分析原则**：若输入范围[a,b]，测试 a-1, a, a+1, (a+b)/2, b-1, b, b+1。

### 2.3 白盒测试（结构/逻辑驱动测试）

基于代码内部结构设计测试用例。

**白盒测试方法**：

| 方法 | 说明 | 覆盖率计算 |
|------|------|-----------|
| **语句覆盖** | 每条可执行语句至少执行一次 | 被执行语句数 / 总语句数 |
| **判定(分支)覆盖** | 每个判定的真/假分支至少走一次 | 被执行分支数 / 总分支数 |
| **条件覆盖** | 每个条件的所有可能取值至少出现一次 | 被覆盖条件取值 / 总条件取值 |
| **判定/条件覆盖** | 同时满足判定覆盖和条件覆盖 | — |
| **条件组合覆盖** | 每个判定的所有条件取值组合至少出现一次 | — |
| **路径覆盖** | 覆盖每条可能的执行路径 | 被执行路径数 / 总路径数 |

**覆盖强度排序**：
```
语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖
```

**白盒测试示例**：
```c
if (a > 0 && b > 0)  // 判定1：两个条件a>0, b>0
    x = x / a;
if (c == 1 || d > 0)  // 判定2：两个条件c==1, d>0
    x = x + 1;
```

| 覆盖类型 | 用例要求 |
|----------|---------|
| 语句覆盖 | 两个if体都执行即可 |
| 判定覆盖 | 判定1取真/假 + 判定2取真/假（4种） |
| 条件覆盖 | a>0真/假、b>0真/假、c==1真/假、d>0真/假 |
| 条件组合覆盖 | 8种条件组合（2^3，判定1含2个条件=4种，判定2含2个条件=4种） |

**McCabe基本路径法**：
1. 画出程序控制流图（节点=顺序语句块，边=控制流向）
2. 计算环路复杂度 V(G) = e - n + 2 或 V(G) = P + 1（P=判定节点数）或 V(G) = 封闭区域数+1
3. 确定V(G)条独立路径（独立路径=至少一条边是其他路径未覆盖的）
4. 为每条路径设计测试用例

## 3. 测试阶段与类型

### 3.1 按阶段划分

| 阶段 | 测试对象 | 测试目标 | 执行者 |
|------|---------|---------|--------|
| 单元测试 | 单个模块/函数 | 模块功能正确 | 开发人员 |
| 集成测试 | 模块间接口 | 模块协作正确 | 测试/开发 |
| 系统测试 | 完整系统 | 满足需求规格 | 独立测试团队 |
| 验收测试 | 可交付系统 | 满足用户期待 | 用户/客户 |

### 3.2 集成测试策略

| 策略 | 方法 | 优缺点 |
|------|------|--------|
| **非增量式（大爆炸）** | 所有模块一次集成测试 | 简单但定位难 |
| **自顶向下** | 从主控模块开始逐步集成 | 需要桩（Stub）模拟下层 |
| **自底向上** | 从底层模块开始逐步集成 | 需要驱动（Driver）模拟上层 |
| **三明治** | 上层自顶向下+下层自底向上，中间汇合 | 综合两者优势 |

### 3.3 按测试目标分类

| 类型 | 测试内容 |
|------|---------|
| **功能测试** | 是否满足功能需求 |
| **性能测试** | 响应时间、吞吐量、资源占用 |
| **负载测试** | 在预期工作负载下的表现 |
| **压力测试** | 超过设计极限时的行为（何时崩溃、如何恢复） |
| **容错/恢复测试** | 故障后恢复能力 |
| **安全测试** | 抵御非法入侵、数据保护 |
| **兼容性测试** | 不同平台/浏览器/设备的表现 |
| **易用性测试** | 用户界面友好度、学习成本 |
| **回归测试** | 确认修改未影响已有功能 |
| **冒烟测试** | 快速验证基本功能是否工作（用于判断是否可进入全面测试） |

## 4. 面向对象的测试

### 4.1 OO测试层次

```
类测试（相当于单元测试）→ 集成测试（类簇测试）→ 系统测试
```

### 4.2 OO测试的特点

- 测试的基本单元从函数变为类
- 需要考虑继承、多态对测试的影响
- 封装性导致测试时需要更多的访问方法
- 类之间通过消息协作，集成测试更关注消息序列
- 状态测试比结构化测试更重要（对象有状态记忆）

### 4.3 OO测试方法

- **基于状态的测试**：用状态图推导测试用例，覆盖状态转换路径
- **基于场景的测试**：用时序图描述典型交互场景，设计测试用例
- **基于继承的测试**：测试子类时重用父类测试用例并扩展
- **类层次测试**：测试类簇中的协作行为

## 6. 软件质量度量

### 6.1 缺陷度量

| 度量 | 含义 |
|------|------|
| 缺陷密度 | 缺陷数 / 规模（KLOC或FP），行业均值约1-25个/KLOC |
| 缺陷移除率（DRE） | 阶段发现的缺陷 / (阶段发现的 + 后续发现的) |
| 平均失效时间（MTTF） | 两次失效间的平均运行时间 |
| 平均修复时间（MTTR） | 从失效到修复恢复的平均时间 |

### 6.2 Halstead软件科学度量

基于代码的运算符和操作数计数：
- n₁ = 不同运算符数，n₂ = 不同操作数数
- N₁ = 运算符总数，N₂ = 操作数总数
- 程序词汇量 n = n₁ + n₂
- 程序长度 N = N₁ + N₂
- **程序量 V = N × log₂(n)**（最小单位是比特）
- 难度 D = (n₁/2) × (N₂/n₂)
- **工作量 E = D × V**
- 错误预估数 B = V / 3000

## 7. 软件可靠性

> 详见 [10-软件可靠性基础知识.md](10-软件可靠性基础知识.md)，此处仅保留测试关联部分

### 7.1 可靠性模型

| 模型 | 特点 |
|------|------|
| **Jelinski-Moranda** | 假设初始错误数为常数，每次修复减少一个错误，失效率与剩余错误数成正比 |
| **Goel-Okumoto** | 累计错误发现数遵循非齐次泊淞过程（NHPP） |
| **Musa执行时间模型** | 用CPU执行时间而非日历时间度量可靠性 |
| **Littlewood-Verrall** | 考虑修复可能引入新错误的不确定性 |

### 7.2 可靠性测试

**可靠性测试目的**：验证系统在给定时间内达到规定的可靠性水平。

**操作剖面（Operational Profile）**：系统实际使用中各操作的发生概率分布。可靠性测试必须基于操作剖面设计用例，否则测试结果不能反映实际可靠性。

**可靠性增长测试**：在测试-修复-再测试循环中，可靠性随缺陷修复逐步提高的过程。

### 7.3 可靠性技术

| 技术 | 说明 |
|------|------|
| **避错** | 预防性技术：严格过程、形式化方法 |
| **容错** | 运行时应对故障：冗余（N版本编程、恢复块） |
| **检错** | 运行时检测：断言、守护进程、心跳 |

## 8. 软件评审与审查

### 8.1 Fagan正式审查

**6个步骤**：
1. 计划：确定审查范围和参与者，准备审查包
2. 概述：作者介绍审查对象的背景和动机
3. 准备：审查员独立逐行阅读审查对象，记录问题和疑问
4. 审查会议：逐项检查，记录缺陷。**注意**：不讨论解决方案，只找问题
5. 返工：作者修改所有记录在案的缺陷
6. 跟踪：主持人检查返工是否充分，决定是否需要重新审查

**正式审查检查项**：
- 是否符合需求规格
- 逻辑是否正确
- 是否遗漏异常处理
- 是否有潜在性能问题
- 是否符合编码/设计规范

### 8.2 评审角色

- **主持人**：推进流程，控制节奏，不是作者本人
- **作者**：回答疑问，澄清意图
- **评审员**：找出缺陷（2-5人）
- **记录员**：记录所有缺陷和问题
- **经理**：了解情况（可选，不在审查会议中参与，以免被评审者感到压力）

### 8.3 评审类型对比

| 类型 | 正式度 | 主持 | 准备 | 输出 | 适用 |
|------|--------|------|------|------|------|
| **审查（Inspection）** | 高 | 主持人（非作者） | 充分准备 | 正式缺陷清单+报告 | 关键模块 |
| **技术评审（TR）** | 中 | 技术负责人 | 中等准备 | 技术意见 | 设计/方案 |
| **走查（Walkthrough）** | 低 | 作者 | 轻微准备 | 非正式反馈 | 早期获取反馈 |

## 9. 测试驱动开发与BDD

### 9.1 TDD（Test-Driven Development）

**TDD 三步循环（Red-Green-Refactor）**：
```
① Red：编写一个失败的测试（描述期望行为）
        ↓
② Green：编写最小代码让测试通过
        ↓
③ Refactor：重构代码，保持测试通过
        ↓  循环回 ①
```

**TDD 三条法则**：
1. 在没有失败的测试之前不要写任何业务代码
2. 只编写恰好能让一个测试失败的测试代码
3. 只编写恰好能让测试通过的业务代码

**TDD 优势**：高测试覆盖率、可测试的设计、回归保护网、快速反馈。

### 9.2 BDD（Behavior-Driven Development）

**BDD**：TDD 的演进，用自然语言描述期望行为，让非技术人员也能理解和参与。

**BDD 三段式（Gherkin语法）**：
```gherkin
Feature: 用户登录
  Scenario: 正确的用户名和密码登录成功
    Given 用户在登录页面
    When 输入正确的用户名 "admin" 和密码 "123456"
    Then 跳转到首页，显示 "欢迎, admin"
```

**BDD vs TDD**：
| 维度 | TDD | BDD |
|------|-----|-----|
| 关注点 | 代码行为正确性 | 业务行为期望 |
| 语言 | 编程语言（JUnit/assert） | 领域语言（Gherkin/Cucumber） |
| 参与者 | 开发人员 | 开发+QA+业务 |
| 粒度 | 单元测试为主 | 端到端场景为主 |

### 9.3 ATDD（验收测试驱动开发）

在开发前先与业务方协作编写验收测试，确保团队对"完成"有一致理解。验收测试驱动整个Sprint的开发。

## 10. 测试管理

### 10.1 测试过程

```
测试计划 → 测试设计 → 测试实现（编写用例/脚本）
→ 测试执行 → 缺陷管理 → 测试报告
```

### 10.2 测试计划核心内容

| 内容 | 说明 |
|------|------|
| 测试范围 | 测试什么、不测试什么 |
| 测试策略 | 用哪些测试方法/级别 |
| 资源安排 | 谁测试、需要什么环境 |
| 进度安排 | 测试各阶段的时间表 |
| 风险与应对 | 测试可能遇到的阻塞和预案 |
| 准入/准出条件 | 什么时候开始测试 / 什么时候结束测试 |

**测试准出条件示例**：无P0/P1缺陷、代码覆盖率≥80%、所有验收用例通过、回归测试通过。

### 10.3 缺陷生命周期

```
新建(New) → 已分配(Assigned) → 已修复(Fixed) → 已验证(Verified) → 关闭(Closed)
                      ↓                        ↓
                  拒绝(Rejected)          重新打开(Reopened)
```

**缺陷严重性 vs 优先级**：
| 维度 | 严重性（Severity） | 优先级（Priority） |
|------|-------------------|-------------------|
| 含义 | 对系统功能的影响程度 | 修复的紧迫程度 |
| 确定者 | 测试人员 | 项目经理/产品经理 |
| 典型分类 | P0(崩溃)-P3(建议) | P0(紧急)-P3(低) |
| 示例 | 支付功能崩溃=高严重性 | 页面排版错误=低优先级 |

### 10.4 测试自动化

- **适合自动化的**：回归测试、性能测试、接口测试、数据驱动测试、冒烟测试
- **不适合自动化的**：可用性测试、探索性测试、一次性测试、需求不稳定的新功能
- **自动化金字塔**：单元测试（最多最底层）> 接口/服务测试（中间层）> UI测试（最少顶层）

**自动化覆盖率目标**：
| 层级 | 推荐比例 | 目的 |
|------|---------|------|
| 单元测试 | 60-70% | 快速反馈、低成本 |
| 接口/集成测试 | 20-30% | 服务协作验证 |
| UI端到端测试 | 10% | 关键用户路径 |

### 10.5 测试度量

| 度量 | 含义 | 公式/计算 |
|------|------|----------|
| **测试覆盖率** | 代码被测试覆盖的程度 | (被执行的行/分支/路径) / 总数 |
| **缺陷密度** | 单位规模的缺陷数 | 缺陷数 / KLOC 或 功能点数 |
| **缺陷移除效率(DRE)** | 测试阶段发现的缺陷占比 | 本阶段发现缺陷 / (本阶段+后阶段)总缺陷 |
| **测试用例通过率** | 测试执行通过的比例 | 通过数 / 执行总数 |
| **缺陷发现率** | 单位时间发现的缺陷数 | 缺陷数 / 测试执行时间 |
| **逃逸缺陷率** | 发布到生产后才发现的缺陷占比 | 生产缺陷 / 总缺陷 |
