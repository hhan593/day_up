# 04 — 软件测试与质量保障

## 1. 软件测试基础

### 1.1 测试定义与目的

测试是为发现错误而执行程序的过程。

**核心观点**：
- 测试证明的是缺陷的存在，而不是没有缺陷
- 穷举测试不可能
- 测试应尽早介入（需求阶段就可以开始测试活动）
- 缺陷具有群集效应（少数模块包含大部分缺陷）
- 杀虫剂悖论（同一组测试反复使用会降低有效性）

### 1.2 测试层级（V模型视角）

```
需求分析 ────────── 验收测试（α测试/β测试）
    │                    │
概要设计 ────────── 系统测试
    │                    │
详细设计 ────────── 集成测试
    │                    │
编码实现 ────────── 单元测试
```

## 2. 测试方法与策略

### 2.1 按是否执行程序分类

| 方法 | 说明 | 常用技术 |
|------|------|---------|
| 静态测试 | 不运行代码，通过检查、评审 | 代码审查、静态分析工具、走查 |
| 动态测试 | 运行代码，输入测试数据检查输出 | 白盒/黑盒测试 |

### 2.2 黑盒测试（功能/数据驱动测试）

不关心内部实现，仅通过输入输出来验证功能。

**黑盒测试方法**：

| 方法 | 说明 |
|------|------|
| **等价类划分** | 将输入域划分为若干等价类，每类取一个代表值测试。分有效等价类和无效等价类 |
| **边界值分析** | 对等价类的边界值进行测试。如范围[0,100]，测-1、0、50、100、101 |
| **决策表** | 将条件组合和动作对应，穷举所有规则 |
| **因果图** | 从输入条件的组合关系推导测试用例 |
| **正交实验法** | 从大量组合中选取代表性样本，减少测试用例 |
| **状态迁移法** | 基于状态图设计测试路径 |
| **场景法** | 基于业务流程设计测试路径 |

### 2.3 白盒测试（结构/逻辑驱动测试）

基于代码内部结构设计测试用例。

**白盒测试方法**：

| 方法 | 说明 |
|------|------|
| **语句覆盖** | 每条可执行语句至少执行一次（最弱的标准） |
| **判定(分支)覆盖** | 每个判定的真/假分支至少走一次 |
| **条件覆盖** | 每个条件的所有可能取值至少出现一次 |
| **判定/条件覆盖** | 同时满足判定覆盖和条件覆盖 |
| **条件组合覆盖** | 每个判定的所有条件取值组合至少出现一次 |
| **路径覆盖** | 覆盖每条可能的执行路径 |

**覆盖强度排序**：
```
语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖
```

**McCabe基本路径法**：
1. 画出程序控制流图
2. 计算环路复杂度 V(G) = e - n + 2 或 V(G) = P + 1（P=判定节点数）
3. 确定V(G)条独立路径
4. 为每条路径设计测试用例

## 3. 测试阶段与类型

### 3.1 按阶段划分

| 阶段 | 测试对象 | 测试目标 | 执行者 |
|------|---------|---------|--------|
| 单元测试 | 单个模块/函数 | 模块功能正确 | 开发人员 |
| 集成测试 | 模块间接口 | 模块协作正确 | 测试/开发 |
| 系统测试 | 完整系统 | 满足需求规格 | 独立测试团队 |
| 验收测试 | 可交付系统 | 满足用户期待 | 用户/客户 |

### 3.2 集成测试策略

| 策略 | 方法 | 优缺点 |
|------|------|--------|
| **非增量式（大爆炸）** | 所有模块一次集成测试 | 简单但定位难 |
| **自顶向下** | 从主控模块开始逐步集成 | 需要桩（Stub）模拟下层 |
| **自底向上** | 从底层模块开始逐步集成 | 需要驱动（Driver）模拟上层 |
| **三明治** | 上层自顶向下+下层自底向上，中间汇合 | 综合两者优势 |

### 3.3 按测试目标分类

| 类型 | 测试内容 |
|------|---------|
| **功能测试** | 是否满足功能需求 |
| **性能测试** | 响应时间、吞吐量、资源占用 |
| **负载测试** | 在预期工作负载下的表现 |
| **压力测试** | 超过设计极限时的行为（何时崩溃、如何恢复） |
| **容错/恢复测试** | 故障后恢复能力 |
| **安全测试** | 抵御非法入侵、数据保护 |
| **兼容性测试** | 不同平台/浏览器/设备的表现 |
| **易用性测试** | 用户界面友好度、学习成本 |
| **回归测试** | 确认修改未影响已有功能 |
| **冒烟测试** | 快速验证基本功能是否工作（用于判断是否可进入全面测试） |

## 4. 面向对象的测试

### 4.1 OO测试层次

```
类测试（相当于单元测试）→ 集成测试（类簇测试）→ 系统测试
```

### 4.2 OO测试的特点

- 测试的基本单元从函数变为类
- 需要考虑继承、多态对测试的影响
- 封装性导致测试时需要更多的访问方法
- 类之间通过消息协作，集成测试更关注消息序列
- 状态测试比结构化测试更重要（对象有状态记忆）

### 4.3 OO测试方法

- **基于状态的测试**：用状态图推导测试用例，覆盖状态转换路径
- **基于场景的测试**：用时序图描述典型交互场景，设计测试用例
- **基于继承的测试**：测试子类时重用父类测试用例并扩展
- **类层次测试**：测试类簇中的协作行为

## 5. 调试（Debugging）

### 5.1 调试策略

| 策略 | 方法 |
|------|------|
| **蛮干法** | 打印变量值、添加日志，逐个排查 |
| **回溯法** | 从出错位置反向追踪代码执行路径 |
| **原因排除法** | 假设一个原因，设计测试来排除或确认（二分法、演绎法、归纳法） |

## 6. 软件质量度量

### 6.1 缺陷度量

| 度量 | 含义 |
|------|------|
| 缺陷密度 | 缺陷数 / 规模（KLOC或FP），行业均值约1-25个/KLOC |
| 缺陷移除率（DRE） | 阶段发现的缺陷 / (阶段发现的 + 后续发现的) |
| 平均失效时间（MTTF） | 两次失效间的平均运行时间 |
| 平均修复时间（MTTR） | 从失效到修复恢复的平均时间 |

### 6.2 Halstead软件科学度量

基于代码的运算符和操作数计数：
- n₁ = 不同运算符数，n₂ = 不同操作数数
- N₁ = 运算符总数，N₂ = 操作数总数
- 程序词汇量 n = n₁ + n₂
- 程序长度 N = N₁ + N₂
- **程序量 V = N × log₂(n)**（最小单位是比特）
- 难度 D = (n₁/2) × (N₂/n₂)
- **工作量 E = D × V**
- 错误预估数 B = V / 3000

## 7. 软件可靠性

### 7.1 可靠性模型

| 模型 | 特点 |
|------|------|
| **Jelinski-Moranda** | 假设初始错误数为常数，每次修复减少一个错误，失效率与剩余错误数成正比 |
| **Goel-Okumoto** | 累计错误发现数遵循非齐次泊淞过程（NHPP） |
| **Musa执行时间模型** | 用CPU执行时间而非日历时间度量可靠性 |
| **Littlewood-Verrall** | 考虑修复可能引入新错误的不确定性 |

### 7.2 可靠性技术

| 技术 | 说明 |
|------|------|
| **避错** | 预防性技术：严格过程、形式化方法 |
| **容错** | 运行时应对故障：冗余（N版本编程、恢复块） |
| **检错** | 运行时检测：断言、守护进程、心跳 |

## 8. 软件评审与审查

### 8.1 Fagan正式审查

**6个步骤**：
1. 计划：确定审查范围和参与者
2. 概述：作者介绍审查对象
3. 准备：审查员独立阅读审查对象
4. 审查会议：逐项检查，记录缺陷
5. 返工：作者修改缺陷
6. 跟踪：检查返工结果

### 8.2 评审角色

- **主持人**：推进流程，控制节奏
- **作者**：回答疑问，澄清意图
- **评审员**：找出缺陷
- **记录员**：记录所有缺陷和问题
- **经理**：了解情况（可选，不在审查会议中参与）

## 9. 测试管理

### 9.1 测试过程

```
测试计划 → 测试设计 → 测试实现（编写用例/脚本）
→ 测试执行 → 缺陷管理 → 测试报告
```

### 9.2 缺陷生命周期

```
新建(New) → 已分配(Assigned) → 已修复(Fixed) → 已验证(Verified) → 关闭(Closed)
                      ↓                        ↓
                  拒绝(Rejected)          重新打开(Reopened)
```

### 9.3 测试自动化

- 适合自动化的：回归测试、性能测试、数据驱动测试
- 不适合自动化的：可用性测试、探索性测试、一次性测试
- 自动化金字塔：单元测试（最多）> 接口/服务测试 > UI测试（最少）
