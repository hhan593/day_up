# 03 — 软件设计原则与设计模式

## 1. 软件设计概述

### 1.1 概要设计与详细设计

| 阶段 | 概要设计（架构设计） | 详细设计 |
|------|---------------------|---------|
| 粒度 | 系统/子系统/模块级 | 模块/类/函数级 |
| 内容 | 模块划分、接口定义、数据流 | 算法设计、数据结构、类内部细节 |
| 输出 | 概要设计说明书、架构图 | 详细设计说明书、类图 |
| 关注点 | "做什么模块" | "模块怎么做" |

### 1.2 模块化设计

**模块**：具有独立功能的程序单元，由接口（Interface）和实现（Implementation）组成。

**信息隐藏原则**：模块接口只暴露必要信息，隐藏内部实现细节。

## 2. 结构化设计

### 2.1 内聚性（Cohesion）

内聚性衡量模块内部元素之间结合的紧密程度，**越高越好**。

| 等级（低→高） | 内聚类型 | 说明 |
|---------------|---------|------|
| 1 | 偶然内聚 | 模块内各元素无逻辑关联，随意放在一起 |
| 2 | 逻辑内聚 | 通过参数决定执行哪部分（如通用错误处理） |
| 3 | 时间内聚 | 各元素在同一时间段执行（如初始化模块） |
| 4 | 过程内聚 | 元素按指定顺序执行 |
| 5 | 通信内聚 | 处理相同输入数据或产生相同输出数据 |
| 6 | 顺序内聚 | 一个元素的输出作为另一个元素的输入 |
| 7 | 功能内聚 | 模块所有元素共同完成单一功能 **（最理想）** |

### 2.2 耦合性（Coupling）

耦合性衡量模块之间的依赖程度，**越低越好**。

| 等级（低→高） | 耦合类型 | 说明 |
|---------------|---------|------|
| 1 | 非直接耦合 | 模块间无直接关系 **（最理想）** |
| 2 | 数据耦合 | 通过简单数据（参数）传递信息 |
| 3 | 标记耦合 | 通过数据结构/记录传递 |
| 4 | 控制耦合 | 传递控制参数影响另一模块内部逻辑 |
| 5 | 外部耦合 | 模块访问同一个全局简单变量 |
| 6 | 公共耦合 | 模块访问同一个全局数据结构 |
| 7 | 内容耦合 | 一个模块直接修改另一模块内部数据 **（最差）** |

### 2.3 结构化设计原则

- **高内聚低耦合**
- **模块规模适中**（50-100行、一个打印页）
- **深度/宽度/扇入/扇出**合理：
  - 扇出（Fan-out）3-4为佳，上限7±2
  - 扇入（Fan-in）越大越好（复用度高）
- **作用域应在控制域之内**：一个判断的作用范围应在其所在模块的控制范围之内

## 3. 面向对象设计原则（SOLID）

| 原则 | 全称 | 含义 |
|------|------|------|
| **SRP** | 单一职责原则 | 一个类只应有一个引起变化的原因 |
| **OCP** | 开闭原则 | 对扩展开放，对修改关闭 |
| **LSP** | 里氏替换原则 | 子类必须能替换其基类而不影响程序正确性 |
| **ISP** | 接口隔离原则 | 不应强迫客户依赖它们不使用的方法 |
| **DIP** | 依赖倒置原则 | 高层模块不应依赖低层模块，两者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象 |

### 其他重要原则

| 原则 | 含义 |
|------|------|
| **LoD（迪米特法则）** | 只与直接朋友通信，不要和陌生人说话（最少知识原则） |
| **CRP**（合成复用原则） | 优先使用对象组合而非继承达到复用目的 |
| **DRY** | Don't Repeat Yourself，减少重复代码 |
| **KISS** | Keep It Simple, Stupid，保持简单 |

## 4. GoF设计模式（23种）

### 4.1 创建型模式（5种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Singleton（单例）** | 确保类只有一个实例，并提供全局访问点 | 全局唯一实例 |
| **Factory Method（工厂方法）** | 定义创建对象的接口，让子类决定实例化哪个类 | 延迟到子类决定 |
| **Abstract Factory（抽象工厂）** | 创建一系列相关或依赖的对象，无需指定具体类 | 产品族 |
| **Builder（建造者）** | 将复杂对象的构建与表示分离 | 相同构建过程、不同表示 |
| **Prototype（原型）** | 用原型实例指定创建对象的种类，通过拷贝创建 | 克隆对象 |

### 4.2 结构型模式（7种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Adapter（适配器）** | 将一个类的接口转换成客户期望的另一个接口 | 接口转换、兼容 |
| **Bridge（桥接）** | 将抽象部分与实现部分分离，使它们可以独立变化 | 多维度独立变化 |
| **Composite（组合）** | 将对象组合成树形结构以表示"整体-部分"层次 | 树形结构、统一对待 |
| **Decorator（装饰）** | 动态地给对象添加额外的职责 | 动态扩展、递归包装 |
| **Facade（外观）** | 为子系统中的一组接口提供统一的高层接口 | 简化接口 |
| **Flyweight（享元）** | 运用共享技术有效支持大量细粒度对象 | 共享、减少内存 |
| **Proxy（代理）** | 为其他对象提供一种代理以控制对这个对象的访问 | 控制访问、延迟加载 |

### 4.3 行为型模式（11种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Chain of Responsibility** | 多个对象有机会处理请求，沿链传递直到被处理 | 请求沿链传递 |
| **Command** | 将请求封装为对象，支持参数化、队列、日志 | 请求封装、撤销 |
| **Interpreter** | 定义语言的文法表示及解释器 | 解释语言/规则 |
| **Iterator** | 顺序访问聚合对象的元素，不暴露内部表示 | 遍历 |
| **Mediator** | 用一个中介对象封装一系列对象交互 | 松耦合、中介 |
| **Memento** | 在不破坏封装的前提下捕获对象内部状态 | 快照、撤销 |
| **Observer** | 一对多依赖，对象状态改变时通知所有依赖者 | 发布-订阅 |
| **State** | 对象内部状态改变时改变其行为 | 状态决定行为 |
| **Strategy** | 定义一系列算法，分别封装，使它们可互换 | 算法互换 |
| **Template Method** | 定义算法骨架，将某些步骤延迟到子类 | 骨架不变，步骤不同 |
| **Visitor** | 表示作用于某对象结构中各元素的操作 | 操作与数据结构分离 |

## 5. UML核心图详解

### 5.1 14种UML图分类（UML 2.x）

```
UML图
├── 结构图（静态结构）
│   ├── 类图（Class Diagram）★
│   ├── 对象图（Object Diagram）
│   ├── 包图（Package Diagram）
│   ├── 组件图（Component Diagram）★
│   ├── 复合结构图（Composite Structure Diagram）
│   ├── 部署图（Deployment Diagram）★
│   └── 制品图（Artifact Diagram）
└── 行为图（动态行为）
    ├── 用例图（Use Case Diagram）★
    ├── 活动图（Activity Diagram）★
    ├── 状态图（State Machine Diagram）★
    ├── 时序图（Sequence Diagram）★
    ├── 通信图（Communication Diagram，即UML1中的协作图）
    ├── 交互概览图（Interaction Overview Diagram）
    └── 定时图（Timing Diagram）
```

★ 标记为重点考查图

### 5.2 核心图要点

**用例图**：
- 要素：参与者（Actor）、用例（椭圆）、系统边界（矩形框）、关系（关联/包含/扩展/泛化）
- <<include>>：必须执行，基用例包含被包含用例的行为
- <<extend>>：可选扩展，基用例在特定条件下扩展的行为
- 泛化关系：子用例继承父用例行为

**类图**：
- 关系强度：依赖 < 关联 < 聚合 < 组合 < 泛化/实现
- 聚合（空心菱形）：整体可以独立存在（如球队与球员）
- 组合（实心菱形）：整体生命周期管理部分（如订单与订单项）
- 依赖（虚线箭头）：使用关系，最弱的关系
- 多重性：1（恰好1个）、0..1（0或1个）、0..*（任意个）、1..*（至少1个）

**时序图**：
- 表示对象之间按时间顺序的交互
- 要素：生命线、激活框、消息（同步/异步/返回）
- 适用于描述具体场景的交互流程

**状态图**：
- 描述对象生命周期中的状态变迁
- 要素：状态、转换（事件[条件]/动作）、初始/终态
- 适用于有明确状态变迁的对象（订单、审批等）

**活动图**：
- 描述业务流程或算法流程
- 要素：活动节点、分支（决策）、汇合、泳道、分叉
- 类似于流程图，功能更强

**组件图**：
- 描述系统的物理组件及其依赖关系
- 要素：组件、接口（提供接口/需求接口）、依赖关系

**部署图**：
- 描述系统运行时的物理节点分布
- 要素：节点（Node）、制品（Artifact）、通信路径

## 6. 4+1视图模型（架构文档体系）

| 视图 | 关注点 | 干系人 | UML图 |
|------|--------|--------|-------|
| 逻辑视图 | 系统功能需求 | 最终用户 | 类图、状态图 |
| 进程视图 | 并发、性能、可扩展性 | 系统集成人员 | 活动图、时序图 |
| 开发视图 | 模块组织、团队分工 | 程序员 | 包图、组件图 |
| 部署视图 | 拓扑、安装、通信 | 运维人员 | 部署图 |
| +1 场景视图 | 用例驱动、架构验证 | 分析人员/干系人 | 用例图 |

**"4+1"中的"+1"是用例场景，它将四个视图串联起来。**

## 7. 软件设计度量

### 7.1 面向对象度量（CK度量集）

| 度量 | 含义 | 说明 |
|------|------|------|
| WMC（加权方法数） | 类中方法的复杂度之和 | 值越大越复杂 |
| DIT（继承树深度） | 类在继承树中的深度 | 太深增加复杂度 |
| NOC（子类数量） | 类的直接子类数目 | 太多可能滥用继承 |
| CBO（类间耦合） | 与当前类耦合的其他类数目 | 越低越好 |
| RFC（类的响应集） | 类能调用的方法总数 | 越大越难维护 |
| LCOM（方法内聚缺乏度） | 方法访问属性的重叠度 | 越高内聚越差 |

### 7.2 结构化设计度量

- **扇入/扇出**：扇入高 = 复用度高；扇出过高 = 耦合严重
- **模块复杂度**：McCabe环路复杂度 V(G) = e - n + 2p（e=边、n=节点、p=连通分量数，通常p=1）
- 环路复杂度建议 ≤ 10
