# 03 — 软件设计原则与设计模式

## 1. 软件设计概述

### 1.1 概要设计与详细设计

| 阶段 | 概要设计（架构设计） | 详细设计 |
|------|---------------------|---------|
| 粒度 | 系统/子系统/模块级 | 模块/类/函数级 |
| 内容 | 模块划分、接口定义、数据流 | 算法设计、数据结构、类内部细节 |
| 输出 | 概要设计说明书、架构图 | 详细设计说明书、类图 |
| 关注点 | "做什么模块" | "模块怎么做" |

### 1.2 模块化设计

**模块**：具有独立功能的程序单元，由接口（Interface）和实现（Implementation）组成。

**信息隐藏原则**：模块接口只暴露必要信息，隐藏内部实现细节。

## 2. 结构化设计

### 2.1 内聚性（Cohesion）

内聚性衡量模块内部元素之间结合的紧密程度，**越高越好**。

| 等级（低→高） | 内聚类型 | 说明 |
|---------------|---------|------|
| 1 | 偶然内聚 | 模块内各元素无逻辑关联，随意放在一起 |
| 2 | 逻辑内聚 | 通过参数决定执行哪部分（如通用错误处理） |
| 3 | 时间内聚 | 各元素在同一时间段执行（如初始化模块） |
| 4 | 过程内聚 | 元素按指定顺序执行 |
| 5 | 通信内聚 | 处理相同输入数据或产生相同输出数据 |
| 6 | 顺序内聚 | 一个元素的输出作为另一个元素的输入 |
| 7 | 功能内聚 | 模块所有元素共同完成单一功能 **（最理想）** |

### 2.2 耦合性（Coupling）

耦合性衡量模块之间的依赖程度，**越低越好**。

| 等级（低→高） | 耦合类型 | 说明 |
|---------------|---------|------|
| 1 | 非直接耦合 | 模块间无直接关系 **（最理想）** |
| 2 | 数据耦合 | 通过简单数据（参数）传递信息 |
| 3 | 标记耦合 | 通过数据结构/记录传递 |
| 4 | 控制耦合 | 传递控制参数影响另一模块内部逻辑 |
| 5 | 外部耦合 | 模块访问同一个全局简单变量 |
| 6 | 公共耦合 | 模块访问同一个全局数据结构 |
| 7 | 内容耦合 | 一个模块直接修改另一模块内部数据 **（最差）** |

### 2.3 结构化设计原则

- **高内聚低耦合**
- **模块规模适中**（50-100行、一个打印页）
- **深度/宽度/扇入/扇出**合理：
  - 扇出（Fan-out）3-4为佳，上限7±2
  - 扇入（Fan-in）越大越好（复用度高）
- **作用域应在控制域之内**：一个判断的作用范围应在其所在模块的控制范围之内

## 3. 面向对象设计原则（SOLID）

| 原则 | 全称 | 含义 |
|------|------|------|
| **SRP** | 单一职责原则 | 一个类只应有一个引起变化的原因 |
| **OCP** | 开闭原则 | 对扩展开放，对修改关闭 |
| **LSP** | 里氏替换原则 | 子类必须能替换其基类而不影响程序正确性 |
| **ISP** | 接口隔离原则 | 不应强迫客户依赖它们不使用的方法 |
| **DIP** | 依赖倒置原则 | 高层模块不应依赖低层模块，两者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象 |

### 其他重要原则

| 原则 | 含义 |
|------|------|
| **LoD（迪米特法则）** | 只与直接朋友通信，不要和陌生人说话（最少知识原则） |
| **CRP**（合成复用原则） | 优先使用对象组合而非继承达到复用目的 |
| **DRY** | Don't Repeat Yourself，减少重复代码 |
| **KISS** | Keep It Simple, Stupid，保持简单 |

## 4. GoF设计模式（23种）

### 4.1 创建型模式（5种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Singleton（单例）** | 确保类只有一个实例，并提供全局访问点 | 全局唯一实例 |
| **Factory Method（工厂方法）** | 定义创建对象的接口，让子类决定实例化哪个类 | 延迟到子类决定 |
| **Abstract Factory（抽象工厂）** | 创建一系列相关或依赖的对象，无需指定具体类 | 产品族 |
| **Builder（建造者）** | 将复杂对象的构建与表示分离 | 相同构建过程、不同表示 |
| **Prototype（原型）** | 用原型实例指定创建对象的种类，通过拷贝创建 | 克隆对象 |

### 4.2 结构型模式（7种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Adapter（适配器）** | 将一个类的接口转换成客户期望的另一个接口 | 接口转换、兼容 |
| **Bridge（桥接）** | 将抽象部分与实现部分分离，使它们可以独立变化 | 多维度独立变化 |
| **Composite（组合）** | 将对象组合成树形结构以表示"整体-部分"层次 | 树形结构、统一对待 |
| **Decorator（装饰）** | 动态地给对象添加额外的职责 | 动态扩展、递归包装 |
| **Facade（外观）** | 为子系统中的一组接口提供统一的高层接口 | 简化接口 |
| **Flyweight（享元）** | 运用共享技术有效支持大量细粒度对象 | 共享、减少内存 |
| **Proxy（代理）** | 为其他对象提供一种代理以控制对这个对象的访问 | 控制访问、延迟加载 |

### 4.3 行为型模式（11种）

| 模式 | 意图 | 考试关键词 |
|------|------|-----------|
| **Chain of Responsibility** | 多个对象有机会处理请求，沿链传递直到被处理 | 请求沿链传递 |
| **Command** | 将请求封装为对象，支持参数化、队列、日志 | 请求封装、撤销 |
| **Interpreter** | 定义语言的文法表示及解释器 | 解释语言/规则 |
| **Iterator** | 顺序访问聚合对象的元素，不暴露内部表示 | 遍历 |
| **Mediator** | 用一个中介对象封装一系列对象交互 | 松耦合、中介 |
| **Memento** | 在不破坏封装的前提下捕获对象内部状态 | 快照、撤销 |
| **Observer** | 一对多依赖，对象状态改变时通知所有依赖者 | 发布-订阅 |
| **State** | 对象内部状态改变时改变其行为 | 状态决定行为 |
| **Strategy** | 定义一系列算法，分别封装，使它们可互换 | 算法互换 |
| **Template Method** | 定义算法骨架，将某些步骤延迟到子类 | 骨架不变，步骤不同 |
| **Visitor** | 表示作用于某对象结构中各元素的操作 | 操作与数据结构分离 |

## 5. 设计模式分类与辨析

### 5.1 设计模式二维分类（GoF）

按**目的**（创建/结构/行为）× **范围**（类/对象）维度的经典分类：

| 范围 \ 目的 | 创建型 | 结构型 | 行为型 |
|-----------|--------|--------|--------|
| **类模式** | Factory Method | Adapter(类) | Interpreter, Template Method |
| **对象模式** | Abstract Factory, Builder, Prototype, Singleton | Adapter(对象), Bridge, Composite, Decorator, Facade, Flyweight, Proxy | Chain of Responsibility, Command, Iterator, Mediator, Memento, Observer, State, Strategy, Visitor |

**类模式 vs 对象模式**：

| 维度 | 类模式 | 对象模式 |
|------|--------|--------|
| 关系建立时机 | 编译时（静态，通过继承） | 运行时（动态，通过组合） |
| 扩展方式 | 子类化 | 对象引用 |
| 灵活性 | 低（编译时固定） | 高（运行时可更换） |
| 典型代表 | Factory Method, Template Method, Interpreter | Strategy, Observer, Composite |

> 对象模式占比远超类模式，体现"**组合优于继承**"原则。

### 5.2 创建型模式——结构与参与者

| 模式 | 参与者 | 结构要点 |
|------|--------|---------|
| **Singleton** | Singleton | 私有构造+静态实例+全局访问点（getInstance） |
| **Factory Method** | Creator(含FactoryMethod), ConcreteCreator, Product, ConcreteProduct | Creator定义工厂方法，ConcreteCreator重写工厂方法返回具体产品 |
| **Abstract Factory** | AbstractFactory, ConcreteFactory, AbstractProduct, ConcreteProduct, Client | ConcreteFactory创建一组相关的ConcreteProduct |
| **Builder** | Builder, ConcreteBuilder, Director, Product | Director持有Builder，调用BuildPart→GetResult |
| **Prototype** | Prototype(含Clone), ConcretePrototype, Client | 实现Clone接口，通过拷贝创建新对象 |

**创建型模式对比**：

| 对比维度 | Factory Method | Abstract Factory | Builder | Prototype |
|----------|---------------|-----------------|---------|-----------|
| 创建对象数 | 1个 | 一组（产品族） | 1个复杂对象 | 任意 |
| 侧重点 | 子类决定类型 | 产品族一致性 | 构造步骤复用 | 拷贝效率 |
| 何时换用别的 | 一组相关产品 → Abstract Factory | 复杂构造步骤 → Builder | 简单对象 → Prototype | 初始化成本高 → 深克隆 |

### 5.3 结构型模式——核心结构

| 模式 | 参与者 | 核心结构 |
|------|--------|---------|
| **Adapter** | Target, Adapter, Adaptee, Client | Adapter继承/组合Adaptee → 适配为Target接口 |
| **Bridge** | Abstraction, RefinedAbstraction, Implementor, ConcreteImplementor | Abstraction持有Implementor引用（桥），两维度独立变化 |
| **Composite** | Component, Leaf, Composite | Leaf和Composite都实现Component，Composite聚合Component列表 |
| **Decorator** | Component, ConcreteComponent, Decorator, ConcreteDecorator | Decorator继承Component+聚合Component（递归嵌套） |
| **Facade** | Facade, Subsystem classes | Facade提供简化接口，内部委托给子系统 |
| **Flyweight** | Flyweight, ConcreteFlyweight, FlyweightFactory, UnsharedConcreteFlyweight | Factory管理共享池，通过内部状态/外部状态分离 |
| **Proxy** | Subject, RealSubject, Proxy | Proxy和RealSubject都实现Subject，Proxy持有RealSubject引用 |

**易混淆结构型模式对比**：

| 对比 | 关键区别 |
|------|---------|
| **Adapter vs Bridge** | Adapter是事后补救（接口不匹配→适配）；Bridge是事前设计（分离抽象与实现让两者独立变化） |
| **Adapter vs Proxy** | Adapter改接口；Proxy不改接口（控制访问） |
| **Adapter vs Decorator** | Adapter改接口；Decorator增强不改接口 |
| **Composite vs Decorator** | Composite管理一组对象（一对多）；Decorator包装单个对象（递归增强） |
| **Proxy vs Decorator** | Proxy控制访问（权限/懒加载）；Decorator添加职责（功能增强） |
| **Facade vs Adapter** | Facade简化复杂子系统的接口；Adapter转换现有接口 |

### 5.4 行为型模式——核心交互

**行为型模式可按处理关系分类**：

**① 父类与子类（继承复用行为）**：

| 模式 | 结构 | 核心思想 |
|------|------|---------|
| **Template Method** | AbstractClass定义骨架+原语操作，ConcreteClass实现原语 | 父类定义算法框架，子类填充细节 |
| **Strategy** | Context持有Strategy，ConcreteStrategyA/B可替换 | 算法独立封装，可运行时替换 |
| **Template Method vs Strategy** | Template Method用继承（编译时决定），Strategy用组合（运行时切换） | |

**② 两个类之间（请求封装与传递）**：

| 模式 | 参与者 | 核心 |
|------|--------|------|
| **Command** | Invoker, Command, ConcreteCommand, Receiver | 请求封装为对象 → 支持撤销、排队、日志 |
| **Memento** | Originator, Memento, Caretaker | Originator创建Memento快照，Caretaker保管但不查看 |
| **Chain of Resp** | Handler(含successor), ConcreteHandler | 请求沿链传递，某处理者决定处理或传递 |
| **Iterator** | Iterator, ConcreteIterator, Aggregate, ConcreteAggregate | 分离遍历算法与聚合结构 |

**③ 对象间通信（解耦依赖）**：

| 模式 | 结构 | 关键 |
|------|------|------|
| **Observer** | Subject(含Observer列表), ConcreteSubject, Observer, ConcreteObserver | 一对多通知，推/拉模型 |
| **Mediator** | Mediator, ConcreteMediator, Colleague | 引入中介者，消除同事对象的网状耦合 |

**④ 状态与行为（封装变化）**：

| 模式 | 结构 | 关键 |
|------|------|------|
| **State** | Context(含State), State, ConcreteStateA/B | 状态对象封装该状态下的行为，Context委托 |
| **Strategy vs State** | Strategy由客户端选择算法；State自动切换内部状态行为 | |
| **Visitor** | Visitor, ConcreteVisitor, Element(含Accept), ConcreteElement, ObjectStructure | 操作与数据结构分离，易于增加新操作 |
| **Interpreter** | Context, AbstractExpression, TerminalExpression, NonTerminalExpression | 文法翻译器，类结构对应语法规则 |

### 5.5 模式间的复合关系

某些模式常常一起使用：

| 组合 | 说明 |
|------|------|
| **Composite + Visitor** | Composite提供树形结构，Visitor遍历树执行不同操作 |
| **Composite + Iterator** | Composite提供结构，Iterator遍历 |
| **Factory Method + Template Method** | Template Method中调用Factory Method延迟创建 |
| **Flyweight + Composite** | 享元对象常组成复合结构 |
| **Mediator + Observer** | Mediator通过Observer接收同事通知 |
| **Command + Memento** | Command执行操作，Memento保存状态供撤销 |
| **Command + Composite** | 宏命令 = Command的组合模式 |
| **Facade + Singleton** | Facade常做成单例 |

### 5.6 设计模式选用决策

**创建对象时**：

```
需要控制实例数 → Singleton
延迟到子类决定类型 → Factory Method
创建一组相关对象 → Abstract Factory
构造过程复杂分步 → Builder
创建成本高、靠拷贝 → Prototype
```

**组织类与对象结构时**：
```
接口不匹配 → Adapter
多维度独立变化 → Bridge
树形"整体-部分" → Composite
动态添加职责 → Decorator
简化复杂子系统接口 → Facade
大量细粒度对象 → Flyweight
控制访问/懒加载 → Proxy
```

**管理行为与交互时**：
```
算法可替换 → Strategy
框架骨架不变 → Template Method
请求沿链处理 → Chain of Responsibility
请求封装（撤销/队列） → Command
一对多自动通知 → Observer
状态决定行为 → State
多对象解耦协作 → Mediator
遍历不暴露内部 → Iterator
保存与恢复状态 → Memento
操作与结构分离 → Visitor
定义语言文法 → Interpreter

## 7. 设计模式易错辨析

### 7.1 名称相似混淆

| 模式 | 易混淆点 |
|------|---------|
| **Abstract Factory vs Factory Method** | Abstract Factory创建产品族（多个相关对象）；Factory Method创建单个对象 |
| **State vs Strategy** | State自动切换行为（内部状态变化驱动）；Strategy手动选择算法（外部注入） |
| **Decorator vs Proxy** | Decorator动态添加功能；Proxy控制访问权/延迟创建 |
| **Bridge vs Strategy** | Bridge是结构型（分离抽象和实现两个变化维度）；Strategy是行为型（封装可互换算法） |

### 7.2 考试常见判断依据

| 题干提示 | 指向模式 |
|----------|---------|
| "动态地给对象添加职责"、"嵌套包装" | Decorator |
| "将抽象与实现解耦"、"独立变化" | Bridge |
| "树形结构"、"整体-部分"、"统一对待叶子与组合" | Composite |
| "希望使用已有的类，但接口不匹配" | Adapter |
| "控制对象访问"、"延迟加载"、"远程代理" | Proxy |
| "定义算法框架，子类实现具体步骤" | Template Method |
| "算法族，可互相替换" | Strategy |
| "一对多，状态变化通知" | Observer |
| "请求的发送者和接收者解耦"、"支持撤销" | Command |
| "多个对象都可以处理请求" | Chain of Responsibility |
| "把一个操作作用于一组对象上" | Visitor |
| "用一个中介来封装一系列对象交互" | Mediator |
| "不破坏封装，捕获内部状态"、"撤销/恢复" | Memento |

### 5.2 核心图要点

**用例图**：
- 要素：参与者（Actor）、用例（椭圆）、系统边界（矩形框）、关系（关联/包含/扩展/泛化）
- <<include>>：必须执行，基用例包含被包含用例的行为
- <<extend>>：可选扩展，基用例在特定条件下扩展的行为
- 泛化关系：子用例继承父用例行为

**类图**：
- 关系强度：依赖 < 关联 < 聚合 < 组合 < 泛化/实现
- 聚合（空心菱形）：整体可以独立存在（如球队与球员）
- 组合（实心菱形）：整体生命周期管理部分（如订单与订单项）
- 依赖（虚线箭头）：使用关系，最弱的关系
- 多重性：1（恰好1个）、0..1（0或1个）、0..*（任意个）、1..*（至少1个）

**时序图**：
- 表示对象之间按时间顺序的交互
- 要素：生命线、激活框、消息（同步/异步/返回）
- 适用于描述具体场景的交互流程

**状态图**：
- 描述对象生命周期中的状态变迁
- 要素：状态、转换（事件[条件]/动作）、初始/终态
- 适用于有明确状态变迁的对象（订单、审批等）

**活动图**：
- 描述业务流程或算法流程
- 要素：活动节点、分支（决策）、汇合、泳道、分叉
- 类似于流程图，功能更强

**组件图**：
- 描述系统的物理组件及其依赖关系
- 要素：组件、接口（提供接口/需求接口）、依赖关系

**部署图**：
- 描述系统运行时的物理节点分布
- 要素：节点（Node）、制品（Artifact）、通信路径

## 6. 4+1视图模型（架构文档体系）

| 视图 | 关注点 | 干系人 | UML图 |
|------|--------|--------|-------|
| 逻辑视图 | 系统功能需求 | 最终用户 | 类图、状态图 |
| 进程视图 | 并发、性能、可扩展性 | 系统集成人员 | 活动图、时序图 |
| 开发视图 | 模块组织、团队分工 | 程序员 | 包图、组件图 |
| 部署视图 | 拓扑、安装、通信 | 运维人员 | 部署图 |
| +1 场景视图 | 用例驱动、架构验证 | 分析人员/干系人 | 用例图 |

**"4+1"中的"+1"是用例场景，它将四个视图串联起来。**

## 7. 软件设计度量

### 7.1 面向对象度量（CK度量集）

| 度量 | 含义 | 说明 |
|------|------|------|
| WMC（加权方法数） | 类中方法的复杂度之和 | 值越大越复杂 |
| DIT（继承树深度） | 类在继承树中的深度 | 太深增加复杂度 |
| NOC（子类数量） | 类的直接子类数目 | 太多可能滥用继承 |
| CBO（类间耦合） | 与当前类耦合的其他类数目 | 越低越好 |
| RFC（类的响应集） | 类能调用的方法总数 | 越大越难维护 |
| LCOM（方法内聚缺乏度） | 方法访问属性的重叠度 | 越高内聚越差 |

### 7.2 结构化设计度量

- **扇入/扇出**：扇入高 = 复用度高；扇出过高 = 耦合严重
- **模块复杂度**：McCabe环路复杂度 V(G) = e - n + 2p（e=边、n=节点、p=连通分量数，通常p=1）
- 环路复杂度建议 ≤ 10
