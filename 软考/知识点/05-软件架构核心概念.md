# 05 — 软件架构核心概念

## 1. 软件架构定义

### 1.1 架构的内涵

软件架构是系统的基本组织结构，体现在：
- 系统的**组件/构件**（Components）
- 组件之间的**关系**（Relationships/Connectors）
- 组件与环境的关系
- 指导系统设计和演进的**原则**

**IEEE 1471-2000 / ISO/IEC 42010 定义**：
> 架构是体现在组件、组件之间关系、组件与环境关系中的系统的基本组织，以及指导其设计和演进的原则。

### 1.2 架构的三个方面

| 方面 | 内容 |
|------|------|
| **结构** | 系统由哪些构件组成，构件之间如何连接 |
| **行为** | 构件之间如何交互来完成系统功能 |
| **决策** | 为什么这样设计（设计理由、约束、折中） |

---

## 2. 架构的4+1视图模型

Kruchten 提出的经典架构文档化模型：

| 视图 | 关注点 | 回答的问题 | 干系人 | 常用UML图 |
|------|--------|-----------|--------|-----------|
| **逻辑视图** | 功能性需求 | 系统提供什么功能服务 | 用户、领域专家 | 类图、状态图、交互图 |
| **进程视图** | 非功能性（并发、性能） | 系统如何处理并发/吞吐 | 系统集成、性能工程师 | 活动图、时序图 |
| **开发视图** | 模块组织 | 代码如何分包、子系统划分 | 开发人员、项目经理 | 包图、组件图 |
| **部署视图** | 物理部署 | 系统部署在哪里，如何通信 | 运维、网络工程师 | 部署图 |
| **+1 场景视图** | 验证说明 | 如何验证架构满足需求 | 所有干系人 | 用例图、时序图 |

**场景视图把四个视图串联成一个有机整体**，每个场景在四个视图下都有对应的架构表现。

## 3. 架构风格（Architecture Styles）

### 3.1 数据流风格

#### 3.1.1 批处理风格（Batch Sequential）

```
输入 → 步骤1 → 步骤2 → 步骤3 → 输出
```

- 每个步骤独立运行，前一步全部完成后才能开始下一步
- **优点**：简单、易于理解和重用
- **缺点**：延迟大、不适合交互
- **典型应用**：传统数据处理、ETL

#### 3.1.2 管道-过滤器风格（Pipe-and-Filter）

```
输入 → [过滤器1] → 管道 → [过滤器2] → 管道 → [过滤器3] → 输出
```

- 每个过滤器独立，可并发，管道连接它们
- **优点**：可重用、可重组、支持并发、易于分析和维护
- **缺点**：不适合交互、数据转换开销
- **典型应用**：Unix Shell管道、编译器（词法分析→语法分析→语义分析→代码生成）

---

### 3.2 调用/返回风格

#### 3.2.1 主程序-子程序风格

- 经典的函数调用结构
- **优点**：简单直观
- **缺点**：紧耦合、难以扩展
- **典型应用**：小型程序、嵌入式系统

#### 3.2.2 面向对象风格

- 数据和操作封装在对象中，对象间通过消息通信
- **优点**：封装、继承、多态，易于扩展和维护
- **缺点**：对象间耦合、标识与引用问题
- **典型应用**：大多数业务系统

#### 3.2.3 层次风格（Layered）

```
┌─────────────┐
│   表示层     │  ← 用户界面
├─────────────┤
│   应用层     │  ← 业务逻辑
├─────────────┤
│   领域层     │  ← 领域模型
├─────────────┤
│   持久层     │  ← 数据访问
└─────────────┘
```

- **严格分层**：每层只能调用相邻下层
- **松散分层**：可以跨层调用
- **优点**：关注点分离、易于替换、支持标准化
- **缺点**：性能开销（层层传递）、层数确定困难、级联修改
- **典型应用**：OSI网络模型、Web应用、企业信息系统

---

### 3.3 数据为中心风格

#### 3.3.1 仓库风格（Repository）

- 中心数据结构，多个组件访问它
- 组件独立执行，通过中心数据进行数据交换
- **优点**：数据共享、数据一致性、组件独立
- **缺点**：中心数据耦合、演化困难
- **典型应用**：数据库系统、IDE（编辑器利用AST仓库）、编译器符号表

#### 3.3.2 黑板风格（Blackboard）

- 仓库风格的变体，中心数据结构触发组件
- **核心组件**：
  - **黑板**：共享的数据存储
  - **知识源**：独立的问题求解模块
  - **控制组件**：调度知识源的激活
- **优点**：适合不确定性问题求解、灵活性高
- **缺点**：控制复杂、性能不确定
- **典型应用**：语音识别、自然语言处理、专家系统

---

### 3.4 虚拟机风格

#### 3.4.1 解释器风格（Interpreter）

```
伪代码 → 解释引擎 → 实际执行操作
```

- 定义一种虚拟语言，由解释引擎执行
- **典型应用**：Python/JS运行时、规则引擎、游戏脚本引擎

#### 3.4.2 基于规则的系统（Rule-Based System）

- 将业务逻辑表达为规则，由规则引擎推断执行
- **核心组件**：规则集、事实库、推断引擎
- **典型应用**：业务规则引擎、专家系统

---

### 3.5 独立构件风格

#### 3.5.1 事件驱动风格（Event-Driven/隐式调用）

```
事件源1 ──→┐
          ├──→ 事件总线 ──→ 事件消费者A、B、C
事件源2 ──→┘
```

- 构件发布事件，但不知道谁会响应
- **优点**：松耦合、易于扩展、支持异步
- **缺点**：无法控制执行顺序、调试困难
- **典型应用**：GUI框架、消息系统、微服务事件驱动

**变体**：
- **发布-订阅（Pub-Sub）**：通过主题/频道分发
- **CQRS/事件溯源**：事件存储，状态由事件还原

## 4. 架构模式（Architecture Patterns）

架构模式是解决特定上下文中反复出现的架构问题的通用方案。

### 4.1 经典架构模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **MVC** | Model-View-Controller，分隔数据、展示和控制 | Web应用、桌面GUI |
| **MVP** | Model-View-Presenter，View更薄，Presenter双向绑定 | .NET、Android开发 |
| **MVVM** | Model-View-ViewModel，数据绑定，View与Model解耦 | WPF、Vue/Angular |
| **PAC** | Presentation-Abstraction-Control，多代理分层架构 | 复杂交互系统 |
| **微内核** | 核心系统+插件 | Eclipse、操作系统 |
| **Broker** | 分布式系统中的中介模式 | CORBA、消息中间件 |
| **Pipes and Filters** | 串联数据处理 | 编译器、数据处理流 |

### 4.2 MVC 详解

```
       ┌── 状态查询 ──→  Model（模型）
       │                   ↓   ↑
    View（视图）        状态改变通知
       │                   ↓   ↑
       └── 用户输入 ──→ Controller（控制器）
```

- **Model**：数据+业务逻辑，不依赖View和Controller
- **View**：展示数据，从Model获取数据
- **Controller**：接收用户输入，更新Model和View

**MVC变体**：
- **MVP**：Presenter替代Controller，View完全被动
- **MVVM**：ViewModel通过数据绑定自动同步View

## 5. 架构的软件架构文档化

### 5.1 架构文档的核心内容

1. 架构概述和设计目标
2. 架构视图（4+1）
3. 架构决策（AD - Architecture Decisions）
4. 架构决策记录（ADR）模板：
   - 标题、状态、上下文、决策、后果
5. 质量属性需求和满足方案
6. 约束与假设

### 5.2 架构描述语言（ADL）

| ADL | 特点 |
|-----|------|
| ACME | 通用架构交换语言，构件+连接件+系统+属性 |
| Wright | 基于CSP形式化描述连接件 |
| xADL 2.0 | 基于XML的ADL，支持扩展 |
| Darwin | 关注分布式系统动态结构 |
| UML | 非专用ADL，但被广泛用于架构描述 |

## 6. 架构师角色与能力

### 6.1 系统架构师的核心职责

- 将需求转化为架构设计
- 做出关键技术决策
- 平衡质量属性（性能 vs 可维护性 vs 安全性等）
- 技术风险评估和缓解
- 架构文档化和干系人沟通
- 指导开发团队遵循架构
- 识别和管理技术债务

### 6.2 系统架构师的能力模型

| 维度 | 内容 |
|------|------|
| **技术能力** | 深厚的技术栈知识、架构模式、设计模式、中间件 |
| **业务能力** | 领域知识、业务分析、需求理解 |
| **沟通能力** | 与开发/管理/客户/运维各方有效沟通 |
| **领导能力** | 技术引导、决策、团队影响 |
| **权衡能力** | 在多种约束和要求中找到最优平衡点 |

### 6.3 架构师 vs 高级开发 vs 技术经理

| 角色 | 关注重点 |
|------|---------|
| **高级开发** | 单个模块/组件的设计和实现质量 |
| **系统架构师** | 全局的系统结构和质量属性 |
| **技术经理** | 资源、进度、团队管理 |
