# 12 — 软件架构的演化和维护

## 1. 软件架构演化概述

### 1.1 架构演化的定义

**软件架构演化（Architecture Evolution）**：软件系统在整个生命周期中，其整体结构从一种架构形态持续、平滑地演变为另一种架构形态的过程，以适应环境、需求和技术的变化。

**架构演化与软件维护的区别**：

| 维度 | 软件维护 | 架构演化 |
|------|---------|---------|
| 粒度 | 代码/模块级修改 | 系统结构级变更 |
| 影响范围 | 局部 | 全局/系统级 |
| 目标 | 修复缺陷、局部增强 | 改变系统的整体结构和质量属性 |
| 频率 | 持续不断 | 阶段性、有计划 |
| 触发时机 | Bug/小需求 | 技术战略变更、业务根本变化 |

### 1.2 架构演化的驱动力

| 驱动力类别 | 具体来源 | 典型场景 |
|-----------|---------|---------|
| **业务驱动** | 业务模式变化、新市场、并购重组 | 从电商→平台化、从国内→全球化 |
| **技术驱动** | 新技术出现、旧技术淘汰 | 单体→微服务、自建机房→云原生 |
| **质量属性驱动** | 性能/安全/可伸缩性不再满足 | 用户量增长100倍、安全合规升级 |
| **环境驱动** | 法律法规、行业标准变化 | GDPR、等保2.0、信创国产化 |
| **组织驱动** | 团队结构变化、外包/自研切换 | 多团队并行开发需要模块化解耦 |

### 1.3 架构演化的分类

| 分类维度 | 类型 | 说明 |
|----------|------|------|
| **按范围** | 局部演化 | 单一架构要素（组件/连接件）的修改 |
| | 全局演化 | 架构风格的整体变迁 |
| **按时机** | 静态演化 | 系统停机期间的架构调整 |
| | 动态演化 | 系统运行期间的架构调整（热演化） |
| **按引发** | 反应式演化 | 被动应对已发生的问题 |
| | 预见式演化 | 主动预防未来的问题（架构重构） |

## 2. 软件架构演化原则

> 系统架构设计师考点：架构演化与软件设计原则的关系

### 2.1 演化基本原则

| 原则 | 含义 | 架构层面的体现 |
|------|------|---------------|
| **开闭原则（OCP）** | 对扩展开放、对修改关闭 | 通过接口和插件机制扩展，而非修改核心架构 |
| **单一职责** | 一个组件只负责一个功能领域 | 架构中每个模块/服务的职责边界清晰 |
| **依赖倒置** | 高层不依赖低层，都依赖抽象 | 架构层次之间通过抽象接口解耦 |
| **接口隔离** | 不被迫依赖不使用的接口 | 组件接口精简、按需暴露 |
| **最少知识（迪米特）** | 组件之间尽量少知道彼此细节 | 通过事件/消息降低组件直接耦合 |

### 2.2 架构演化特有原则

| 原则 | 核心思想 | 实践方法 |
|------|---------|---------|
| **增量演进原则** | 每次只改变系统的一小部分，逐步达成目标架构 | 绞杀者模式、分阶段迁移 |
| **兼容性原则** | 新旧架构并存期间保持接口兼容 | API版本化、双写双读 |
| **可逆性原则** | 每次变更都应可回退 | 特性开关、灰度发布、蓝绿部署 |
| **演进优于重写** | 优先改进而非推倒重建 | 持续重构优于大爆炸重写 |
| **数据先行** | 数据迁移方案先于架构切换 | 先解决数据同步，再切换服务 |
| **质量不降级** | 演化过程中系统质量属性不降低 | 持续性能测试、对比评估 |

## 3. 软件架构演化过程与模型

### 3.1 架构演化的一般过程

```
架构评估（当前状态）
    → 确定演化目标（目标架构）
    → 分析差距（Gap Analysis）
    → 制定演化路线图（Evolution Roadmap）
    → 分阶段实施
       ├── 每阶段：小步迁移 → 验证 → 评估 → 调整
       └── 循环迭代
    → 到达目标架构
    → 持续演化（进入下一轮）
```

### 3.2 演化路线图（Evolution Roadmap）

**路线图要素**：
- **里程碑（Milestone）**：每个阶段的目标状态
- **时间线**：预期的时间进度
- **依赖关系**：哪些步骤必须按顺序完成
- **回退条件**：什么情况下需要回退
- **质量门禁**：每个阶段必须通过的验证

**示例——单体到微服务路线图**：
```
阶段0（现状）：单体应用
    │
阶段1：抽取独立模块，定义接口边界 → 基础解耦
    │
阶段2：拆分第一个独立服务 → 验证CI/CD、监控体系
    │
阶段3：逐批迁移核心业务 → 逐步减少单体范围
    │
阶段4：单体退化为轻量门面 → 全微服务架构
    │
阶段5：持续优化服务边界 → 长期演化维护
```

### 3.3 动态演化（运行时演化）

**动态演化的前提条件**：
1. 系统支持运行时配置/路由变更
2. 组件可热加载/热替换
3. 有完善的健康检查和自动恢复机制
4. 数据和状态的平滑迁移方案

**动态演化典型场景**：
- 不停机更新系统组件（滚动更新）
- 动态扩缩容（弹性伸缩）
- 在线A/B测试和灰度发布
- 运行时切换算法/策略（如降级开关）

## 4. 软件架构演化策略与模式

### 4.1 架构迁移策略对比

| 策略 | 方法 | 风险 | 适用场景 |
|------|------|------|---------|
| **大爆炸重写（Big Bang）** | 全停→重写→上线 | 极高 | 极少推荐 |
| **绞杀者模式（Strangler Fig）** | 新系统逐步替换旧系统 | 低 | **推荐首选** |
| **抽象分支（Branch by Abstraction）** | 引入抽象层→底层逐步替换 | 低 | 组件/库替换 |
| **特性开关（Feature Toggle）** | 通过开关控制新旧代码路径 | 低 | 增量功能迁移 |
| **并行运行** | 新旧系统同时运行→验证→切换 | 中 | 关键系统迁移 |

### 4.2 绞杀者模式（Strangler Fig Pattern）详解

```
初始状态：              中间状态：              终态：
┌──────────────┐   ┌──────────────┐    ┌──────────────┐
│   旧系统      │   │ 旧系统  新系统 │    │   新系统      │
│  ┌────────┐  │   │ ┌───┐   ┌───┐│    │  ┌────────┐  │
│  │模块A   │  │   │ │ A │   │ B ││    │  │模块A   │  │
│  │模块B   │  │   │ │   │   │   ││    │  │模块B   │  │
│  │模块C   │  │   │ │ C │   │   ││    │  │模块C   │  │
│  └────────┘  │   │ └───┘   └───┘│    │  └────────┘  │
└──────────────┘   └──────────────┘    └──────────────┘
    ↑                   ↑ ↑                 ↑
  100%请求          路由分发请求         100%请求

步骤：
1. 识别：找出可独立的功能模块
2. 拦截：在旧系统前加路由层
3. 迁移：逐个迁移模块到新系统
4. 验证：每迁移一个模块，验证功能与性能
5. 下线：所有模块迁移完成后，下线旧系统
```

**路由层实现方式**：
- **HTTP代理**：Nginx/Envoy根据URL路径路由到新旧系统
- **消息队列**：改变消息的消费者
- **DNS**：解析到新服务的域名
- **特性开关**：应用内根据开关选择调用


### 4.3 抽象分支模式（Branch by Abstraction）

```
步骤1：                  步骤2：                  步骤3：
┌───────┐            ┌───────┐            ┌───────┐
│Client │            │Client │            │Client │
└──┬────┘            └──┬────┘            └──┬────┘
   │                    │                    │
   ▼                    ▼                    ▼
┌──────────┐     ┌──────────────┐     ┌──────────────┐
│ 旧实现    │      │  抽象接口     │      │  抽象接口     │
└──────────┘     └──┬───────┬───┘     └──────┬───────┘
                    │       │                │
                    ▼       ▼                ▼
               ┌────────┐ ┌────────┐   ┌────────┐
               │ 旧实现  │ │ 新实现  │   │ 新实现  │
               └────────┘ └────────┘   └────────┘

1. 引入抽象层，Client依赖抽象
2. 开发新实现，与旧实现并行
3. 切换Client到新实现，移除旧实现
```

### 4.4 特性开关（Feature Toggle）

**四种开关类型**：
| 类型 | 生命周期 | 用途 |
|------|---------|------|
| **发布开关** | 短期（数天-数周） | 未完成功能的隐藏发布 |
| **实验开关** | 中期（数周-数月） | A/B测试 |
| **运维开关** | 长期 | 运行时降级、限流控制 |
| **权限开关** | 长期 | 不同用户看到不同功能（VIP/普通） |

**最佳实践**：开关过期自动提醒/清理，避免开关堆积成为技术债务。

## 5. 软件架构技术债务

### 5.1 架构技术债务的定义

**架构技术债务（Architecture Technical Debt）**：当前架构与理想架构之间的差距所产生的长期代价。即由于短视/妥协的架构决策，未来需要付出额外努力来修复。

**技术债务积累公式**：
```
技术债务 = Σ（偏离理想架构的决策 × 每项决策的利息代价 × 时间）
```

### 5.2 架构技术债务分类

| 类型 | 说明 | 示例 |
|------|------|------|
| **结构债务** | 模块划分不合理、包依赖混乱、循环依赖 | 单体中直接跨模块调用 |
| **质量属性债务** | 架构无法满足非功能需求 | 无缓存→响应慢、无队列→峰值崩溃 |
| **技术栈债务** | 使用了过时/不受支持的技术 | 使用已EOL的框架/语言 |
| **集成债务** | 系统间耦合不当、接口不一致 | 通过共享数据库集成（点对点集成） |
| **设计债务** | 设计模式误用、模式退化 | 单例滥用、不恰当的继承层次 |
| **测试债务** | 缺少架构层面的测试 | 自动化测试覆盖低、缺乏性能基线测试 |
| **文档债务** | 架构文档过时/缺失 | 架构图与实现不一致 |

### 5.3 技术债务管理

**技术债务管理四象限**：

| | 低利息 | 高利息 |
|------|--------|--------|
| **高本金** | 需要计划偿还（大重构） | **紧急**：必须优先处理 |
| **低本金** | 可接受（暂时保留） | 适当时机处理 |

**技术债务的"利息"**：
- 开发效率下降（每次改动涉及更多文件）
- 缺陷率上升（改一处意外影响多处）
- 新人上手周期变长
- 部署风险增加

**债务偿还策略**：
| 策略 | 说明 |
|------|------|
| **专门偿还迭代** | 每N个迭代安排一个"技术迭代"专门还债 |
| **童子军规则** | 每次修改代码时，让相关代码比原来更干净 |
| **债务上限** | 设定可接受的技术债务上限，超标时暂停需求开发 |
| **逐步偿还** | 每个Sprint分配固定比例（如20%）还债 |

### 5.4 架构技术债务识别方法

| 方法 | 说明 |
|------|------|
| **架构评审** | 定期评审架构，对比目标架构找差距 |
| **代码度量** | 圈复杂度、耦合度、包依赖分析 |
| **架构违规检测** | 使用工具（ArchUnit/SonarQube/Structure101）自动检测架构规则 |
| **质量属性评估** | 性能/安全性基准测试持续监控 |
| **团队反馈** | 收集开发者对"痛点"的反馈 |
| **部署频率分析** | 部署频率下降可能意味着架构腐化 |

## 6. 软件架构腐化与治理

### 6.1 架构腐化（Architecture Erosion）

**架构腐化**：随着时间推移，系统的实际实现逐渐偏离设计的架构，导致架构退化。

**腐化的典型表现**：
- 模块间出现未预期的依赖（循环依赖）
- 分层架构出现跨层/反向调用
- 微服务间出现"分布式单体"
- 接口不断膨胀（接口污染）
- 设计模式退化（如单例→全局变量滥用）

**腐化的根本原因**：
| 原因 | 说明 |
|------|------|
| **时间压力** | 赶工期走了捷径，绕过架构规范 |
| **知识流失** | 原始设计者离开，新人不知道架构意图 |
| **需求蠕变** | 不断添加新功能未在架构层面消化 |
| **缺少架构守护** | 无人持续监督架构一致性 |
| **技术演进不同步** | 部分模块技术升级，部分停留原地 |

### 6.2 架构治理（Architecture Governance）

**架构治理三支柱**：

| 支柱 | 内容 | 实践 |
|------|------|------|
| **规范定义** | 架构原则、标准、约束 | 编写架构决策记录（ADR）、编码规范 |
| **合规检查** | 确保实现符合架构规范 | 自动化架构测试、代码审查、架构评审 |
| **例外管理** | 处理必要的架构偏离 | 记录偏离和理由、设定偏离有效期和偿还计划 |

**架构治理组织职责**：
| 角色 | 职责 |
|------|------|
| **架构委员会（Architecture Board）** | 制定和维护架构原则、审批架构变更 |
| **首席架构师** | 架构愿景、重大技术决策、架构一致性守护 |
| **领域架构师** | 特定领域的架构设计和技术选型 |
| **开发团队** | 遵循架构规范、反馈问题、参与评审 |

### 6.3 防腐层（Anti-Corruption Layer, ACL）

**防腐层（ACL）**是DDD中提出的模式，用于在系统集成时保护自身领域模型不受外部系统的污染。

```
系统A（本系统）                 系统B（外部/遗留系统）
┌──────────────┐              ┌──────────────┐
│   领域模型    │              │   外部模型    │
└──────┬───────┘              └──────┬───────┘
       │                             │
       │    ┌──────────────┐         │
       └────│  防腐层(ACL)  │─────────┘
            │ 翻译+适配     │
            └──────────────┘
```

**ACL职责**：协议转换、数据模型映射、异常隔离。

**ACL的架构演化意义**：当外部系统变更或替换时，只需修改ACL，领域模型不受影响。

## 7. 软件架构演化的评估

### 7.1 演化可行性评估

在实施演化前，需要评估**演化成本**和**演化风险**：

| 评估维度 | 评估内容 |
|----------|---------|
| **技术可行性** | 目标架构的技术成熟度、团队能力匹配度 |
| **经济可行性** | 演化投入（人力/时间/资源）vs 预期收益 |
| **风险可控性** | 能否增量进行、能否随时回退 |
| **业务连续性** | 演化期间对业务的影响程度 |
| **数据迁移难度** | 数据迁移的工作量和风险 |

### 7.2 演化过程评估

在演化过程中持续评估架构状态：

| 评估指标 | 含义 | 测量方式 |
|----------|------|---------|
| **架构一致性** | 实现与目标架构的符合程度 | 架构违规检测工具 |
| **技术债务指数** | 债务积累程度 | SonarQube技术债务指标 |
| **质量属性满足度** | 是否达到演化阶段的质量目标 | 性能/安全基准测试 |
| **演化进度** | 完成迁移的模块/服务比例 | 进度跟踪看板 |
| **缺陷趋势** | 演化期间的缺陷率变化 | 缺陷密度统计 |

### 7.3 基于场景的演化分析

在架构演化场景下使用类似 ATAM 的方法评估演化对质量属性的影响：

```
演化前：
识别当前架构 → 分析当前质量属性基线 → 识别待改进点

演化方案评估：
对每个候选演化方案 → 分析各质量属性受影响程度 → 识别新的敏感点/权衡点

演化后：
验证质量属性 → 更新架构文档 → 记录经验教训
```

## 8. 软件产品线的架构演化

### 8.1 软件产品线中的架构角色

**软件产品线（Software Product Line, SPL）**：共享一组公共资产（核心架构+核心构件），通过变化点机制定制出多个产品。

**产品线架构的核心**：区分共性（Commonality）和可变性（Variability）。

### 8.2 产品线架构演化特点

| 演化类型 | 触发条件 | 处理方法 |
|----------|---------|---------|
| **核心资产演化** | 技术升级、质量属性提升 | 所有产品受影响，需升级兼容性测试 |
| **产品特定演化** | 某产品独有需求 | 尽量通过可变性机制处理，避免分支 |
| **可变性模型演化** | 新的市场变化产生新的可变点 | 扩展变化点机制，保持核心稳定 |

**产品线演化风险**：核心资产变更影响所有产品，需要全面的回归测试。

## 9. 架构演化与DevOps

### 9.1 持续交付环境下的架构演化

DevOps 对架构演化的影响：

| DevOps实践 | 对架构演化的支持 |
|-----------|-----------------|
| **CI/CD管道** | 支持小步快速演化，随时验证 |
| **基础设施即代码（IaC）** | 架构变更可版本化、可重现、可回滚 |
| **蓝绿部署** | 新旧架构平滑切换 |
| **金丝雀发布** | 新架构在小范围验证后逐步推广 |
| **监控与可观测性** | 演化效果实时可见，快速发现问题 |
| **混沌工程** | 验证演化后系统的韧性 |

### 9.2 演化驱动力——适应度函数（Fitness Functions）

**适应度函数**：自动化测试/度量，用于持续验证架构是否满足质量目标。

**类型**：
| 类型 | 验证内容 | 示例 |
|------|---------|------|
| **关键适应度函数** | 验证架构基本原则 | "所有模块依赖必须遵守分层规则" |
| **相关适应度函数** | 验证具体质量属性 | "API响应时间 < 200ms" |
| **过度工程适应度函数** | 检测过度设计 | "未使用的接口/抽象层" |

**适应度函数在演化中的作用**：每次代码变更自动运行，确保演化不破坏架构完整性。

### 10.2 架构演化的度量指标

| 度量 | 含义 | 趋势要求 |
|------|------|---------|
| **抽象度（A）** | 抽象组件数/总组件数 | 稳定 |
| **不稳定性（I）** | 传出耦合/(传出+传入耦合) | 适当 |
| **距主序列距离（D）** | D = \|A + I - 1\| | 越小越好 |
| **组件依赖深度** | 依赖链的最大长度 | 不宜过大 |
| **循环依赖数** | 包/模块间的循环依赖 | 趋零 |
| **核心/共享代码比** | 核心和共享代码占总代码比重 | 合理范围 |

> 距主序列距离 D = |A + I - 1| 是 Martin 提出的度量：A（抽象度）高的模块应稳定（I低），A低的模块允许不稳定（I高）。

## 11. 常考考点速查

### 11.1 核心概念对比

| A | B | 区别 |
|---|---|------|
| **演化（Evolution）** | **维护（Maintenance）** | 演化是结构级变更，维护是局部修正 |
| **绞杀者模式** | **大爆炸重写** | 前者增量替换，后者一次性重写 |
| **静态演化** | **动态演化** | 前者需停机，后者运行时进行 |
| **架构腐化** | **技术债务** | 腐化是过程/现象，债务是度量/结果 |
| **架构治理** | **项目管理** | 前者关注架构一致性，后者关注进度和资源 |
| **防腐层** | **适配器模式** | ACL是架构级隔离层，适配器是代码级转换 |

### 11.2 架构演化决策要点

```
架构需要演化吗？
├── 是 → 能增量进行吗？
│   ├── 是 → 绞杀者模式 / 抽象分支 → 制定路线图 → 分阶段执行
│   └── 否 → 是否可降级为可以增量？
│       ├── 是 → 重新设计演化方案
│       └── 否 → 极端情况才考虑大爆炸重写（需高层批准+严格验证）
└── 否 → 当前是否已存在技术债务？
    ├── 是 → 制定债务偿还计划
    └── 否 → 监控 + 定期架构评审
```

### 11.3 架构演进中常见陷阱

| 陷阱 | 说明 | 规避方法 |
|------|------|---------|
| **第二系统效应** | 重写时过度设计，复杂度远超原系统 | 保持克制，新架构满足当前需求即可 |
| **迁移无限延长** | 新旧系统并行时间过长，维护成本翻倍 | 设定DDL，优先迁移高频模块 |
| **数据不同步** | 新旧系统数据不一致 | 数据同步方案先于架构切换 |
| **迁移后性能倒退** | 新架构引入额外网络/序列化开销 | 演化前后性能基准对比 |
| **团队分裂** | 新老团队对立，知识断层 | 全员参与，渐进式交接 |
